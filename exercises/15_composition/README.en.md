# Exercise 15: Make it a component (RCLCPP_COMPONENTS) [Advanced]

The contents of the official tutorials
[Writing a Composable Node (C++)](https://docs.ros.org/en/jazzy/Tutorials/Intermediate/Writing-a-Composable-Node.html)
and
[Composing multiple nodes in a single process](https://docs.ros.org/en/jazzy/Tutorials/Intermediate/Composition.html)
are condensed into one class, `ComposableTalker`.

In the earlier exercises you made each node an executable with `add_executable` and
started it as a process with `ros2 run`. This exercise drops that approach, and
teaches a way of writing that **does not force "one process, one node"**.

## What to do

Fill in the TODOs in `src/composable_talker.cpp`. The specification is almost the same as the `MinimalPublisher` of exercise 01,
but there is one more rule to follow.

| Item | Value |
| --- | --- |
| Class name | `ComposableTalker` (no namespace) |
| Default node name | `composable_talker` |
| Topic name | `topic` |
| Type | `std_msgs::msg::String` |
| QoS depth | 10 |
| Period | 200ms |
| Message text | `"composable hello " + std::to_string(count_++)` |
| Log | `Publishing: '<message text>'` |

The class declaration (`include/drill/composable_talker.hpp`) is provided.
What goes into `publisher_` / `timer_` / `count_` follows the same idea as exercise 01.

There are three TODOs.

1. **The constructor passes `options` as it is to `Node`.**
   `explicit ComposableTalker(const rclcpp::NodeOptions & options)` must
   not throw away the `options` it receives, and must pass it as `Node("composable_talker", options)`.
2. **Create the Publisher and the timer.** The same as exercise 01.
3. **Register it at the end of the source.**
   ```cpp
   #include "rclcpp_components/register_node_macro.hpp"
   RCLCPP_COMPONENTS_REGISTER_NODE(ComposableTalker)
   ```
   Making you write this line is the heart of this exercise. Even if you fill in the other two perfectly,
   without this registration `component_container` cannot
   notice that this class exists.

## The meaning of passing NodeOptions

`component_container` does not instantiate this class directly with `new ComposableTalker()`.
It builds a `NodeOptions` through the
factory generated by `RCLCPP_COMPONENTS_REGISTER_NODE` and then creates the node. This
`NodeOptions` carries settings decided at run time, such as the following.

- Remapping of node names and topic names, such as `--ros-args -r __node:=foo`
- Parameters passed with `--ros-args -p param:=value`
- `use_intra_process_comms(true)` (the zero-copy communication of exercise 14). A component
  is a mechanism for putting several nodes in the same process, so whether zero copy works
  can be controlled only through NodeOptions.

If the constructor receives `options` but hard-codes `Node("composable_talker")`,
none of these settings are reflected.

## Advantages of components

- **Zero copy works with intra-process communication.** The
  `use_intra_process_comms(true)` you saw in exercise 14 works only when the Publisher and the Subscription are in the
  same process. If you split the nodes into executables,
  the communication goes over DDS and you cannot get the benefit. With components,
  you can put several nodes in one process, so this optimization becomes possible.
- **You can rearrange the startup setup with launch.** Which nodes to put together in which process
  can be changed only by editing the launch file, without changing the C++ code
  (see the launch example below).
- **You can reduce the number of processes.** If you start as many processes as there are nodes, the overhead of context
  switching and memory adds up. If you put closely related nodes together in
  one process, you can reduce them.

## The difference from an `add_executable` executable

The earlier exercises (for example, the `talker` of exercise 01) were "ordinary executables" made with `add_executable`.
They are processes dedicated to that node, which only call `rclcpp::spin()` inside `main()`.
They cannot share a process with other nodes.

Components are different. `ComposableTalker` is built as part of a **shared library** made with `add_library(... SHARED)`,
and has no `main()`.
`component_container` (itself just an executable) does `dlopen` on this `.so` at startup or
at run time, creates an instance through the factory registered by `RCLCPP_COMPONENTS_REGISTER_NODE`,
and puts it on its own Executor and spins it. You can load any number of other components
into the same container, and they all run in the same process and the same Executor.

## The CMake side

In `CMakeLists.txt`, these two lines are the key.

```cmake
add_library(${PROJECT_NAME}_node SHARED src/composable_talker.cpp)
...
rclcpp_components_register_node(${PROJECT_NAME}_node
  PLUGIN "ComposableTalker"
  EXECUTABLE composable_talker_node
)
```

- `add_library(... SHARED)`: Build it as a shared library, not an executable.
  This is required to make it something that can be `dlopen`ed.
- `rclcpp_components_register_node(...)`: It does two things.
  1. It writes the plugin name given by `PLUGIN` and the location of the library
     into the ament resource index
     (`share/ament_index/resource_index/rclcpp_components/<package name>`).
     `component_container` and `ros2 component types` look at this index
     to find the components that can be loaded.
  2. It automatically generates an executable with the name given by `EXECUTABLE` (this time
     `composable_talker_node`). Its contents are just a thin wrapper that loads this `.so` with
     `class_loader` and spins it as a single node, and you do not need to write
     `add_executable` yourself.

Whether `component_container` can actually find the component finally depends on
whether `RCLCPP_COMPONENTS_REGISTER_NODE(ComposableTalker)`
(the plugin registration macro of `class_loader`) is written in the source code.
The CMake settings alone cannot find a class
whose registration macro was forgotten.

After the tests pass, let's load it dynamically into `component_container` and
check. First start the container in another terminal.

```bash
ros2 run rclcpp_components component_container         # another terminal
```

From one more terminal, check the list of loadable components and load it.

```bash
ros2 component list
ros2 component load /ComponentManager drill_15_composition ComposableTalker
ros2 topic echo /topic
```

At the moment you type `ros2 component list`, nothing is loaded yet, so it is
empty. If you type it again after `load`, you can see
`ComposableTalker` hanging under the container's process.

If you just want to run it alone, you can also use the executable that
`rclcpp_components_register_node` generated automatically.

```bash
ros2 run drill_15_composition composable_talker_node
```

## Putting several components in one process from launch

With `ComposableNodeContainer` and `ComposableNode`, you can write a launch file that starts several components
together in one process.

```python
from launch import LaunchDescription
from launch_ros.actions import ComposableNodeContainer
from launch_ros.descriptions import ComposableNode


def generate_launch_description():
    container = ComposableNodeContainer(
        name='drill_container',
        namespace='',
        package='rclcpp_components',
        executable='component_container',
        composable_node_descriptions=[
            ComposableNode(
                package='drill_15_composition',
                plugin='ComposableTalker',
                name='composable_talker',
                # Intra-process communication (the zero copy of exercise 14) is disabled by default.
                # If you want to use it, enable it explicitly here.
                extra_arguments=[{'use_intra_process_comms': True}],
            ),
            # If you add other components to the same container too,
            # they run in the same process and the same Executor.
        ],
        output='screen',
    )
    return LaunchDescription([container])
```

**Note: Making it a component alone does not give you zero copy.** A component only
satisfies the precondition of "being in the same process", and intra-process communication itself
works only when you explicitly enable `use_intra_process_comms`
(the default in `rclcpp/node_options.hpp` is `false`). The official
`composition_demo_launch.py` does not enable it either, so the
talker / listener started by that launch file communicate over DDS even though they are in the same process.

It is the same when you load from the CLI, and the official tutorial passes it explicitly.

```bash
ros2 component load /ComponentManager composition composition::Talker \
  -e use_intra_process_comms:=true
```

You can also start a node made with `add_executable` as a separate process from the same launch file,
but in that case you cannot put it in the same process as above.
Being able to choose "whether to put them in the same process" with only the launch file
is the biggest advantage of components.

## Common pitfalls

- If you write `Node("composable_talker")` and forget to pass `options`, you get a node where remapping and
  parameter settings with `--ros-args` do not work (detected by test 1).
- If you forget to write `RCLCPP_COMPONENTS_REGISTER_NODE(ComposableTalker)`, the
  build itself passes normally. It is complete as a shared library,
  but it becomes an "invisible" component that cannot be loaded from `component_container`
  (detected by test 3).
- The argument of the registration macro (`ComposableTalker`) must match the string in
  `rclcpp_components_register_node(... PLUGIN "ComposableTalker" ...)` in `CMakeLists.txt`.
