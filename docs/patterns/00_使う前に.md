# 0. 使う前に — パターンがコードを壊すとき

> **この章のねらい**: 輪読の直後が、いちばんコードを壊しやすい時期です。
> 「パターンを知らないから汚くなる」より、
> **「覚えたてのパターンを使いすぎて汚くなる」**方が圧倒的に多い。
> 先に、やりがちな 4 つの壊し方を見ておきます。

この章にコードの課題はありません。5 分で読めます。

## 0.1 実装が 1 つしかないのに抽象化する（Strategy 病）

輪読で Strategy を読んだ翌日に、こうなります。

```cpp
// 悪い例：実装が MotorDriverImpl 1 つしかない
class IMotorDriver
{
public:
  virtual ~IMotorDriver() = default;
  virtual void set_duty(double duty) = 0;
};

class MotorDriverImpl : public IMotorDriver
{
public:
  void set_duty(double duty) override { /* ... */ }
};
```

インタフェースが 1 実装しか持たないなら、それは抽象化ではなく**ファイルが 2 つに増えただけ**です。
呼ぶ側は `IMotorDriver` を見ても何が起きるか分からず、実装を探しに行く手間だけが増えます。

```cpp
// まずこれでいい
class MotorDriver
{
public:
  void set_duty(double duty) { /* ... */ }
};
```

**判断基準**: 「2 つ目の実装が**今**あるか、次の 1 か月で確実に来るか」。
テストのためのモックは 2 つ目に数えて構いませんが、それなら
「テスト用に差し替えたい」と理由を書いてください。

## 0.2 グローバル変数を Singleton に改名する

第 5 章のあとに来ます。

```cpp
// 悪い例：ただのグローバル変数
class Config
{
public:
  static Config & instance();
  int motor_max_duty = 100;
};
```

Singleton にしても、**グローバル変数の問題は 1 つも解決していません**。

- どこからでも書き換えられる
- テストで差し替えられない（前のテストの状態が次に漏れる）
- 誰が依存しているかコードから読めない
- マルチスレッドで壊れる

むしろ「パターンを使った」という理由で、**グローバル変数への罪悪感だけが消えます**。これが一番害です。

**まず引数で渡せないか考えてください。** `Config` を使う関数が 3 つなら、3 つに渡せば済みます。
本当にシングルトンが要るのは、**ハードウェアが 1 つしかない**とき（`UART1` は世界に 1 個）です。
その話は第 5 章でやります。

## 0.3 生成が 3 段になる

Factory Method と Abstract Factory を続けて読むと起きます。

```cpp
auto factory = SensorFactoryProvider::instance().get_factory("imu");
auto builder = factory->create_builder();
auto sensor  = builder->with_address(0x68)->build();
```

`Imu sensor{0x68};` で済むものが 3 行になっています。
このコードで得したのは「センサの種類を実行時の文字列で切り替えられる」ことだけです。
**部活のライブラリで、センサの種類を実行時に文字列で決める場面が本当にありますか。**
コンパイル時に決まっているなら、Factory は要りません。

## 0.4 Observer で通知が循環する

第 17 章。C++ ではさらに寿命の問題が乗ります。

```cpp
// A が更新されると B に通知、B が更新されると A に通知
a.add_observer(&b);
b.add_observer(&a);   // 無限ループ
```

さらに C++ 固有として、**購読者が先に死ぬ**と生ポインタが宙に浮きます。

```cpp
{
  Display display;
  sensor.add_observer(&display);
}                                 // display が死ぬ。sensor はまだ &display を持っている
sensor.notify();                  // 未定義動作
```

Java なら GC が生かしておくので（それはそれでリークですが）落ちません。
C++ では落ちます。第 17 章の本題はここです。

## 0.5 まとめ — 使う前のチェック

パターンを入れる前に、この 4 つを自分に聞いてください。

1. **今、実装は 2 つ以上あるか。** 1 つなら入れない
2. **この抽象を消したら、どの変更が難しくなるか。** 答えられないなら入れない
3. **誰がこのオブジェクトを解放するか、1 行で言えるか。** 言えないなら設計が未完成
4. **標準ライブラリに同じものが無いか。** Iterator・Proxy・Flyweight・Command は既にある

「グチャグチャにならないためにパターンを使う」のは半分正しくて、半分逆です。
**グチャグチャにしないのは、パターンではなく「所有権が明確であること」と「抽象の数が少ないこと」です。**
パターンはそのための道具の一部でしかありません。
