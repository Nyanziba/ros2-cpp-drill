# 6. スマートポインタ

> **この章のねらい**: ドリルで `make_shared` は **89 回**出てきます。全構文の中で 2 番目に多い。
> そして、初学者が最初に踏むバグはこれです。
>
> ```cpp
> MinimalPublisher::MinimalPublisher() : Node("minimal_publisher")
> {
>   auto publisher = this->create_publisher<std_msgs::msg::String>("topic", 10);
>   //   ^^^^^^^^^ メンバ変数 publisher_ ではなくローカル変数にしてしまった
> }
> ```
>
> **エラーは出ません。警告も出ません。ただ何も publish されません。**
> なぜそうなるのかを、`shared_ptr` と `weak_ptr` の仕組みから説明します。
> この章が終われば、rclcpp のあの「戻り値を必ずメンバに持て」という作法が
> 暗記事項ではなく当然の帰結として読めるようになります。

> **前提**: 生のポインタが分かっている前提です。
> 不安なら[入門編 4章 ポインタ①](../cpp-basics/04_ポインタ1.md)と
> [5章 ポインタ②](../cpp-basics/05_ポインタ2.md)を先に。
> **`nullptr` と間接参照が分かっていないと、`weak_ptr` の `lock()` が何をしているか掴めません。**

## 6.1 生ポインタの何が問題なのか

```cpp
void leaky()
{
  int * p = new int(42);
  if (something_wrong) {
    return;              // delete し忘れ → リーク
  }
  may_throw();           // 例外が飛ぶ → リーク
  delete p;
}
```

`delete` を書く場所が「関数を抜けるすべての経路」にあります。
`return` が 3 箇所あれば 3 箇所、例外が飛ぶ可能性があればさらに増えます。

2 章の RAII を思い出してください。**デストラクタは必ず呼ばれます。**
なら「デストラクタで `delete` するクラス」に包んでしまえば、書き忘れが構造的になくなります。
それがスマートポインタです。

3 種類あります。使い分けは **「所有者は何人か」** で決まります。

| 型 | 所有者 | コピー | ドリルでの出現 |
| --- | --- | --- | --- |
| `std::unique_ptr<T>` | **1 人** | できない（ムーブのみ） | 6 回 |
| `std::shared_ptr<T>` | **複数** | できる（参照カウント） | 33 回 + `make_shared` 89 回 |
| `std::weak_ptr<T>` | **0 人**（観測するだけ） | できる | 0 回（ただし rclcpp の内部が使っている） |

## 6.2 `unique_ptr` — 所有者は 1 人

```cpp
#include <iostream>
#include <memory>

int main()
{
  auto p = std::make_unique<int>(42);
  std::cout << *p << "\n";              // 42
  std::cout << p.get() << "\n";         // アドレス

  // auto q = p;                        // エラー: コピーできない
  auto q = std::move(p);                // ムーブなら可
  std::cout << (p == nullptr) << "\n";  // 1（ムーブ元は nullptr が保証される）

  return 0;                             // ここで q が delete する
}
```

`delete` を書いていません。`q` のデストラクタがやってくれます。

コピーできないのは、`std::unique_ptr` が 2 章で見た `= delete` を使っているからです。

```cpp
unique_ptr(const unique_ptr &) = delete;
unique_ptr & operator=(const unique_ptr &) = delete;
```

**「所有者は 1 人」という設計方針が、型で強制されています。**
うっかり 2 人にしようとするとコンパイルエラーになります。

5 章で書いたとおり、`unique_ptr` は**ムーブ後に必ず `nullptr` になることが規格で保証**されています。
これは `std::string` などの「有効だが未規定」より強い保証です。

### `->` と `*` と `.get()`

```cpp
auto p = std::make_unique<std_msgs::msg::String>();

p->data = "hello";        // 指す先のメンバ（いちばん使う）
(*p).data = "hello";      // 同じ意味。誰も書かない
std::string s = *p;       // 指す先そのもの（コピーが起きる）
p.get();                  // 生ポインタを取り出す（所有権は渡さない）
p.reset();                // 今すぐ解放する
```

`->` と `.` の区別は重要です。

- `p->data` — **指す先**（`std_msgs::msg::String`）のメンバ
- `p.get()` — **スマートポインタ自身**のメンバ関数

課題 14 で `msg.get()` と `msg->data` が両方出てきます。

```cpp
// solutions/14_zero_copy/src/zero_copy_nodes.cpp
auto msg = std::make_unique<std_msgs::msg::String>();
ss << std::hex << reinterpret_cast<std::uintptr_t>(msg.get());   // ← アドレスを見る
msg->data = ss.str();                                             // ← 中身を書く
```

**`.get()` で得た生ポインタを `delete` しないでください。**
所有権はまだスマートポインタが持っているので、二重解放になります。
`get()` は「見るだけ」「C の API に渡すだけ」に使います。

### `make_unique` と `new` の違い

```cpp
auto a = std::make_unique<Foo>(1, 2);           // 推奨
std::unique_ptr<Foo> b(new Foo(1, 2));          // 動くが冗長
```

`make_unique` を使う理由は 3 つです。

1. 型を 1 回しか書かない（`b` の行は `Foo` が 2 回出てくる）
2. `new` を書かないので、`delete` を探す必要が構造的になくなる
3. 例外安全（引数の評価中に例外が飛んでもリークしない）

**`shared_ptr` では 3 番目に加えてもう 1 つ理由があります。** 次の節で扱います。

## 6.3 `shared_ptr` — 参照カウント

```cpp
#include <iostream>
#include <memory>

int main()
{
  auto a = std::make_shared<int>(42);
  std::cout << "a のみ:      " << a.use_count() << "\n";   // 1

  {
    auto b = a;                                             // コピー（カウント +1）
    std::cout << "a と b:      " << a.use_count() << "\n";  // 2

    auto c = a;
    std::cout << "a と b と c: " << a.use_count() << "\n";  // 3
  }   // b と c がここで消える

  std::cout << "戻って:      " << a.use_count() << "\n";    // 1
  return 0;                                                 // 0 になり delete
}
```

```
a のみ:      1
a と b:      2
a と b と c: 3
戻って:      1
```

**最後の所有者が消えたときに `delete` されます。**
「誰が最後か」を人間が管理しなくてよいのが値打ちです。

`shared_ptr` は 2 つのものを指しています。

```
  a ─┬─▶ 制御ブロック { 強参照カウント=1, 弱参照カウント=0, deleter }
     └─▶ オブジェクト { 42 }
```

だから `shared_ptr` は生ポインタの 2 倍（16 バイト）あります。
カウントの増減はアトミック操作なので、コピーは無料ではありません。
**関数に渡すだけなら `const shared_ptr<T> &` にするか、`const T &` にする**のが軽いです。

### `make_shared` を使う理由

```cpp
auto a = std::make_shared<Foo>();               // 確保 1 回
std::shared_ptr<Foo> b(new Foo());              // 確保 2 回
```

`make_shared` は**オブジェクトと制御ブロックを 1 回の確保でまとめて取ります。**
`new` を使う形は、オブジェクトで 1 回、制御ブロックで 1 回、計 2 回確保します。

**ドリルで `make_shared` が 89 回出てくるのはこれが標準的な書き方だからです。**

```cpp
rclcpp::spin(std::make_shared<MinimalPublisher>());
auto request = std::make_shared<AddTwoInts::Request>();
```

（トレードオフもあります。`make_shared` はオブジェクトと制御ブロックが同じ確保なので、
`weak_ptr` が生き残っている間はオブジェクト部分のメモリも解放されません。
巨大なオブジェクトで `weak_ptr` を長く持つ場合だけ問題になる話で、ドリルでは関係しません。）

### 同じ生ポインタから 2 回作ってはいけない

```cpp
Foo * raw = new Foo();
std::shared_ptr<Foo> a(raw);
std::shared_ptr<Foo> b(raw);      // 制御ブロックが 2 つできる → 二重解放
```

`a` と `b` はそれぞれ「自分がカウント 1 の唯一の所有者」だと思っています。
両方がスコープを抜けると `delete` が 2 回走ってクラッシュします。

**`make_shared` を使えばこの事故は起こせません。** 生ポインタが表に出ないからです。

### 循環参照 — `shared_ptr` が漏れる唯一のパターン

```cpp
#include <iostream>
#include <memory>

struct Node
{
  std::shared_ptr<Node> other;
  ~Node() { std::cout << "破棄\n"; }
};

int main()
{
  auto a = std::make_shared<Node>();
  auto b = std::make_shared<Node>();
  a->other = b;     // a が b を持つ
  b->other = a;     // b が a を持つ
  std::cout << "main を抜けます\n";
  return 0;
}
```

```
main を抜けます
```

**「破棄」が出ていません。** 2 つとも漏れました。

`main` を抜けて `a` と `b` の変数が消えても、
`a` のカウントは `b->other` が握っているので 1、`b` のカウントも `a->other` が握っているので 1。
どちらも 0 にならないので、永久に解放されません。

これを断ち切るのが `weak_ptr` です。

## 6.4 `weak_ptr` — 所有せずに観測する

`weak_ptr` は「そこにまだ在るか」を確認できるが、**生かし続けはしない**参照です。

```cpp
#include <iostream>
#include <memory>

int main()
{
  std::weak_ptr<int> w;

  {
    auto s = std::make_shared<int>(42);
    w = s;                                          // 弱参照（カウントは増えない）
    std::cout << "生存中 use_count = " << s.use_count() << "\n";   // 1

    if (auto locked = w.lock()) {                   // 一時的に強参照に昇格
      std::cout << "lock 成功: " << *locked << "\n";
    }
  }   // s が消える → オブジェクトは delete される

  std::cout << "expired = " << w.expired() << "\n";  // 1

  if (auto locked = w.lock()) {
    std::cout << "lock 成功\n";
  } else {
    std::cout << "lock 失敗（もう無い）\n";
  }
  return 0;
}
```

```
生存中 use_count = 1
lock 成功: 42
expired = 1
lock 失敗（もう無い）
```

`w = s` してもカウントが 1 のままなことを確認してください。**弱参照は数に入りません。**

使い方は必ず `lock()` 経由です。

```cpp
if (auto p = w.lock()) {
  // p は shared_ptr。このブロックの中では絶対に生きている
}
```

`lock()` が返すのは `shared_ptr` で、成功すれば一時的にカウントが +1 されます。
**`w.expired()` で確認してから使う、という書き方は避けてください。**
確認した直後に他のスレッドが解放する可能性があります（TOCTOU）。
`lock()` は確認と取得を同時にやるので安全です。

循環参照は、片方を `weak_ptr` にすれば解けます。

```cpp
struct Node
{
  std::shared_ptr<Node> child;
  std::weak_ptr<Node> parent;      // 親は弱く持つ
};
```

「親が子を所有し、子は親を観測するだけ」という非対称にするのが定石です。

## 6.5 なぜ戻り値をメンバに持たないと動かないのか

ここまでの道具で、冒頭の謎を説明できます。

`create_publisher()` の戻り値は `shared_ptr` です。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp
template<typename MessageT, ...>
std::shared_ptr<PublisherT>
create_publisher(const std::string & topic_name, const rclcpp::QoS & qos, ...);
```

そして **rclcpp 側はそれを `weak_ptr` でしか持ちません。**

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/callback_group.hpp
for (auto & weak_ptr : vect_ptrs) {
  auto ref_ptr = weak_ptr.lock();
  ...
}
```

`add_publisher()` は引数として `SharedPtr` を受け取りますが、
内部で `weak_ptr` に変換して保持します。

つまり所有権の構図はこうです。

```
あなたのコード（メンバ変数 publisher_）
   │  shared_ptr（強参照・唯一の所有者）
   ▼
Publisher<T>
   ▲
   │  weak_ptr（生死の確認だけ。所有はしない）
CallbackGroup ◀───── weak_ptr ───── Executor
```

**強い矢印は「あなたのコード」からしか伸びていません。**

だから

```cpp
auto publisher = this->create_publisher<...>("topic", 10);   // ローカル変数
```

と書くと、コンストラクタを抜けた瞬間にカウントが 0 になって `Publisher` が破棄されます。
rclcpp 側に残っているのは `weak_ptr` だけなので、`lock()` は毎回 `nullptr` を返します。
Executor は「そのエンティティはもう無い」と判断して、**何も実行しません。**

エラーも警告も出ません。**これは「うっかりミス」ではなく、
「所有権を持っていないものは消える」という C++ として当然の帰結です。**

同じ構造がノードと Executor の間にもあります。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/executors/executor_entities_collector.hpp
using NodeCollection = std::set<
  rclcpp::node_interfaces::NodeBaseInterface::WeakPtr,
  std::owner_less<rclcpp::node_interfaces::NodeBaseInterface::WeakPtr>>;
NodeCollection weak_nodes_ RCPPUTILS_TSA_GUARDED_BY(mutex_);
```

**Executor もノードを所有しません。** だから

```cpp
rclcpp::spin(std::make_shared<MinimalPublisher>());
```

の `make_shared` の戻り値は `spin()` の引数として生きているあいだだけ有効で、
`spin` が `shared_ptr` を値で受け取っているからノードが生き続けます。

課題 07 でも同じ罠が待っています。

```cpp
// ParameterEventHandler のコメント
// Note: the object returned from add_parameter_callback must be captured
// or the callback will [be unregistered].
```

`add_parameter_callback` の戻り値（`ParameterCallbackHandle::SharedPtr`）を
保持しないと、登録した直後にコールバックが解除されます。**同じ設計、同じ罠です。**

**規則は 1 つ覚えれば済みます。rclcpp が `shared_ptr` を返してきたら、メンバに持つ。**

## 6.6 rclcpp の型エイリアス

rclcpp のクラスは `SharedPtr` という別名を持っています。

```cpp
rclcpp::Publisher<std_msgs::msg::String>::SharedPtr publisher_;
rclcpp::TimerBase::SharedPtr timer_;
rclcpp::Node::SharedPtr node;
std_msgs::msg::String::ConstSharedPtr msg;
```

これは `std::shared_ptr<...>` と**まったく同じもの**です。

```cpp
// この 2 つは同じ型
rclcpp::Publisher<std_msgs::msg::String>::SharedPtr a;
std::shared_ptr<rclcpp::Publisher<std_msgs::msg::String>> b;
```

正体はマクロです。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/macros.hpp:36
#define RCLCPP_SMART_PTR_DEFINITIONS(...) \
  RCLCPP_SHARED_PTR_DEFINITIONS(__VA_ARGS__) \
  RCLCPP_WEAK_PTR_DEFINITIONS(__VA_ARGS__) \
  RCLCPP_UNIQUE_PTR_DEFINITIONS(__VA_ARGS__)
```

`rclcpp::Node` の `public` セクションの 1 行目がこれです。

```cpp
// node.hpp:82
RCLCPP_SMART_PTR_DEFINITIONS(Node)
```

`SharedPtr` / `WeakPtr` / `UniquePtr` / `ConstSharedPtr` の別名と、
`Node::make_shared(...)` という静的関数が一括で定義されます。

**`std::shared_ptr<...>` を長々と書く代わりの省略記法**だと思ってください。
ネストしたテンプレートは行長 100 文字にすぐ収まらなくなるので、実用的な工夫です。

### `enable_shared_from_this`

3 章で見た `Node` の宣言に戻ります。

```cpp
// node.hpp:79
class Node : public std::enable_shared_from_this<Node>
```

これを継承すると、メンバ関数の中から**自分自身の `shared_ptr` を取れます。**

```cpp
void MyNode::register_somewhere()
{
  some_registry.add(shared_from_this());   // 自分の shared_ptr
}
```

なぜ必要か。`this` は生ポインタなので、そこから `shared_ptr` を作ってはいけません。

```cpp
some_registry.add(std::shared_ptr<Node>(this));   // 絶対にダメ
```

新しい制御ブロックができて、6.3 節の二重解放になります。
`shared_from_this()` は**既存の制御ブロックを見つけて**カウントを +1 します。

**注意点が 1 つ。`shared_ptr` として作られていないオブジェクトで
`shared_from_this()` を呼ぶと例外（`std::bad_weak_ptr`）が飛びます。**

```cpp
MinimalPublisher node;                              // スタック上
node.some_method_calling_shared_from_this();        // std::bad_weak_ptr

auto node = std::make_shared<MinimalPublisher>();   // これなら OK
```

コンストラクタの中でも呼べません（制御ブロックがまだ紐付いていない）。

**これも「ノードは必ず `make_shared` で作る」理由の 1 つです。**
`rclcpp::spin(std::make_shared<MinimalPublisher>())` という定型が、
3 章のコピー禁止と、この `enable_shared_from_this` の両方から要求されています。

## 手元で試す

**カウントを目で見て、循環参照を自分で作って壊します。**

```cpp
// ptr.cpp
#include <iostream>
#include <memory>
#include <string>

struct Resource
{
  std::string name;
  explicit Resource(std::string n) : name(std::move(n))
  {
    std::cout << "  [" << name << "] 確保\n";
  }
  ~Resource() { std::cout << "  [" << name << "] 解放\n"; }
};

void observe(const std::weak_ptr<Resource> & w, const char * tag)
{
  if (auto p = w.lock()) {
    std::cout << tag << ": 生きている (" << p->name << ")\n";
  } else {
    std::cout << tag << ": もう無い\n";
  }
}

int main()
{
  std::cout << "-- unique_ptr\n";
  {
    auto u = std::make_unique<Resource>("unique");
    // auto copy = u;                 // ① コメントを外すと何のエラーか
    auto moved = std::move(u);
    std::cout << "  u は null か: " << (u == nullptr) << "\n";
  }

  std::cout << "\n-- shared_ptr のカウント\n";
  std::weak_ptr<Resource> w;
  {
    auto a = std::make_shared<Resource>("shared");
    w = a;
    std::cout << "  a だけ:        " << a.use_count() << "\n";
    {
      auto b = a;
      std::cout << "  a と b:        " << a.use_count() << "\n";
      observe(w, "  内側");
    }
    std::cout << "  b が消えた後: " << a.use_count() << "\n";
  }
  observe(w, "  外側");

  std::cout << "\n-- 循環参照\n";
  struct Cycle
  {
    std::string name;
    std::shared_ptr<Cycle> other;      // ② weak_ptr に変えるとどうなるか
    explicit Cycle(std::string n) : name(std::move(n)) {}
    ~Cycle() { std::cout << "  [" << name << "] 解放\n"; }
  };
  {
    auto x = std::make_shared<Cycle>("X");
    auto y = std::make_shared<Cycle>("Y");
    x->other = y;
    y->other = x;
    std::cout << "  x.use_count = " << x.use_count() << "\n";
    std::cout << "  スコープを抜けます\n";
  }
  std::cout << "  抜けました\n";
  return 0;
}
```

**予想を 4 つ立ててください。**

1. `w = a` した時点で `use_count` は 1 か 2 か
2. 外側の `observe` は「生きている」か「もう無い」か
3. `x.use_count` は何になるか
4. 循環参照のブロックを抜けたとき `[X] 解放` `[Y] 解放` は出るか

```bash
g++ -std=c++17 -Wall -Wextra ptr.cpp -o ptr && ./ptr
```

確認したら 2 つ変更してください。

**① `auto copy = u;` のコメントを外す。**
エラーメッセージを読んでください。`use of deleted function` が出ます。
「所有者は 1 人」が型で強制されていることの実物です。

**② `std::shared_ptr<Cycle> other;` を `std::weak_ptr<Cycle> other;` に変える。**
`x->other = y;` はそのまま通ります（`weak_ptr` に `shared_ptr` を代入できる）。
出力がどう変わるか。`use_count` はどうなるか。

最後に、**この章の主題であるバグを再現します。**
6.5 節の構図を、rclcpp なしで模擬したものです。

```cpp
// weakbug.cpp
#include <iostream>
#include <memory>
#include <vector>

struct Timer
{
  int id;
  explicit Timer(int i) : id(i) {}
  void fire() const { std::cout << "  timer " << id << " 発火\n"; }
};

class Executor
{
public:
  void add(const std::shared_ptr<Timer> & t) { timers_.push_back(t); }   // weak で持つ

  void spin_once()
  {
    for (const auto & w : timers_) {
      if (auto t = w.lock()) {
        t->fire();
      } else {
        std::cout << "  （消えているエンティティを 1 つ飛ばした）\n";
      }
    }
  }

private:
  std::vector<std::weak_ptr<Timer>> timers_;      // ← rclcpp と同じ
};

class GoodNode
{
public:
  explicit GoodNode(Executor & e)
  {
    timer_ = std::make_shared<Timer>(1);
    e.add(timer_);
  }
private:
  std::shared_ptr<Timer> timer_;                 // メンバに持つ
};

class BadNode
{
public:
  explicit BadNode(Executor & e)
  {
    auto timer = std::make_shared<Timer>(2);     // ローカル変数にしてしまった
    e.add(timer);
  }
};

int main()
{
  Executor exec;
  GoodNode good(exec);
  BadNode bad(exec);
  std::cout << "spin_once:\n";
  exec.spin_once();
  return 0;
}
```

**予想: `timer 1` と `timer 2` はどちらが発火するか。**

```bash
g++ -std=c++17 -Wall -Wextra weakbug.cpp -o weakbug && ./weakbug
```

`BadNode` にはエラーも警告も出ません。**これが課題 01 で最も多いつまずきの正体です。**
`BadNode` を直して両方発火することを確認してください。

## つまずきポイント

**`error: use of deleted function ‘std::unique_ptr<...>::unique_ptr(const std::unique_ptr<...>&)’`**
`unique_ptr` をコピーしようとしています。`std::move` を付けるか、`shared_ptr` にします。

**`error: invalid use of incomplete type`**
前方宣言（`class Foo;`）しかしていない型のスマートポインタで、`*p` や `p->x` を使っています。
その型の完全な定義を `#include` してください。
`unique_ptr` はデストラクタで完全な型を要求するので、メンバに持つだけでも
デストラクタを `.cpp` 側に書く必要が出ることがあります。

**セグメンテーション違反になった**
3 つの定番があります。

1. ムーブ後のポインタを使った（`p` は `nullptr`）
2. `lock()` の結果を確認せずに使った
3. `.get()` した生ポインタを、スマートポインタが死んだ後に使った

`nullptr` を経由した落ち方は、`gdb` で見ると一目で分かります。

```bash
gdb --batch -ex run -ex bt ./your_binary
```

**`std::bad_weak_ptr` が飛んだ**
`shared_ptr` として作られていないオブジェクトで `shared_from_this()` を呼んでいます。
またはコンストラクタの中で呼んでいます。6.6 節。

**`use_count()` が思った値と違う**
デバッグ以外で `use_count()` を使わないでください。
「1 なら自分だけ」という判定はマルチスレッドでは競合します。
ドリルでは `expired()` / `lock()` で足ります。

**publish しているのに `ros2 topic echo` に何も出ない**
この章の 6.5 節です。まず `create_publisher` / `create_wall_timer` の戻り値が
メンバ変数に入っているかを確認してください。
QoS の非互換（12 章相当。ドリルでは課題 12）でも同じ症状になりますが、
**戻り値の保持のほうが圧倒的に多い原因です。**

## ドリルのどこで出るか

| 課題 | この章の何が出るか |
| --- | --- |
| 01 | `publisher_` / `timer_` をメンバに持つ。**ここを外すと何も起きない** |
| 02 | `subscription_` をメンバに持つ |
| 04, 05 | `service_` / `client_` をメンバに。`std::make_shared<AddTwoInts::Request>()` |
| 05 | `async_send_request` の戻り値（future）を受ける |
| 07 | `ParameterEventHandler` と `ParameterCallbackHandle` の**両方**を保持する必要がある |
| 10 | アクションの `GoalHandle` を `shared_ptr` で受け取る |
| 13 | `rclcpp::CallbackGroup::SharedPtr` をメンバに持つ |
| 14 | `std::make_unique` → `std::move` で publish。`msg.get()` でアドレスを見る |
| 全課題 | `rclcpp::spin(std::make_shared<...>())` |

課題 07 が「保持し忘れ」のいちばん厳しい例です。**2 つ持たないといけません。**

```cpp
private:
  std::shared_ptr<rclcpp::ParameterEventHandler> param_subscriber_;   // ①
  std::shared_ptr<rclcpp::ParameterCallbackHandle> cb_handle_;        // ②
```

① だけ持って ② を捨てると、コールバックが登録された直後に解除されます。
② だけ持って ① を捨てると、`/parameter_events` の購読自体が消えます。
**どちらもエラーにならず、ただコールバックが呼ばれません。**

課題 07 の README が「今回いちばんのハマりどころ」と書いているのはこれです。
6.5 節の構図が分かっていれば、「rclcpp が返す `shared_ptr` は全部メンバに持つ」で機械的に回避できます。
