# 5. ムーブと所有権

> **この章のねらい**: 課題 14 でこの 1 行を書きます。
>
> ```cpp
> publisher_->publish(std::move(msg));
> ```
>
> `std::move` は名前に反して**何も動かしません。** 実体は 1 行のキャストです。
> それなのに、この 1 行があるかないかで「メッセージのコピーが 1 回起きるか 0 回か」が変わり、
> 課題 14 のテストは**メッセージのアドレスを比較して**それを検出します。
> この章で「所有権を渡す」という考え方を身につけます。
> C++ でいちばん誤解が多い機能なので、`std::move` の中身まで見ます。

> **前提**: [入門編 9章 値のセマンティクス](../cpp-basics/09_値のセマンティクス.md)で
> 「代入はコピー」「コピーがいつ何回起きるか」を扱っています。
> **ムーブはその続き**です。コピー回数を数えられる状態で読んでください。
> ポインタが不安なら[4章](../cpp-basics/04_ポインタ1.md)・[5章](../cpp-basics/05_ポインタ2.md)へ。

## 5.0 なぜムーブという機能が必要になったのか

先に「何を解決したかったのか」から入ります。ここが分かると残りが全部理由の付いた話になります。

C++11 より前、オブジェクトを関数に渡したり返したりする方法は**2 つしかありませんでした。**

1. **コピーする** — 安全。ただし中身が大きいと遅い
2. **ポインタ／参照を渡す** — 速い。ただし**誰が解放するのか**が型に現れない

2 番の問題が深刻でした。

```cpp
std::vector<int> * make_data();     // 戻り値は誰が delete するのか？
```

シグネチャを見ても分かりません。ドキュメントを読むしかなく、読まなければリークするか
二重解放します。C 言語のライブラリで延々と繰り返されてきた事故です。

**欲しかったのは「コピーせず、しかも所有権の移動が型に現れる」渡し方**でした。
それがムーブです。

```cpp
std::unique_ptr<std::vector<int>> make_data();   // 呼び出し側が所有する。型が言っている
```

だから**ムーブは「速くするための最適化」というより、「所有権を型で表すための機能」**です。
速くなるのは結果であって目的ではありません。
このドリルで `std::move` が出てくるのは課題 14 の 1 箇所だけですが、
`std::unique_ptr` と `std::shared_ptr`（6 章）を理解するには
この「所有権が動く」という感覚が土台になります。

### 3 つの渡し方を並べる

```cpp
void copy_it(std::vector<int> v);                  // コピー: 呼び出し側も持ち続ける
void borrow_it(const std::vector<int> & v);        // 借用: 所有権は動かない
void take_it(std::vector<int> && v);               // 移動: 所有権をもらう
```

日本語にするとこうです。

| 書き方 | 意味 | 呼び出し後、元の変数は |
| --- | --- | --- |
| `T v` | **複製をください** | そのまま使える |
| `const T & v` | **見せてください** | そのまま使える |
| `T && v` | **もらいます** | **もう使わない約束** |

**この 3 段は 4 章の続きです。** 4 章で「値か `const &` か」を選びましたが、
実は 3 つ目の選択肢があった、という話です。

### 「もう使わない約束」は約束にすぎない

3 行目をあえて「約束」と書きました。ここは誤解しやすいので先に潰します。

**`T &&` で受け取っただけでは、中身は 1 バイトも動きません。**

```cpp
#include <iostream>
#include <utility>
#include <vector>

void take_it(std::vector<int> && v)
{
  std::cout << "take (size " << v.size() << ")\n";
  // v から何も奪っていない
}

int main()
{
  std::vector<int> v{1, 2, 3};
  take_it(std::move(v));
  std::cout << "after move, size = " << v.size() << "\n";
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/xbfj849P5)

```
take (size 3)
after move, size = 3
```

**`std::move` を書いたのに `v` は空になっていません。**

`&&` は「奪ってよい」という**許可**であって、奪う**動作**ではないからです。
実際に奪うには、受け取った側が中身をムーブしなければなりません。

```cpp
void take_it(std::vector<int> && v)
{
  std::vector<int> mine = std::move(v);    // ここで初めて奪われる
  std::cout << "take (size " << mine.size() << ")\n";
}
```

これで `after move, size = 0` になります。

つまり `std::move` と `&&` が揃っても、**誰かがムーブコンストラクタかムーブ代入を
呼ばなければ何も起きません。** その 3 者の関係が 5.2 節の主題です。

- `std::move(x)` — 「これは奪ってよい」と印を付ける（キャストするだけ）
- `T &&` — 「印の付いたものだけ受け取る」引数の型
- ムーブコンストラクタ / ムーブ代入 — **実際に奪う処理**

## 5.1 左辺値と右辺値

`T &&` の話をする前に、`&&` が受け取る「右辺値」を定義します。

前章の最後に出たエラーを思い出してください。

```cpp
void f(std::string & s);
f("hello");   // error: cannot bind non-const lvalue reference ... to an rvalue
```

「rvalue（右辺値）」という言葉が出てきました。まずこれを片付けます。

### 名前の由来と、実用的な見分け方

もともとは **`=` の左に置けるか（left value）／右にしか置けないか（right value）** という
区別でした。

```cpp
a = 42;         // a は = の左に置ける → 左辺値
42 = a;         // これは書けない       → 42 は右辺値
```

ただこの説明は現代の C++ では正確ではありません（`const int a` は左に置けないが左辺値です）。
**実用的な見分け方は「名前が付いているか」**です。

```cpp
std::string a = "hello";
std::string b = "world";

a                       // 左辺値（名前がある）
"hello"                 // 右辺値（名前がない）
std::string("hi")       // 右辺値（一時オブジェクト）
a + b                   // 右辺値（計算結果の一時オブジェクト）
make_string()           // 右辺値（戻り値の一時オブジェクト）
std::move(a)            // 右辺値（名前はあるが、そう扱えと指示した）
```

もう 1 つの機械的な判定法は **`&` でアドレスが取れるか**です。

```cpp
&a;                     // OK → 左辺値
&std::string("hi");     // エラー → 右辺値
```

```
error: taking address of rvalue
```

### なぜこの区別に意味があるのか

**右辺値は「この式が終わったら誰もアクセスできない」ことが、コンパイラに分かっているから**です。

```cpp
std::string make() { return "長い文字列..."; }

std::string s = make();
```

`make()` の戻り値は一時オブジェクトで、この行を過ぎたら名前が無いのでアクセスする手段がありません。
**誰も見ていないなら、中身をコピーせず、そのまま奪ってしまってよい。**
これがムーブの発想です。

逆に左辺値から奪うのは危険です。

```cpp
std::string a = "hello";
std::string b = a;        // a はこの後も使えるはず。奪ってはいけない
std::cout << a;           // だからここが動く
```

**「奪ってよいか」を型で判定できるようにしたのが右辺値参照 `&&`** です。

### もう少し正確な話（読み飛ばして構いません）

規格では 3 種類に分かれています。ドリルで必要になることはありませんが、
エラーメッセージに `xvalue` などが出てくることがあるので、対応だけ置いておきます。

| 用語 | 何 | 例 |
| --- | --- | --- |
| **lvalue** | 名前があり、まだ使う | `a` |
| **prvalue** | 名前がなく、これから作られる値 | `42`、`make()` の戻り値 |
| **xvalue** | 名前はあるが、もう使わないと宣言されたもの | `std::move(a)` |

「rvalue」は prvalue と xvalue をまとめた呼び名です。
**`&&` が受け取れるのは rvalue（prvalue と xvalue）** と覚えれば足ります。

### 右辺値参照 `&&`

右辺値だけを受け取る参照の書き方があります。

```cpp
void f(std::string & s);        // 左辺値参照 — 左辺値だけ受ける
void f(const std::string & s);  // const 左辺値参照 — 両方受ける
void f(std::string && s);       // 右辺値参照 — 右辺値だけ受ける
```

実際に呼び分けを見ます。

```cpp
#include <iostream>
#include <string>

void take(const std::string & s) { std::cout << "const & : " << s << "\n"; }
void take(std::string && s)      { std::cout << "&&      : " << s << "\n"; }

int main()
{
  std::string a = "named";
  take(a);                    // 左辺値 → const &
  take("literal");            // 右辺値 → &&
  take(std::string("temp"));  // 右辺値 → &&
  take(std::move(a));         // ← これは？
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/qrYMMc9r9)

```
const & : named
&&      : literal
&&      : temp
&&      : named
```

最後の行が肝心です。**`std::move(a)` は `a` を右辺値として扱わせています。**

## 5.2 `std::move` は何もしない

いきなり結論を書きます。

**`std::move(x)` は `x` を右辺値にキャストするだけです。データは 1 バイトも動きません。**

標準ライブラリの実装は実質こうです。

```cpp
template<typename T>
constexpr std::remove_reference_t<T> && move(T && t) noexcept
{
  return static_cast<std::remove_reference_t<T> &&>(t);
}
```

`static_cast` が 1 つあるだけです。実行時のコストはゼロです。

では何のためにあるのか。**オーバーロード解決を変えるため**です。
`std::move` を書くと、コンパイラは `&&` を取るオーバーロード（＝ムーブ版）を選びます。
実際に「盗む」処理をするのはムーブコンストラクタのほうで、`std::move` はその引き金にすぎません。

**名前が悪い**というのはよく言われる話で、`std::rvalue_cast` のような名前だったら
誤解が少なかったはずです。

### ムーブコンストラクタが「盗む」

`std::string` のムーブが何をしているか、自作クラスで再現します。

```cpp
#include <iostream>
#include <utility>

class Buffer
{
public:
  explicit Buffer(std::size_t n) : size_(n), data_(new int[n]())
  {
    std::cout << "  確保 " << n << "\n";
  }

  ~Buffer() { delete[] data_; }

  // コピー: 新しく確保して中身を写す
  Buffer(const Buffer & o) : size_(o.size_), data_(new int[o.size_])
  {
    std::copy(o.data_, o.data_ + o.size_, data_);
    std::cout << "  コピー（確保あり）\n";
  }

  // ムーブ: ポインタを付け替えるだけ
  Buffer(Buffer && o) noexcept : size_(o.size_), data_(o.data_)
  {
    o.data_ = nullptr;      // ← ここが重要
    o.size_ = 0;
    std::cout << "  ムーブ（確保なし）\n";
  }

  std::size_t size() const { return size_; }
  const int * raw() const { return data_; }

private:
  std::size_t size_;
  int * data_;
};

int main()
{
  Buffer a(4);
  std::cout << "a のアドレス: " << static_cast<const void *>(a.raw()) << "\n";

  std::cout << "コピー:\n";
  Buffer b = a;
  std::cout << "b のアドレス: " << static_cast<const void *>(b.raw()) << "\n";

  std::cout << "ムーブ:\n";
  Buffer c = std::move(a);
  std::cout << "c のアドレス: " << static_cast<const void *>(c.raw()) << "\n";
  std::cout << "a の size: " << a.size() << "\n";
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/n5G39vWzP)

出力例（アドレスは実行ごとに変わります）。

```
  確保 4
a のアドレス: 0x5f3e2a2b62b0
コピー:
  コピー（確保あり）
b のアドレス: 0x5f3e2a2b62d0
ムーブ:
  ムーブ（確保なし）
c のアドレス: 0x5f3e2a2b62b0
a の size: 0
```

**`c` のアドレスが、元の `a` のアドレスと同じです。**
コピーでは `b` に別のアドレスが確保されましたが、
ムーブでは同じメモリを `c` が引き継いでいます。「所有権が移った」とはこのことです。

そして `a` の `size` は 0 になりました。**ムーブ元は空になります。**

### ムーブ元はどうなるのか

規格が保証しているのは「**有効だが未規定の状態**」（valid but unspecified）です。

- **してよいこと**: 破棄する、新しい値を代入する
- **してはいけないこと**: 中身を読んで意味があると期待する

```cpp
std::string a = "hello";
std::string b = std::move(a);

std::cout << a;        // 何が出るか未規定（実際は多くの実装で空文字列）
a = "reset";           // これは OK
std::cout << a;        // "reset"
```

**「ムーブしたら、もう読まない」** を習慣にしてください。
`std::string` は実際には空になりますが、それは実装の都合であって保証ではありません。

`std::unique_ptr` は例外で、**ムーブ後は必ず `nullptr` になる**ことが規格で保証されています。
これは 6 章で使います。

### `noexcept` を付ける理由

ムーブコンストラクタに `noexcept` を付けました。これは重要です。

`std::vector` は要素数が増えると再確保して全要素を移します。
このとき **ムーブが例外を投げないと保証されていれば**ムーブを使い、
保証されていなければ安全のためコピーを使います。

つまり `noexcept` を書き忘れると、**`std::vector` に入れたときだけ静かにコピーになります。**
ムーブコンストラクタとムーブ代入には `noexcept` を付けてください。

## 5.3 `std::move` を書くべき場所と書いてはいけない場所

### 書くべき場所 ①: 所有権を渡すとき

課題 14 のこれです。

```cpp
// solutions/14_zero_copy/src/zero_copy_nodes.cpp
void ZeroCopyTalker::publish_once()
{
  auto msg = std::make_unique<std_msgs::msg::String>();
  // ... msg を組み立てる ...
  publisher_->publish(std::move(msg));
}
```

`publish` には 2 つのオーバーロードがあります。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/publisher.hpp（要約）
void publish(std::unique_ptr<T, ...> msg)   // 所有権を受け取る
{
  if (!intra_process_is_enabled_) { this->do_inter_process_publish(*msg); return; }
  this->do_intra_process_publish(std::move(msg));    // コピーせずそのまま渡す
}

void publish(const T & msg)                  // 値を受け取る
{
  if (!intra_process_is_enabled_) { this->do_inter_process_publish(msg); return; }
  // Otherwise we have to allocate memory in a unique_ptr and pass it along.
  auto unique_msg = this->duplicate_ros_message_as_unique_ptr(msg);
  this->publish(std::move(unique_msg));
}
```

コメントに `we have to allocate memory` と書いてあります。
**値渡し版は必ず 1 回複製します。** 呼び出し側の `msg` がまだ生きているので、盗めないからです。

`std::move` を書き忘れると `unique_ptr` はコピーできないのでコンパイルエラーになり、
すぐ気付けます。ここは安全です。

課題 14 のテストは、**送信側と受信側でメッセージのアドレスが一致するか**を検査します。
`std::move` があってコピーが起きていなければ一致し、コピーが挟まれば別のアドレスになります。

### 書くべき場所 ②: コンストラクタで引数を受け取るとき

```cpp
class Node
{
public:
  explicit Node(std::string name) : name_(std::move(name)) {}
private:
  std::string name_;
};
```

「値で受けて `std::move` で入れる」という形です。
呼び出し側が右辺値を渡せばムーブ 1 回、左辺値を渡せばコピー 1 回で済みます。

`const std::string & name` にして `name_(name)` とすると、右辺値を渡した場合でも
必ずコピー 1 回になります。**この形のほうが 1 回分得**です。

### 書いてはいけない場所 ①: `return` するとき

```cpp
std::string make_bad()
{
  std::string s = "hello";
  return std::move(s);       // ← 書かないでください
}

std::string make_good()
{
  std::string s = "hello";
  return s;                  // これが正しい
}
```

**`return std::move(s)` は遅くなります。**
`return s;` と書けば、コンパイラは **NRVO（named return value optimization）** で
「戻り先のメモリに直接構築する」ことができ、ムーブすら起きません。
`std::move` を書くと右辺値参照になり、この最適化が効かなくなってムーブが 1 回発生します。

g++ は警告してくれます。

```bash
g++ -std=c++17 -Wall -Wextra -Wpessimizing-move ...
```

```
warning: moving a local object in a return statement prevents copy elision [-Wpessimizing-move]
```

**`-Wpessimizing-move` は `-Wall` に含まれています。** この警告が出たら `std::move` を消してください。

### 書いてはいけない場所 ②: そのあとも使う変数

```cpp
auto msg = std::make_unique<std_msgs::msg::String>();
publisher_->publish(std::move(msg));
std::cout << msg->data;              // msg は nullptr。クラッシュ
```

**`std::move` した変数は、その行以降で読まない。** 5.2 節のとおりです。

ループの中で同じ変数をムーブするのは典型的な事故です。

```cpp
auto msg = std::make_unique<std_msgs::msg::String>();
for (int i = 0; i < 10; ++i) {
  publisher_->publish(std::move(msg));   // 2 周目で nullptr
}
```

**毎周作り直す**のが正解です。

```cpp
for (int i = 0; i < 10; ++i) {
  auto msg = std::make_unique<std_msgs::msg::String>();
  publisher_->publish(std::move(msg));
}
```

### 書く必要がない場所: 一時オブジェクト

```cpp
v.push_back(std::move(std::string("hi")));   // 無意味
v.push_back(std::string("hi"));              // すでに右辺値
```

## 5.4 コピー省略 — そもそもコピーもムーブも起きない場合

C++17 では、次のケースで**コピーもムーブも起きないことが規格で保証**されています。

```cpp
std::string make() { return std::string("hello"); }   // 一時オブジェクトを返す
std::string s = make();                                // 構築は 1 回だけ
```

確かめられます。

```cpp
#include <iostream>

struct Noisy
{
  Noisy() { std::cout << "生成\n"; }
  Noisy(const Noisy &) { std::cout << "コピー\n"; }
  Noisy(Noisy &&) noexcept { std::cout << "ムーブ\n"; }
};

Noisy make() { return Noisy(); }

int main()
{
  Noisy a = make();
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/PrW8qnW1e)

```
生成
```

**「生成」だけです。** コピーもムーブも 1 回も起きていません。
`Noisy()` が最初から `a` の場所に構築されています。

これを知っていると、「戻り値のコピーが心配だから参照を返そう」という発想が
不要だと分かります。**値を返してよい**のです。4 章のダングリング参照を避けられます。

（`-fno-elide-constructors` を付けると省略を止められるので、
違いを見たいときはそれで比較してください。ただし C++17 の保証されるケースは止まりません。）

## 5.5 Rule of Zero / Rule of Five

2 章で「コピーとムーブは自動で生えてくる」と書きました。
自分で書くかどうかの判断基準を整理します。

**Rule of Zero: 何も書かないのが最善。**
メンバを全部 RAII 型（`std::string`、`std::vector`、`std::unique_ptr`）にすれば、
コピーもムーブもデストラクタも正しく自動生成されます。

上の `Buffer` は生ポインタ `int * data_` を持っていたので自分で書く必要がありました。
`std::vector<int>` にすれば全部要らなくなります。

```cpp
class Buffer
{
public:
  explicit Buffer(std::size_t n) : data_(n) {}
  // コピー、ムーブ、デストラクタ、全部書かなくてよい
private:
  std::vector<int> data_;
};
```

**Rule of Five: 1 つ書いたら 5 つ書く。**
どうしても手で管理する必要がある場合、次の 5 つはセットです。

1. デストラクタ
2. コピーコンストラクタ
3. コピー代入演算子
4. ムーブコンストラクタ
5. ムーブ代入演算子

**1 つでも書くと、他のいくつかが自動生成されなくなります。**
特に危ないのがこれです。

| 自分で書いたもの | 生成されなくなるもの |
| --- | --- |
| デストラクタ | **ムーブコンストラクタ、ムーブ代入** |
| コピーコンストラクタ | **ムーブコンストラクタ、ムーブ代入** |
| ムーブコンストラクタ | **コピーコンストラクタ、コピー代入**（`delete` される） |

「デストラクタだけ書いたら、ムーブが消えて全部コピーになっていた」が典型的な事故です。
`-Wall` でも検出できません。

**Rule of Zero を目指してください。** メンバを RAII 型にすれば 5 つ全部書かずに済みます。
`rclcpp::Node` のメンバが全部 `SharedPtr` なのも、この方針に沿っています。

## 手元で試す

**アドレスを見て、コピーとムーブを区別します。** これが課題 14 のテストと同じ考え方です。

```cpp
// move.cpp
#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

void show(const char * tag, const std::string & s)
{
  std::cout << tag << " len=" << s.size()
            << " buf=" << static_cast<const void *>(s.data()) << "\n";
}

int main()
{
  // 十分長い文字列にする（短いとヒープを使わず、アドレスが動いてしまう）
  std::string a(64, 'x');
  show("a       ", a);

  std::string b = a;                 // コピー
  show("b (copy)", b);

  std::string c = std::move(a);       // ムーブ
  show("c (move)", c);
  show("a (後)  ", a);

  std::cout << "\n-- unique_ptr\n";
  auto p = std::make_unique<std::string>("owned");
  std::cout << "p.get() = " << static_cast<const void *>(p.get()) << "\n";
  auto q = std::move(p);
  std::cout << "q.get() = " << static_cast<const void *>(q.get()) << "\n";
  std::cout << "p.get() = " << static_cast<const void *>(p.get()) << "\n";

  std::cout << "\n-- ムーブ後に使う\n";
  std::cout << "q は " << *q << "\n";
  // std::cout << *p << "\n";   // ← コメントを外すとどうなるか
  return 0;
}
```

**予想を 3 つ立ててください。**

1. `b (copy)` の `buf` は `a` と同じか、違うか
2. `c (move)` の `buf` は `a` と同じか、違うか
3. `p.get()` はムーブ後に何になるか

```bash
g++ -std=c++17 -Wall -Wextra move.cpp -o move && ./move
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/qeK4v4ovr)

**`std::string a(64, 'x')` を `std::string a = "hi"` に変えて、もう一度実行してください。**
短い文字列では結果が変わります。**short string optimization (SSO)** といって、
15 文字程度まではヒープを使わずオブジェクト内部に直接持つため、
ムーブでもアドレスが変わります。「ムーブならアドレスが保たれる」は
**ヒープを持つ場合の話**だと確認しておいてください。

次に `-Wpessimizing-move` を体験します。

```cpp
std::string make_bad()
{
  std::string s(64, 'y');
  return std::move(s);
}
```

```bash
g++ -std=c++17 -Wall -Wextra move.cpp -o move
```

警告文を読んでから `std::move` を消してください。

最後に、コメントアウトしてある `std::cout << *p` を有効にして実行してください。
**`p` は `nullptr` なので、ここで落ちます。**
どんなメッセージでどう落ちるかを一度見ておくと、実機で同じ症状に遭ったとき早く気付けます。

## つまずきポイント

**`error: use of deleted function ‘std::unique_ptr<T>::unique_ptr(const std::unique_ptr<T>&)’`**
`unique_ptr` をコピーしようとしています。`std::move` を付けてください。
関数に渡すとき、`return` するとき、`vector` に入れるときによく出ます。

**`std::move` したのにコピーが起きている**
3 つの可能性があります。

1. ムーブコンストラクタが自動生成されていない（Rule of Five の表を見てください）
2. `noexcept` が付いておらず、`std::vector` の再確保がコピーを選んだ
3. `const` なオブジェクトをムーブしようとした
   → `std::move(const T &)` は `const T &&` になり、ムーブコンストラクタは
   `T &&` を取るので選ばれません。静かにコピーになります

**`error: cannot bind rvalue reference of type ‘T&&’ to lvalue of type ‘T’**
`&&` を取る関数に名前付きの変数を渡しています。`std::move` を付けてください。

**ムーブしたはずの変数を使ってしまった**
コンパイラは教えてくれません（`clang-tidy` の `bugprone-use-after-move` なら検出できます）。
**`std::move` を書いた行から下では、その変数の名前を書かない**というルールで自衛してください。

**関数の引数に `&&` を書いたら左辺値を渡せなくなった**
`T &&` は右辺値専用です。両方受けたいなら 2 つオーバーロードするか、
`const T &` にします。テンプレート引数の `T &&` は「転送参照」といって別の意味になりますが、
ドリルでは出てきません。

## ドリルのどこで出るか

| 課題 | この章の何が出るか |
| --- | --- |
| 14 | `publisher_->publish(std::move(msg))` — この章の主題。テストはアドレス比較で検出する |
| 14 | `std::make_unique<std_msgs::msg::String>()` — 所有権が 1 人の状態を作る |
| 01, 15 | `publisher_->publish(message)` — 値渡し版。**コピーが 1 回起きる** |
| 全課題 | メッセージ型のメンバは `std::string` / `std::vector` なので Rule of Zero が効いている |

課題 01 と課題 14 を並べると、この章の要点がそのまま出ます。

```cpp
// 課題 01: 値を渡す（コピー 1 回）
auto message = std_msgs::msg::String();
message.data = "Hello, world! " + std::to_string(count_++);
publisher_->publish(message);

// 課題 14: 所有権を渡す（コピー 0 回）
auto msg = std::make_unique<std_msgs::msg::String>();
msg->data = ss.str();
publisher_->publish(std::move(msg));
```

**課題 01 の書き方が間違っているわけではありません。**
`std_msgs::msg::String` は小さいので、コピー 1 回は問題になりません。
公式チュートリアルの字面に合わせることのほうが価値があります。

差が出るのは `sensor_msgs::msg::PointCloud2` のような数 MB のメッセージです。
**「大きいメッセージを高頻度で流すときだけ `std::move` 版に切り替える」**
という判断ができれば十分です。
ゼロコピーが成立する条件は 4 つあり（同一プロセス、`use_intra_process_comms(true)`、
QoS の History、`std::move`）、`std::move` はそのうちの 1 つにすぎません。
残り 3 つは [rclcpp の設計思想](../rclcpp-の設計思想.md)の 6 章にあります。
