# 2. クラスと初期化

> **この章のねらい**: ドリルの全 15 課題が、`MinimalPublisher::MinimalPublisher()` のような
> コンストラクタの中身を書く課題です。そして全課題に `: Node("minimal_publisher"), count_(0)` という
> **コロンで始まる見慣れない行**があります。
> これはメンバ初期化子リストといって、C++ のコンストラクタの本体です。
> この章では初期化のしかたと、**デストラクタが自動で呼ばれること（RAII）** を扱います。
> RAII は次章以降の所有権の話の土台になります。

> **前提**: [入門編 6章 `const`](../cpp-basics/06_const.md)と
> [2章 スコープと寿命](../cpp-basics/02_スコープと寿命.md)を読んでいる前提です。
> `const` メンバが**初期化子リストでしか初期化できない**理由と、
> オブジェクトがいつ構築されいつ破棄されるかが、この章の土台になります。

## 2.1 いちばん短いクラス

```cpp
#include <iostream>

class Counter
{
public:
  Counter()
  {
    std::cout << "作られた\n";
    count_ = 0;
  }

  void tick() { ++count_; }
  int value() const { return count_; }

private:
  int count_;
};

int main()
{
  Counter c;        // ここで Counter() が走る
  c.tick();
  c.tick();
  std::cout << c.value() << "\n";
  return 0;
}
```

```
作られた
2
```

`Counter c;` に `new` が無いことに注目してください。
Java や C# と違い、**C++ のクラスは値として直接置ける**のがふつうです。
`c` はスタック上のただの変数で、`main` を抜ければ自動で消えます。

`public:` と `private:` はそこから下のメンバの公開範囲を変えるラベルです。
**`class` の既定は `private`** なので、`public:` を書かないと外から何も触れません。
`struct` は既定が `public` で、それ以外は `class` と全く同じです。

`value() const` の末尾の `const` は「このメンバ関数はメンバ変数を書き換えない」という宣言です。
3 章で詳しく扱います。

## 2.2 メンバ初期化子リスト — コロンの正体

上の `Counter` は本体の中で `count_ = 0;` としていました。これは**代入**です。
C++ では**初期化**と代入を区別します。

```cpp
Counter()
: count_(0)     // ← メンバ初期化子リスト（初期化）
{
  // ここに来た時点で count_ はもう 0
}
```

`{` の前、`:` から始まる部分がメンバ初期化子リストです。
ここに書いたメンバは、**コンストラクタ本体が始まる前に**初期化されます。

ドリルの課題 01 がこの形です。

```cpp
// solutions/01_publisher/src/minimal_publisher.cpp
MinimalPublisher::MinimalPublisher()
: Node("minimal_publisher"), count_(0)
{
  publisher_ = this->create_publisher<std_msgs::msg::String>("topic", 10);
  timer_ = this->create_wall_timer(
    500ms, std::bind(&MinimalPublisher::timer_callback, this));
}
```

`count_(0)` はメンバ変数 `count_` の初期化です。
`Node("minimal_publisher")` は**基底クラスのコンストラクタ呼び出し**で、これは次章の話です。

### なぜ代入ではなく初期化を使うのか

3 つ理由があります。ドリルで効くのは 1 番と 3 番です。

**① 代入できないメンバがある**

`const` メンバと参照メンバは、初期化はできても代入はできません。

```cpp
class Config
{
public:
  Config(int limit)
  {
    limit_ = limit;    // ← エラー
  }
private:
  const int limit_;
};
```

```
error: assignment of read-only member ‘Config::limit_’
```

初期化子リストなら通ります。

```cpp
Config(int limit) : limit_(limit) {}
```

**② 二度手間になる**

`std::string` のようなクラス型のメンバは、初期化子リストに書かなくても
**既定コンストラクタが先に走ります**。本体で代入すると「空文字列を作ってから代入」の 2 手になります。
初期化子リストに書けば 1 手です。

**③ 初期化されていないメンバを読む事故を防げる**

これがいちばん怖い理由です。**`int` のような組み込み型のメンバは、
書かなければ初期化されません。** ゼロにもなりません。

```cpp
#include <iostream>

class Bad
{
public:
  Bad() {}          // count_ を初期化していない
  int value() const { return count_; }
private:
  int count_;
};

int main()
{
  Bad b;
  std::cout << b.value() << "\n";   // 何が出るか分からない
}
```

これは未定義動作です。実行するたび違う値が出ることも、たまたま 0 が出ることもあります。
**「手元では動いた」がまったく保証にならない**種類のバグです。

`-Wall` を付けると g++ が警告してくれることもありますが、
コンストラクタが別ファイルにあると検出できません。
`Wall` に頼らず、**メンバは全部初期化子リストに書く**のを習慣にしてください。

### 書く順番はメンバの宣言順に合わせる

初期化子リストに書いた順番は無視されます。
**実際の初期化順は、クラス定義でメンバを宣言した順**です。

```cpp
class Ordered
{
public:
  Ordered()
  : b_(1), a_(b_ + 1)    // 書いた順は b_ → a_
  {
  }
  int a_;                 // 宣言順は a_ → b_
  int b_;
};
```

`a_(b_ + 1)` は `b_` を読みますが、**宣言順では `a_` が先に初期化される**ので、
`b_` はまだ初期化されていません。未定義動作です。

g++ は `-Wall` で教えてくれます。

```
warning: ‘Ordered::b_’ will be initialized after [-Wreorder]
warning:   ‘int Ordered::a_’ [-Wreorder]
```

**`-Wreorder` の警告が出たら順番を直してください。**
ドリルの全課題で `-Wall -Wextra -Wpedantic` を有効にしているのは、この類を拾うためです。

### メンバ変数の既定値（C++11 以降）

宣言のところに直接書く手もあります。

```cpp
class Counter
{
private:
  int count_ = 0;                    // 既定値
  std::string name_ = "unnamed";
};
```

初期化子リストで指定すればそちらが勝ちます。指定しなければこの値が使われます。
**「初期化を忘れる」事故が構造的に起きなくなる**ので、
コンストラクタが複数あるクラスでは特に有効です。

ドリルのコードは公式チュートリアルの字面に合わせているため初期化子リスト形式ですが、
自分のコードではこちらを使ってかまいません。

## 2.3 `this` と `this->`

メンバ関数の中では `this` が使えます。**自分自身へのポインタ**です。

ドリルのコードは `this->create_publisher(...)` と、いちいち `this->` を付けています。
実は**省略しても同じ**です。

```cpp
publisher_ = create_publisher<std_msgs::msg::String>("topic", 10);   // これでも動く
publisher_ = this->create_publisher<std_msgs::msg::String>("topic", 10);  // 公式はこちら
```

grep すると、ドリルには `this->` が 65 箇所あります。全部が省略可能です。
公式チュートリアルがこう書いているので合わせているだけです。

省略できないのは次の 2 つの場合です。

**① 引数とメンバ名が衝突しているとき**

```cpp
void set_count(int count_)
{
  this->count_ = count_;     // 左が メンバ、右が 引数
}
```

ただし ROS 2 の命名規約ではメンバに `_` の接尾辞を付けるので、この衝突はまず起きません。
**`count_` という接尾辞そのものが、`this->` を要らなくするための工夫**です。

**② テンプレートの基底クラスのメンバを参照するとき**

これは 9 章のテンプレートの話ですが、rclcpp では出てきません。

### `this` はポインタなので `->` を使う

`this` は参照ではなくポインタです。だから `this.foo` ではなく `this->foo` です。
`(*this).foo` とも書けますが、誰も書きません。

`std::shared_ptr` も同じで、`publisher_->publish(message)` の `->` は
「ポインタの指す先のメンバ」という同じ意味です（6 章）。

## 2.4 RAII — デストラクタが自動で呼ばれる

C++ には Python の `with` や Java の `try-with-resources` に相当する構文がありません。
**必要ないからです。** スコープを抜けるとデストラクタが自動で呼ばれます。

```cpp
#include <iostream>

class Noisy
{
public:
  explicit Noisy(const char * name) : name_(name)
  {
    std::cout << name_ << " 生成\n";
  }

  ~Noisy()
  {
    std::cout << name_ << " 破棄\n";
  }

private:
  const char * name_;
};

int main()
{
  std::cout << "-- main 開始\n";
  Noisy a("a");
  {
    Noisy b("b");
    std::cout << "-- 内側スコープの終わり\n";
  }
  std::cout << "-- main 終わり\n";
  return 0;
}
```

```
-- main 開始
a 生成
b 生成
-- 内側スコープの終わり
b 破棄
-- main 終わり
a 破棄
```

3 点確認してください。

1. `b` は内側の `}` で破棄され、`a` は `main` の `}` まで生きている
2. `delete` を 1 つも書いていないのにデストラクタが呼ばれている
3. **破棄は生成の逆順**（`a` → `b` の順に生成、`b` → `a` の順に破棄）

この「スコープを抜けたら確実に片付く」性質を使って資源を管理するのが
**RAII（Resource Acquisition Is Initialization）** です。
「コンストラクタで確保し、デストラクタで解放する」という型に資源を包んでしまえば、
呼び出し側は解放を書かなくてよくなります。

RAII が効くのは、**例外が飛んでも、`return` がどこにあっても、デストラクタは必ず呼ばれる**からです。
`goto` で飛び出しても呼ばれます。

```cpp
void f()
{
  Noisy a("a");
  if (something_wrong) {
    return;              // ここで抜けても a は破棄される
  }
  may_throw();           // 例外が飛んでも a は破棄される
}
```

C 言語で `goto cleanup;` を書いていたのは、これが無かったからです。

### RAII は ROS 2 のあちこちに出てくる

| RAII で包んでいるもの | 何を確保・解放しているか |
| --- | --- |
| `std::shared_ptr` / `std::unique_ptr` | ヒープメモリ（6 章） |
| `std::lock_guard` | mutex のロック（12 章） |
| `rclcpp::Node` | rcl のノードハンドル、DDS の participant |
| `rclcpp::Publisher` | DDS の DataWriter |
| `std::ofstream` | ファイルディスクリプタ |

`rclcpp::init()` / `rclcpp::shutdown()` を `main` で対にして書いているのは、
**ここだけは RAII になっていない**部分です（`rclcpp::Context` は RAII ですが、
グローバルな init/shutdown は手続き的な API として残っています）。

```cpp
// exercises/01_publisher/src/talker_main.cpp
int main(int argc, char * argv[])
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<MinimalPublisher>());
  rclcpp::shutdown();
  return 0;
}
```

### デストラクタで例外を投げない

`~Noisy()` の中から例外を投げてはいけません。
デストラクタは「例外で巻き戻している最中」にも呼ばれるので、
そこでさらに例外が飛ぶと `std::terminate` でプロセスが落ちます。

[ROS 2 のコーディング規約](../ros2-コーディング規約.md)にも
「例外はデストラクタでは避ける」と明記されています。

## 2.5 `explicit` — 意図しない変換を止める

`explicit` はドリルに 3 箇所あります。全部この形です。

```cpp
// exercises/14_zero_copy/include/drill/zero_copy_nodes.hpp
explicit ZeroCopyTalker(const rclcpp::NodeOptions & options);
```

**引数 1 つのコンストラクタは、既定では暗黙の型変換として使われます。**
これが厄介な事故を生みます。

```cpp
#include <iostream>

class Meters
{
public:
  Meters(double v) : v_(v) {}     // explicit なし
  double value() const { return v_; }
private:
  double v_;
};

void move_robot(Meters distance)
{
  std::cout << distance.value() << " m 進む\n";
}

int main()
{
  move_robot(Meters(1.5));   // 意図した呼び方
  move_robot(1.5);           // これも通ってしまう
  move_robot(true);          // これも通る（bool → double → Meters）
  return 0;
}
```

```
1.5 m 進む
1.5 m 進む
1 m 進む
```

`move_robot(true)` が「1 メートル進む」になりました。
コンパイラは `bool` → `double` → `Meters` と 2 段変換して黙って通します。

`explicit` を付けると止まります。

```cpp
explicit Meters(double v) : v_(v) {}
```

```
error: could not convert ‘1.5e+0’ from ‘double’ to ‘Meters’
```

`move_robot(Meters(1.5))` は通り、`move_robot(1.5)` だけが落ちます。

**引数 1 つのコンストラクタには原則 `explicit` を付ける**、と覚えてください。
例外は「本当に同じものの別表現」の場合（`std::string` が `const char *` を受けるなど）だけです。

`ZeroCopyTalker(const rclcpp::NodeOptions &)` に `explicit` が付いているのは、
`NodeOptions` がうっかりノードに変換されると意味不明なので当然の措置です。

## 2.6 コピーとムーブは自動で生えてくる

書かなくても、コンパイラが次の 6 つを自動生成します。

| 何が生えるか | いつ呼ばれるか |
| --- | --- |
| 既定コンストラクタ | `Foo f;` |
| デストラクタ | スコープを抜けたとき |
| コピーコンストラクタ | `Foo b = a;` |
| コピー代入演算子 | `b = a;` |
| ムーブコンストラクタ | `Foo b = std::move(a);` |
| ムーブ代入演算子 | `b = std::move(a);` |

自動生成されるものは「全メンバに対して同じ操作をする」だけです。
メンバが `int` と `std::string` なら、`int` をコピーし、`std::string` をコピーします。

**多くの場合これで正しく、自分で書く必要はありません。**
ムーブとコピーの区別は 5 章で扱います。

止めたいときは `= delete` を書きます。

```cpp
class NonCopyable
{
public:
  NonCopyable() = default;
  NonCopyable(const NonCopyable &) = delete;             // コピー禁止
  NonCopyable & operator=(const NonCopyable &) = delete; // コピー代入禁止
};
```

`std::unique_ptr` がまさにこの形です（6 章）。
「所有者は 1 人」を型で強制するために、コピーを消してムーブだけ残しています。

## 手元で試す

**初期化されていないメンバと、初期化順の警告を自分で見ます。**

```cpp
// init.cpp
#include <iostream>
#include <string>

class Sloppy
{
public:
  Sloppy()
  : b_(1), a_(b_ + 1)      // 罠 1: 宣言順と逆
  {
  }
  int a_;
  int b_;
  int c_;                  // 罠 2: どこでも初期化していない
  std::string s_;          // クラス型なので既定コンストラクタが走る
};

int main()
{
  Sloppy s;
  std::cout << "a_=" << s.a_ << " b_=" << s.b_
            << " c_=" << s.c_ << " s_=[" << s.s_ << "]\n";
  return 0;
}
```

**予想: `a_` はいくつになるか。`c_` はいくつになるか。`s_` は何が入っているか。**

```bash
g++ -std=c++17 -Wall -Wextra init.cpp -o init && ./init
```

警告を読んでから実行してください。
数回実行して `c_` の値が変わるか（変わらないか）も見てみてください。
**変わらなくても未定義動作であることは変わりません。**
「たまたま 0 だった」を「0 になる」と覚えてしまうのがいちばん危険です。

次に、`Sloppy` を直してください。

- 初期化子リストを宣言順（`a_`, `b_`, `c_`）に並べ替える
- `a_(1), b_(2), c_(3)` のように全部初期化する

警告が消え、出力が安定することを確認します。

続けて RAII を試します。上の `Noisy` クラスの `main` を次に差し替えて、
**破棄の順番と、`return` を飛び越えても呼ばれること**を確認してください。

```cpp
int main()
{
  Noisy outer("outer");
  for (int i = 0; i < 2; ++i) {
    Noisy loop("loop");
    if (i == 1) {
      std::cout << "-- return する\n";
      return 0;              // outer と loop はどうなるか
    }
  }
  return 0;
}
```

**予想: `loop 破棄` は何回出るか。`return` のあとに `outer 破棄` は出るか。**

## つまずきポイント

**`error: no matching function for call to ‘Foo::Foo()’`**
既定コンストラクタが無いクラスを `Foo f;` と書いています。
引数付きのコンストラクタを 1 つでも自分で書くと、**既定コンストラクタは自動生成されません**。
`Foo() = default;` を足すか、引数を渡してください。

**`error: ‘class Foo’ has no member named ‘bar’` なのにメンバはある**
`private` です。`class` の既定は `private` なので、`public:` を書き忘れていないか見てください。

**メンバ関数の定義で `Foo::` を忘れる**

```cpp
// minimal_publisher.cpp
void timer_callback()      // Foo:: を忘れた
{
}
```

これはエラーになりません。**まったく別のグローバル関数を定義した**ことになるので、
コンパイルは通り、`undefined reference to MinimalPublisher::timer_callback()` で
リンクが落ちます（1 章）。
「実装したのに undefined reference」はこのパターンを疑ってください。

**`~Foo()` を書いたらムーブが消えた**
デストラクタを自分で書くと、**ムーブコンストラクタとムーブ代入は自動生成されなくなります**。
コピーは生成されるので、気付かないうちに全部コピーになっていることがあります。
「Rule of Zero」といって、**デストラクタを書かなくて済む設計（メンバを全部 RAII 型にする）が最善**です。

**構造体を `{}` で初期化したときの罠**

```cpp
std::vector<int> a(3, 0);   // 要素 3 個、全部 0
std::vector<int> b{3, 0};   // 要素 2 個、3 と 0
```

`()` と `{}` は同じではありません。`std::vector` では特にこの差が出ます。
`{}` は初期化子リストを優先して解釈します。

## ドリルのどこで出るか

| 課題 | この章の何が出るか |
| --- | --- |
| 01 | `: Node("minimal_publisher"), count_(0)` — 初期化子リスト。`count_` の初期化を忘れるとログの番号が変な値から始まる |
| 04, 05 | コンストラクタでサービスを作り、メンバに保持する |
| 06 | `declare_parameter` をコンストラクタで呼ぶ。宣言前に `get_parameter` すると例外（13 章） |
| 11 | `limit_velocity` は**クラスですらない自由関数**。テストしやすさのために意図的にそうしている |
| 14, 15 | `explicit ZeroCopyTalker(const rclcpp::NodeOptions & options)` — `explicit` の実例 |
| 全課題 | `this->` が 65 箇所。全部省略可能 |

課題 11 の設計判断はこの章と関係が深いので触れておきます。
`limit_velocity` はクラスのメンバではなく、**引数だけで結果が決まる自由関数**です。

```cpp
// exercises/11_node_test/include/drill/velocity_limiter.hpp
double limit_velocity(double target, double previous, double max_speed, double max_delta);
```

ノードのメンバ関数にしてしまうと、テストするには
「ノードを作る → パラメータを宣言する → Executor に載せる → spin する」
が必要になります。自由関数なら 1 行で呼べます。

**テストしにくいと感じたら、まず「状態に触らない部分」を自由関数に切り出す。**
これはこの章の初期化の話とは逆方向ですが、同じくらい実務で効く判断です。
