# 9. テンプレートの読み方

> **この章のねらい**: ドリルの `exercises/` と `solutions/` を grep すると、
> **自分で `template` を書いている箇所は 0 件**です。
> それでも `create_publisher<std_msgs::msg::String>` のような `<>` は毎課題に出てきます。
> **この章は「テンプレートを書けるようになる」章ではなく「読めるようになる」章です。**
> 目標は 3 つだけ。`<>` が何を決めているか読み下せること、
> `::SharedPtr` のような型メンバの意味が分かること、そして
> **テンプレートのエラーメッセージ 100 行から本当の原因 1 行を見つけられること**です。

## 9.1 テンプレートは「型を引数に取る関数」

まず自分で 1 つだけ書いてみます。読むための下地としてこれで十分です。

```cpp
#include <iostream>
#include <string>

template<typename T>
T larger(T a, T b)
{
  return (a > b) ? a : b;
}

int main()
{
  std::cout << larger(3, 7) << "\n";              // int 版
  std::cout << larger(1.5, 0.5) << "\n";          // double 版
  std::cout << larger<std::string>("a", "b") << "\n";  // 明示指定
  return 0;
}
```

```
7
1.5
b
```

**`larger` は 1 つの関数ではありません。3 つの別々の関数が生成されています。**
`larger<int>`、`larger<double>`、`larger<std::string>` です。

これを **インスタンス化（instantiation）** といいます。
コンパイル時にコードが複製され、`T` が具体的な型に置き換わります。

だから

- **実行時のコストはゼロ** です（`virtual` と違い、間接呼び出しになりません）
- **コンパイル時間とバイナリサイズは増えます**（使った型の分だけコードが増える）
- **エラーはインスタンス化のときに出ます**（使わなければエラーにならない）

最後の性質が、あの読みにくいエラーメッセージの原因です。

### 型は推論されることも、明示することもある

```cpp
larger(3, 7);                  // 引数から T = int と推論
larger<std::string>("a", "b"); // T を明示（"a" は const char * なので推論だと困る）
```

**戻り値の型からは推論できません。** 引数に現れない型は明示する必要があります。

これが rclcpp で `<>` を書く理由です。

```cpp
this->create_publisher<std_msgs::msg::String>("topic", 10);
```

引数は `"topic"` と `10` だけで、**メッセージの型はどこにも現れません。**
だから明示するしかありません。

一方 `publish` は引数からわかるので `<>` が要りません。

```cpp
publisher_->publish(message);   // message の型から決まる
```

## 9.2 rclcpp の `<>` を読み下す

ドリルで出てくる形を全部並べます。

```cpp
this->create_publisher<std_msgs::msg::String>("topic", 10);
this->create_subscription<std_msgs::msg::String>("topic", 10, callback);
this->create_service<example_interfaces::srv::AddTwoInts>("add_two_ints", callback);
this->create_client<example_interfaces::srv::AddTwoInts>("add_two_ints");
rclcpp_action::create_server<action_tutorials_interfaces::action::Fibonacci>(...);
std::make_shared<MinimalPublisher>();
std::make_unique<std_msgs::msg::String>();
```

**規則は 1 つです。`<>` の中は「何を扱うか」。**

| 関数 | `<>` に入るもの |
| --- | --- |
| `create_publisher<T>` | 流すメッセージの型 |
| `create_subscription<T>` | 受けるメッセージの型 |
| `create_service<T>` / `create_client<T>` | サービスの型（`.srv`） |
| `create_server<T>`（アクション） | アクションの型（`.action`） |
| `make_shared<T>` / `make_unique<T>` | **作るオブジェクトの型** |

最後の 2 つは他と意味が違うので注意してください。
`make_shared<MinimalPublisher>()` の `<>` は「扱う型」ではなく「作る型」です。

### 戻り値の型を読む

`create_publisher<std_msgs::msg::String>` の戻り値はこうです。

```cpp
std::shared_ptr<rclcpp::Publisher<std_msgs::msg::String>>
```

**`<>` が入れ子になっています。** 内側から読みます。

1. `rclcpp::Publisher<std_msgs::msg::String>` — String を流す Publisher
2. `std::shared_ptr<それ>` — その shared_ptr

メンバに持つときは 6 章の型エイリアスで書きます。

```cpp
rclcpp::Publisher<std_msgs::msg::String>::SharedPtr publisher_;
```

**`::SharedPtr` は「そのクラスの中で定義された型の別名」です。**
関数ではありません。`Publisher<T>` の中に

```cpp
using SharedPtr = std::shared_ptr<Publisher<T>>;
```

があるので、`Publisher<T>::SharedPtr` と書けます。
[コーディング規約](../ros2-コーディング規約.md)に「テンプレートの入れ子は `set<list<string>>` と書く」
（`> >` の間に空白を入れない）とあるのは、この入れ子が日常的に出るからです。

## 9.3 `typename` と `::` — 型メンバの読み方

テンプレートを読むときにいちばん混乱するのがこれです。

`Foo::Bar` は 3 つのどれかです。

```cpp
Foo::Bar        // ① 静的メンバ変数
Foo::Bar()      // ② 静的メンバ関数
Foo::Bar        // ③ 型の別名（using / typedef / ネストしたクラス）
```

**書き方が同じなので、文脈でしか区別できません。**
人間は「大文字で始まっていて変数のように使われていないから型だろう」と判断します。

コンパイラも、テンプレートの中では判断できません。だから `typename` を付けます。

```cpp
template<typename T>
void f()
{
  typename T::SharedPtr p;    // 「T::SharedPtr は型だ」と教える
}
```

**この `typename` はテンプレートの中だけで必要です。**
具体的な型が確定していれば要りません。

```cpp
rclcpp::Publisher<std_msgs::msg::String>::SharedPtr p;   // typename は不要
```

だから**ドリルのコードに `typename` は出てきません。** rclcpp のヘッダを読むと大量に出てきます。
「型だと明示しているだけ」と読み飛ばせれば十分です。

### メッセージ型に生えるメンバ

`.msg` から生成される型には、決まったメンバが生えます。

```cpp
std_msgs::msg::String
  ├── ::SharedPtr           std::shared_ptr<String>
  ├── ::ConstSharedPtr      std::shared_ptr<const String>
  ├── ::UniquePtr           std::unique_ptr<String>
  └── data                  フィールド（.msg で定義したもの）
```

課題 03 で `.msg` を書くと、フィールドがこのようにメンバとして生えます。

```
# Num.msg
int64 num
```

```cpp
auto msg = drill_03_custom_interface::msg::Num();
msg.num = 42;        // ← .msg のフィールドがそのまま生えている
```

**`.msg` を書き換えたらビルドし直さないと生えません。**
課題 03 でビルドが「has no member named ...」で大量に落ちるのは、
`.msg` が未完成でフィールドが生成されていないからです。
ドリルのランナーはこの場合に専用のメッセージを出すようにしています。

```
この課題は、インターフェース定義（.msg / .srv）が未完成のうちは
ビルドが通りません。定義したフィールドが C++ の型に生えないので、
「has no member named ...」というエラーが大量に出ます。
```

## 9.4 エラーメッセージの読み方

**ここがこの章のいちばん実用的な部分です。**

テンプレートのエラーは長いです。まず実物を作ります。

```cpp
#include <algorithm>
#include <vector>

struct Point { int x; int y; };

int main()
{
  std::vector<Point> v{{1, 2}, {3, 4}};
  std::sort(v.begin(), v.end());     // Point に < が無い
  return 0;
}
```

```bash
$ g++ -std=c++17 sorterr.cpp -o sorterr 2>&1 | wc -l
84
```

**84 行**出ます。しかし本当の原因は 1 つ、「`Point` に `operator<` が無い」だけです。

読み方の手順を決めておきます。

**手順 1: `error:` で始まる行だけ抜き出す。**

```bash
g++ -std=c++17 sorterr.cpp 2>&1 | grep "error:"
```

```
/usr/include/c++/13/bits/predefined_ops.h:43:23: error: no match for ‘operator<’ (operand types are ‘Point’ and ‘Point’)
```

**1 行になりました。** これが原因です。
残りの 83 行は `note:`（候補の列挙）と `In instantiation of`（呼び出し経路）です。

**手順 2: 自分のファイル名が出ている行を探す。**

```bash
g++ -std=c++17 sorterr.cpp 2>&1 | grep "sorterr.cpp"
```

```
sorterr.cpp: In function ‘int main()’:
sorterr.cpp:9:8: required from here
```

**`required from here` が「自分のコードのどの行が引き金か」を教えています。**
9 行目の `std::sort` です。

**手順 3: `required from here` を下から上に辿る。**
エラーは「ライブラリの深いところ」で出ますが、`In instantiation of` の連鎖を辿ると
自分のコードに戻ってきます。**自分のファイル名が出ている一番下の行が起点です。**

まとめるとこうなります。

| したいこと | コマンド |
| --- | --- |
| 本当の原因を見る | `2>&1 \| grep "error:"` |
| 自分のコードのどこが引き金か | `2>&1 \| grep "あなたのファイル.cpp"` |
| 最初のエラーだけ見る | `-fmax-errors=1` |
| テンプレート展開の深さを制限 | `-ftemplate-backtrace-limit=0`（全部出す）/ `=1`（1 段だけ） |

**`-fmax-errors=1` は覚えておく価値があります。**
最初のエラーだけ直せば残りが連鎖的に消えることが多いので、
84 行が 20 行になって読みやすくなります。

```bash
g++ -std=c++17 -fmax-errors=1 sorterr.cpp
```

### rclcpp でよく出るテンプレートエラー

**① メッセージ型とコールバックの引数型が合わない**

```cpp
this->create_subscription<std_msgs::msg::String>(
  "topic", 10,
  [this](const std_msgs::msg::Int32 & msg) { });   // Int32 になっている
```

エラーは `create_subscription` の内部から数十行出ます。
`grep "error:"` で絞ると `no matching function for call to ...` が見え、
**`<>` の型とラムダの引数型を見比べる**だけで直ります。

**② `_1` の数が合わない**（7 章）

`std::bind` の 22 行のエラーです。同じ手順で絞れます。

**③ ヘッダの include 漏れ**

```cpp
this->create_publisher<std_msgs::msg::String>("topic", 10);
```

`#include "std_msgs/msg/string.hpp"` を忘れると、
`incomplete type` や `has not been declared` が出ます。
**テンプレートの `<>` に不完全な型を渡すと、エラーはインスタンス化の場所で出る**ので、
自分の書いた行から離れた場所に出ることがあります。

## 9.5 知っておくと読める周辺機能

自分で書く必要はありませんが、rclcpp のヘッダに出てくるので意味だけ挙げます。

| 記法 | 意味 | どこで見るか |
| --- | --- | --- |
| `template<typename T, typename Alloc = std::allocator<void>>` | 既定のテンプレート引数 | `create_publisher` の宣言 |
| `template<typename... Args>` | 可変長テンプレート | `make_shared` の実装 |
| `std::enable_if_t<...>` | 条件を満たす型のときだけ有効 | rclcpp のオーバーロード選択 |
| `static_assert(条件, "メッセージ")` | コンパイル時の検査 | メッセージ型の検証 |
| `constexpr` | コンパイル時に計算する | `rclcpp::QoS` の定数 |
| `std::remove_reference_t<T>` | 型を加工する（型特性） | `std::move` の実装（5 章） |

**`static_assert` は自分でも使えて有用です。**
たとえば自分で定義したエラーコードの値が、`move_base_flex` など
外部ライブラリ側の定義と一致しているかを、`static_assert` で
機械的に保証しておくと、片方だけ変わったときにコンパイルで気付けます。

```cpp
static_assert(ec::kNoPathFound == GetPathResult::NO_PATH_FOUND);
```

**実行しなくてもコンパイル時に検出できる**ので、定数の対応表のようなものには非常に有効です。

## 手元で試す

**84 行のエラーを 1 行に絞る練習をします。** これが実務でいちばん使うスキルです。

```cpp
// tmplerr.cpp
#include <algorithm>
#include <iostream>
#include <map>
#include <vector>

struct Point
{
  int x;
  int y;
};

int main()
{
  std::vector<Point> v{{3, 4}, {1, 2}};
  std::sort(v.begin(), v.end());
  for (const auto & p : v) {
    std::cout << p.x << "," << p.y << "\n";
  }
  return 0;
}
```

まず素で出して行数を数えます。

```bash
g++ -std=c++17 tmplerr.cpp -o tmplerr 2>&1 | wc -l
```

次に 3 つの絞り方を試します。

```bash
g++ -std=c++17 tmplerr.cpp 2>&1 | grep "error:"
g++ -std=c++17 tmplerr.cpp 2>&1 | grep "tmplerr.cpp"
g++ -std=c++17 -fmax-errors=1 tmplerr.cpp 2>&1 | wc -l
```

**`grep "error:"` の結果が 1 行であることを確認してください。**
84 行の出力の中で、意味のある情報はその 1 行だけです。

直し方は 2 通りあります。両方試してください。

```cpp
// ① 比較関数を渡す
std::sort(v.begin(), v.end(), [](const Point & a, const Point & b) { return a.x < b.x; });

// ② operator< を定義する
bool operator<(const Point & a, const Point & b) { return a.x < b.x; }
```

**②のほうがエラーメッセージに忠実な直し方です**（「`operator<` が無い」と言われたので足す）。
ただし実務では①を選ぶことが多いです。
「この型に唯一の自然な順序があるか」が疑わしいときは、比較関数を明示するほうが安全です。

もう 1 つ、**型を間違えたときのエラーを見ます。**

```cpp
std::map<std::string, int> m;
m.insert({1, "one"});      // key と value が逆
```

これも `grep "error:"` で絞ってから読んでください。
`no matching function for call to ‘std::map<...>::insert(...)’` が出ます。

## つまずきポイント

**エラーが 100 行出て読む気が失せる**
`grep "error:"` を先にやってください。この章の 9.4 節です。
それでも分からなければ `-fmax-errors=1` を足します。

**`error: ‘SharedPtr’ in ‘class rclcpp::Publisher<...>’ does not name a type`**
`typename` が必要な文脈です（テンプレートの中）。
ドリルのコードでこれが出るなら、`<>` の中の型を間違えている可能性が高いです。

**`error: template argument 1 is invalid`**
`<>` の中に型ではないもの（変数名など）を書いています。

**`error: wrong number of template arguments`**
`<>` の中の個数が違います。`create_publisher<T>` は 1 つです。

**`undefined reference` がテンプレート関数で出た**
テンプレートの定義を `.cpp` に書いています。
**テンプレートは使う場所で定義が見えていなければインスタンス化できない**ので、
`.hpp` に定義を書きます（1 章の ODR の例外です。`inline` を付ける必要はありません）。

**メッセージ型のメンバが無いと言われる**
`.msg` を変更したのにビルドし直していない、または `.msg` が未完成です（課題 03）。
`rm -rf build install log` してからやり直してください。

## ドリルのどこで出るか

| 課題 | この章の何が出るか |
| --- | --- |
| 01 | `create_publisher<std_msgs::msg::String>` / `Publisher<T>::SharedPtr` |
| 02 | `create_subscription<std_msgs::msg::String>` |
| 03 | **`.msg` / `.srv` から型が生成される。** フィールドがメンバとして生える |
| 04, 05 | `create_service<T>` / `create_client<T>`。`T::Request` / `T::Response` |
| 10 | `create_server<Fibonacci>`。`Fibonacci::Goal` / `::Feedback` / `::Result` |
| 11 | **テンプレートが 1 つも出てこない課題。** `double` だけで書ける |
| 12 | `rclcpp::QoS` のメソッドチェーン（テンプレートではない） |
| 14 | `make_unique<std_msgs::msg::String>` / `String::ConstSharedPtr` |

課題 04 が「型の中の型」がいちばん出る課題です。

```cpp
void add_two_ints(
  const std::shared_ptr<example_interfaces::srv::AddTwoInts::Request> request,
  std::shared_ptr<example_interfaces::srv::AddTwoInts::Response> response)
{
  response->sum = request->a + request->b;
}
```

`AddTwoInts::Request` と `AddTwoInts::Response` は、
**`.srv` ファイルの `---` の上と下から生成された 2 つの型**です。

```
# AddTwoInts.srv
int64 a
int64 b
---
int64 sum
```

`---` の上が `Request`（`a`、`b`）、下が `Response`（`sum`）。
**`.srv` の構造がそのまま型の構造になっている**ことが分かると、
`request->a` や `response->sum` が暗記事項でなくなります。
