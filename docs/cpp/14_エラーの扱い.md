# 14. エラーの扱い

> **この章のねらい**: ドリルの全 15 課題を grep すると、`throw` / `try` / `catch` は出てきません。0 回です。
> なのになぜこの章があるのか。それは「C++ がなぜ例外を用意したのか」と
> 「ROS 2 のコードがなぜ例外を避けるのか」が深く結びついているからです。
> 例外の仕組み（スタック巻き戻し、RAII）を理解すると、
> なぜドリルが返却コード（パラメータ未宣言時の `ParameterNotDeclaredException`）や
> タイムアウト機構を大事にしているのかが見えてきます。

## 14.1 エラー報告の 4 つの手段

C++ でエラーを報告する方法は 4 つあります。

| 手段 | 例 | 使うべき場面 |
| --- | --- | --- |
| **返却コード** | `int status = func(); if (status != 0) { ... }` | 言語・プロセス境界を越える（DDS、パイプ、ファイル） |
| **`std::optional<T>`** | `auto r = func(); if (!r) { ... }` | 値がある/ないという 2 値の違い |
| **例外** | `throw std::runtime_error(...);` | コールスタック上でのエラー伝播。言語内。C++ オンリー |
| **abort/assert** | `assert(x > 0);` | 仮定違反。デバッグ用。リリースビルドで消される |

ROS 2 コードが返却コードを多く使う理由は、**DDS 上で Python と C++ が混在する**からです。
Python の例外は DDS 越しに送れません。Service/Action の応答は返却コードで返す。

## 14.2 例外 — `throw`, `try`, `catch`

```cpp
#include <iostream>
#include <stdexcept>

int divide(int a, int b)
{
  if (b == 0) {
    throw std::invalid_argument("0 で割れません");
  }
  return a / b;
}

int main()
{
  try {
    std::cout << "10 / 2 = " << divide(10, 2) << "\n";
    std::cout << "10 / 0 を試す...\n";
    divide(10, 0);
    std::cout << "ここには来ない\n";
  } catch (const std::invalid_argument & e) {
    std::cout << "例外をキャッチ: " << e.what() << "\n";
  }

  std::cout << "プログラム続行\n";
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/bK9eq4h76)

```
10 / 2 = 5
10 / 0 を試す...
例外をキャッチ: 0 で割れません
プログラム続行
```

`throw std::invalid_argument(...)` で例外を発生させます。
`try { ... } catch (...) { ... }` で捕捉します。

**重要: `catch` は常に `const &` で受けてください。** 値で受けるとスライシングが起きます。

```cpp
catch (std::exception & e) { }          // 参照 ← こう
catch (std::exception e) { }             // 値 ← これはダメ
```

### スライシング — 派生クラスが基底に縮む

3 章でやった話が例外にも当てはまります。

```cpp
#include <iostream>
#include <stdexcept>
#include <string>

class MyError : public std::runtime_error
{
public:
  explicit MyError(const std::string & msg) : std::runtime_error(msg), code_(99) {}
  int code() const { return code_; }

private:
  int code_;
};

int main()
{
  try {
    throw MyError("カスタムエラー");
  } catch (const std::exception & e) {
    std::cout << "基底でキャッチ: " << e.what() << "\n";
    // e は std::exception。MyError ではない
    auto pe = dynamic_cast<const MyError *>(&e);
    if (pe) {
      std::cout << "MyError として復元: " << pe->code() << "\n";
    }
  }

  std::cout << "\n値でキャッチするとスライシング:\n";
  try {
    throw MyError("カスタムエラー");
  } catch (std::exception e) {  // ← 値でキャッチ
    std::cout << "スライシング: " << e.what() << "\n";
    // e は std::exception のコピー。MyError 部分は削除済み
  }
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/56f1c6T8z)

```
基底でキャッチ: カスタムエラー
MyError として復元: 99

値でキャッチするとスライシング:
スライシング: カスタムエラー
```

2 番目の `try` ブロックで、`e` は `std::exception` のコピーです。
派生クラスの `code_` メンバは切り落とされます。

コンパイラは警告を出します：`warning: catching polymorphic type by value`。
この警告が出たら `const &` に直してください。

## 14.3 スタック巻き戻し（Stack Unwinding）と RAII

C++ の例外の強力なところは、**スタックが自動的に巻き戻り、デストラクタが呼ばれる**ことです。

```cpp
#include <iostream>
#include <stdexcept>

class Resource
{
public:
  explicit Resource(const std::string & name) : name_(name)
  {
    std::cout << "  [" << name_ << "] 確保\n";
  }
  ~Resource() { std::cout << "  [" << name_ << "] 解放\n"; }

private:
  std::string name_;
};

void may_throw()
{
  std::cout << "  may_throw() 実行\n";
  throw std::runtime_error("エラー");
}

int main()
{
  try {
    Resource r1("リソースA");
    Resource r2("リソースB");
    may_throw();
    std::cout << "ここには来ない\n";
  } catch (const std::exception & e) {
    std::cout << "例外をキャッチ: " << e.what() << "\n";
  }

  std::cout << "リソースは確実に解放されました\n";
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/nPEfxPchW)

```
  [リソースA] 確保
  [リソースB] 確保
  may_throw() 実行
  [リソースB] 解放
  [リソースA] 解放
例外をキャッチ: エラー
リソースは確実に解放されました
```

`may_throw()` で例外が飛ぶと、スコープを逆順に抜けます。
`r2` 、 `r1` の順でデストラクタが呼ばれます。

**これが C++ で例外を安全に使える理由です。** 2 章の RAII と組み合わせると、
例外が飛んでも「取得したリソースは必ず解放される」という保証が成り立ちます。

## 14.4 デストラクタから例外を投げてはいけない

デストラクタが呼ばれているとき、既に例外が propagate 中かもしれません。
その時にさらに例外が飛ぶと、**`std::terminate` が呼ばれてプログラム強制終了します。**

```cpp
#include <iostream>
#include <stdexcept>

class BadDtor
{
public:
  ~BadDtor() noexcept(false)
  {
    throw std::runtime_error("デストラクタから例外");
  }
};

int main()
{
  try {
    BadDtor b;
    throw std::runtime_error("別の例外");
  } catch (const std::exception & e) {
    std::cout << "キャッチ: " << e.what() << "\n";
  }

  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/8fnzYhEsM)

```
terminate called after throwing an instance of 'std::runtime_error'
  what():  デストラクタから例外
```

`BadDtor` のデストラクタが例外を投げようとしますが、既に `std::runtime_error` が propagate 中です。
その時点で 2 番目の例外が飛ぶことは UB（未定義動作）で、`std::terminate` が呼ばれます。

**規則: デストラクタには `noexcept` を付け、絶対に例外を投げない。**

```cpp
class Good
{
public:
  ~Good() noexcept  // ← 例外を投げないことを約束
  {
    // クリーンアップのロジック
    // 例外は投げない、またはキャッチして処理する
  }
};
```

## 14.5 `noexcept` — 例外の約束

`noexcept` は「この関数は例外を投げない」という約束です。
違反すると `std::terminate` が呼ばれます。

```cpp
#include <iostream>
#include <stdexcept>

void safe_operation() noexcept
{
  std::cout << "安全な操作\n";
}

void unsafe_operation() noexcept
{
  throw std::runtime_error("例外をスロー");  // noexcept 違反
}

int main()
{
  try {
    safe_operation();
    unsafe_operation();
  } catch (const std::exception & e) {
    std::cout << "キャッチ: " << e.what() << "\n";
  }

  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/T7fjejozK)

```
安全な操作
terminate called after throwing an instance of 'std::runtime_error'
  what():  例外をスロー
```

コンパイラは警告を出します。

```
warning: 'throw' will always call 'terminate' [-Wterminate]
```

`noexcept` は単なるドキュメントではなく、**コンパイラの最適化根拠**にもなります。
「例外が飛ばない」と保証されているので、例外処理のコストを削れます。

5 章で「ムーブコンストラクタは `noexcept`」と書いたのはこの理由です。
`std::vector` は再確保時に `noexcept` ムーブコンストラクタを使い、そうでなければコピーします。

## 14.6 ROS 2 のエラー処理の流儀

公式の [コーディング規約](../ros2-コーディング規約.md) では、こう書いています：

> 例外: 可。ユーザ向け API では慣用的。ただし**デストラクタでは避ける**。
> C でラップする API では避けることを検討。

つまり：

- **ユーザ向け API（C++ のメイン部分）**: 例外 OK
- **デストラクタ**: 例外 NG（`noexcept` 必須）
- **C 側へ投げる API**: 例外 NG（C は例外を理解できない）

## 14.7 ドリルで実際に踏む例外

ドリルには `throw` は出ないと言いましたが、`catch` する機会はあります。

### `rclcpp::exceptions::ParameterNotDeclaredException`

課題 06 で出ます。

```cpp
// 悪い例
auto value = this->get_parameter("speed");  // 未宣言なら throw
```

正しくは先に宣言してから使う：

```cpp
this->declare_parameter("speed", 1.0);
auto value = this->get_parameter("speed");
```

この設計は **「静かに失敗するより、大きく失敗しろ」** という哲学です。
デフォルト値で動いているつもりで、実は設定されていなかった、という罠を防ぎます。

### `std::bad_weak_ptr` — 6 章の復習

`shared_ptr` として作られていないオブジェクトで `shared_from_this()` を呼ぶと飛びます。

```cpp
MinimalPublisher node;  // スタック上
node.some_method_calling_shared_from_this();  // std::bad_weak_ptr
```

### `rclcpp::exceptions::InvalidNamespaceError`

ノード名に無効な文字が含まれていると飛びます。

## 14.8 なぜ ROS 2 は例外を避けるのか

一言：**例外は言語内だけです。DDS を越えられません。**

Service や Action の応答には返却コードを使います。

```cpp
// これは C++ で書けます
throw std::runtime_error("エラー");

// でも Action の Result は言語非依存の型
example_interfaces::action::Fibonacci_Result result;
result.sequence = {1, 1, 2, 3, 5};  // ← 返却コードはここに入れる
```

Python ノードと通信する時点で、**例外は使えません**。
だから ROS 2 は返却コード文化が強いのです。

## 14.9 他のエラー処理手段

### `std::optional<T>` — あるか無いか

```cpp
#include <iostream>
#include <optional>
#include <string>

std::optional<int> parse_int(const std::string & s)
{
  try {
    return std::stoi(s);
  } catch (const std::exception &) {
    return std::nullopt;
  }
}

int main()
{
  auto a = parse_int("42");
  if (a) {
    std::cout << "成功: " << *a << "\n";
  } else {
    std::cout << "失敗\n";
  }

  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/E616zYs9f)

```
成功: 42
```

`std::optional` は「値がある / ない」の 2 値です。
エラーの詳細（どの理由で失敗したのか）を伝えられません。

ドリルでは出ないので、知識として押さえる程度で大丈夫です。

### `assert()` と `static_assert`

```cpp
#include <iostream>
#include <cassert>

static_assert(sizeof(int) >= 4);  // コンパイル時チェック

void check_range(int x)
{
  assert(x >= 0 && x < 100);  // 実行時チェック
  std::cout << "OK: " << x << "\n";
}

int main()
{
  check_range(50);
  // check_range(-1);  // コメント外すと assert に引っかかる
  return 0;
}
```

```
OK: 50
```

| 種類 | 時期 | リリースビルド | 用途 |
| --- | --- | --- | --- |
| `static_assert` | コンパイル時 | 残る | テンプレートの要件チェック |
| `assert()` | 実行時 | 消える（`NDEBUG`） | 開発時の仮定チェック |

**`assert` は リリースビルドで全削除されます。** 本番で必須なチェックは `assert` ではなく、
例外か返却コードを使ってください。

## 手元で試す

**エラー処理の 4 つのパターンを全部実装してください。**

```cpp
// error_handling.cpp
#include <cassert>
#include <iostream>
#include <optional>
#include <stdexcept>
#include <string>

// パターン 1: 返却コード
int divide_rc(int a, int b, int & result)
{
  if (b == 0) {
    return -1;  // エラーコード
  }
  result = a / b;
  return 0;
}

// パターン 2: std::optional
std::optional<int> divide_opt(int a, int b)
{
  if (b == 0) {
    return std::nullopt;
  }
  return a / b;
}

// パターン 3: 例外
int divide_exc(int a, int b)
{
  if (b == 0) {
    throw std::invalid_argument("divide by zero");
  }
  return a / b;
}

// パターン 4: assert
int divide_assert(int a, int b)
{
  assert(b != 0);
  return a / b;
}

int main()
{
  std::cout << "-- 1. 返却コード\n";
  {
    int result = 0;
    if (divide_rc(10, 2, result) == 0) {
      std::cout << "成功: " << result << "\n";
    } else {
      std::cout << "エラー\n";
    }
  }

  std::cout << "\n-- 2. std::optional\n";
  {
    auto r = divide_opt(10, 2);
    if (r) {
      std::cout << "成功: " << *r << "\n";
    } else {
      std::cout << "エラー\n";
    }
  }

  std::cout << "\n-- 3. 例外\n";
  {
    try {
      int r = divide_exc(10, 2);
      std::cout << "成功: " << r << "\n";
    } catch (const std::invalid_argument & e) {
      std::cout << "エラー: " << e.what() << "\n";
    }
  }

  std::cout << "\n-- 4. assert\n";
  {
    int r = divide_assert(10, 2);
    std::cout << "成功: " << r << "\n";
  }

  std::cout << "\n-- RAII: 例外時も解放\n";
  {
    struct Resource {
      explicit Resource(const char * n) : name(n) {
        std::cout << "  [" << n << "] 確保\n";
      }
      ~Resource() { std::cout << "  [" << name << "] 解放\n"; }
      const char * name;
    };

    try {
      Resource r1("A");
      Resource r2("B");
      std::cout << "  エラーを投げます\n";
      throw std::runtime_error("問題");
    } catch (const std::exception & e) {
      std::cout << "例外をキャッチ: " << e.what() << "\n";
    }
  }

  std::cout << "プログラム終了\n";
  return 0;
}
```

**予想: 各パターンでどのメッセージが出るか。特に:**

1. 返却コード版で `divide_rc(10, 0, result)` すると「エラー」が出るか
2. RAII ブロックで両方のリソースが確実に解放されるか（逆順）

```bash

```

## つまずきポイント

**`error: exception specification of overriding function is more lax`**

デストラクタを `noexcept` で上書きしようとしています。基底も `noexcept` でないと通りません。
その場合は `~Derived() noexcept = default;` のように明示的にしてください。

**`error: catch (...) must be the last handler`**

`catch (...)` の後に別の catch がいます。`catch (...)` は「すべてを捕捉」するので、
最後に置いてください。

**`exception specification of [...]  differs from [...]`**

仮想関数の `noexcept` 指定が基底と異なります。
`override` する関数は基底の `noexcept` 指定を踏襲してください。

**メモリリークが出ている（Valgrind で）**

`catch` ブロックで `new` したメモリを `delete` し忘れていませんか。
または例外を throw する前に `delete` するか、スマートポインタを使ってください。

**`std::bad_weak_ptr`（6 章の復習）**

`shared_ptr` として作られていないオブジェクトで `shared_from_this()` を呼んでいます。
ノードは必ず `std::make_shared<MinimalPublisher>()` で作ってください。

## ドリルのどこで出るか

| 課題 | この章の何が出るか |
| --- | --- |
| 06 | `get_parameter()` 呼び出し前に `declare_parameter()` を忘れると `ParameterNotDeclaredException` |
| 07 | `declare_parameter()` で同じ名前を 2 回宣言するとエラー。`has_parameter()` で先に確認 |
| 09 | action 完了時の `ResultCode` は返却コード（例外ではない） |
| テスト | service 応答が無いとき、`future.wait_for()` でタイムアウト処理（返却コードパターン） |

課題 06 で実際に `ParameterNotDeclaredException` を踏みます。
「パラメータの設定を忘れた」と「名前のタイポ」の両方を catch するには、
`try { ... } catch (const rclcpp::exceptions::ParameterNotDeclaredException & e) { ... }` で拾います。

ドリルのテストコードには例外処理が出てきます。
が、あなたが実装するメイン部分には基本的に出ません。
