# 1. ビルドとリンクの仕組み

> **この章のねらい**: C++ には「モジュール」がありません（C++20 にはありますが ROS 2 Jazzy は C++17 です）。
> 代わりにあるのは、**テキストを貼り付けるだけの `#include`** と、**あとから名前を解決するリンカ**です。
> この 2 段構えを知らないと、`undefined reference` や `redefinition` というエラーが
> 「文法は合っているのに通らない」謎のエラーに見えます。
> ドリルで最初に踏むのはこれです。文法の話に入る前に、ここを片付けます。

> **前提**: [入門編 10章 ヘッダとプロジェクト構成](../cpp-basics/10_ヘッダとプロジェクト構成.md)で
> 宣言と定義の分離とインクルードガードを、[7章 `static`](../cpp-basics/07_static.md)で
> ファイルスコープの `static`（内部リンケージ）を扱っています。
> この章はそこから一段深く、**リンカが何を探して失敗するのか**に踏み込みます。

## 1.1 Python との違い — `#include` はインポートではない

Python の `import` は「モジュールを探して読み込み、名前空間として結び付ける」操作です。
C++ の `#include` は違います。**指定したファイルの中身を、その場にテキストとして貼り付けるだけ**です。

確かめられます。

```cpp
// hello.cpp
#include <string>
int main() { return 0; }
```

```bash
$ g++ -std=c++17 -E hello.cpp | wc -l
25257
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/e1Wax65x1)

`-E` はプリプロセッサだけを走らせるオプションです。
2 行のファイルが **25257 行**になりました。`<string>` とそれが `#include` しているものすべてが、
本当に展開されて貼り付けられています。

この「貼り付けるだけ」という性質が、C++ のビルドのすべてを決めています。

## 1.2 コンパイルは「1 ファイルずつ、他を知らずに」進む

C++ のビルドは 2 段階です。

```
  minimal_publisher.cpp ──コンパイル──▶ minimal_publisher.o  ┐
                                                            ├─リンク─▶ talker
  talker_main.cpp       ──コンパイル──▶ talker_main.o       ┘
```

重要なのは、**コンパイルは 1 つの `.cpp` ごとに完全に独立して行われる**ことです。
`minimal_publisher.cpp` をコンパイルしているあいだ、コンパイラは
`talker_main.cpp` の存在を知りません。

この単位を **翻訳単位（translation unit）** と呼びます。
1 つの `.cpp` と、そこから `#include` で貼り付けられた全部を合わせたものが 1 翻訳単位です。

すると問題が起きます。`talker_main.cpp` から `MinimalPublisher` を使いたいのに、
その定義は `minimal_publisher.cpp` にあって、コンパイル時には見えません。

これを解決するのが**宣言と定義の分離**です。

## 1.3 宣言と定義 — `.hpp` と `.cpp` を分ける理由

- **宣言（declaration）** — 「そういう名前のものが、どこかにある」と型だけ伝える
- **定義（definition）** — 実際の中身

コンパイラは、呼び出しをコンパイルするのに**宣言だけあれば足ります**。
中身がどこにあるかは知らなくてよく、「あとでリンカが見つけてくれる」前提で
呼び出し命令だけ書き出します。

ドリルの課題 01 がまさにこの形です。

```cpp
// exercises/01_publisher/include/drill/minimal_publisher.hpp（宣言）
class MinimalPublisher : public rclcpp::Node
{
public:
  MinimalPublisher();

private:
  void timer_callback();

  rclcpp::TimerBase::SharedPtr timer_;
  rclcpp::Publisher<std_msgs::msg::String>::SharedPtr publisher_;
  size_t count_;
};
```

```cpp
// solutions/01_publisher/src/minimal_publisher.cpp（定義）
MinimalPublisher::MinimalPublisher()
: Node("minimal_publisher"), count_(0)
{
  publisher_ = this->create_publisher<std_msgs::msg::String>("topic", 10);
  timer_ = this->create_wall_timer(
    500ms, std::bind(&MinimalPublisher::timer_callback, this));
}
```

`.hpp` に `MinimalPublisher();` と書いてあるだけで、`talker_main.cpp` は
`std::make_shared<MinimalPublisher>()` と書けます。中身は知らなくてよいのです。

`MinimalPublisher::` という接頭辞に注目してください。
`.cpp` 側では「どのクラスのメンバか」を明示する必要があります。
クラス定義の外に出た瞬間、そのスコープから抜けているからです。

### メンバ変数の宣言は「定義」でもある

ややこしい例外です。
`.hpp` の `size_t count_;` は宣言のように見えますが、
**これはクラスのレイアウト（どのメンバが何バイト占めるか）を決める情報**なので、
クラス定義の一部として `.hpp` に必ず書かなければなりません。

だから `.hpp` を見れば、そのクラスが何を持っているかは全部分かります。
逆に言うと、**メンバを 1 つ足すだけで `.hpp` を include している全 `.cpp` の再コンパイルが必要**です。
これが C++ のビルドが遅い主要な理由の 1 つです。

## 1.4 One Definition Rule — 「定義は 1 回だけ」

`#include` が「貼り付けるだけ」であることを思い出してください。
すると、次のような事故が起きます。

```cpp
// a.hpp
struct Point { int x; int y; };
```

```cpp
// b.hpp
#include "a.hpp"
```

```cpp
// main.cpp
#include "a.hpp"
#include "b.hpp"   // ここで a.hpp が 2 回目の貼り付けになる
int main() { return 0; }
```

```
In file included from b.hpp:1,
                 from redef.cpp:2:
a.hpp:1:8: error: redefinition of ‘struct Point’
    1 | struct Point { int x; int y; };
      |        ^~~~~
```

エラーの行が `a.hpp:1` を指していることに注目してください。
**間違っているのは `main.cpp` の 2 行の `#include` なのに、コンパイラは貼り付けられた先の行を指します。**
`In file included from` の連なりが「どう辿ってここに来たか」の経路です。
C++ のエラーを読むときは、この経路を下から上に読むのが基本になります。

`Point` の定義が同じ翻訳単位に 2 回現れました。
C++ には **One Definition Rule（ODR）** という規則があり、
**1 つの翻訳単位に同じ定義が 2 回あってはいけません**。

解決策は **インクルードガード**です。ドリルでは `#pragma once` を使っています。

```cpp
// exercises/11_node_test/include/drill/velocity_limiter.hpp
#pragma once

double limit_velocity(double target, double previous, double max_speed, double max_delta);
```

`#pragma once` は「このファイルは 1 翻訳単位につき 1 回しか貼り付けない」という指示です。
2 回目の `#include` は何もしません。

古い書き方は次の形で、意味は同じです。ROS 2 のコアはこちらを使っています。

```cpp
#ifndef DRILL__VELOCITY_LIMITER_HPP_
#define DRILL__VELOCITY_LIMITER_HPP_
// ...
#endif  // DRILL__VELOCITY_LIMITER_HPP_
```

`#pragma once` は正式な規格ではありませんが、g++ / clang / MSVC すべてが対応しています。
このドリルは短さを優先して `#pragma once` を使っています。

### ODR は翻訳単位をまたいでも効く

もう 1 つ罠があります。`.hpp` に**関数の中身を書いて**しまうと、
その `.hpp` を include した各 `.cpp` が、それぞれ同じ関数の定義を持ちます。

```cpp
// bad.hpp
#pragma once
int add(int a, int b) { return a + b; }   // 中身を書いてしまった
```

`#pragma once` があっても、これは `x.cpp` と `y.cpp` の**別々の翻訳単位**にそれぞれ
1 個ずつ定義を作ります。コンパイルは通り、リンクで落ちます。

```
/usr/bin/ld: /tmp/ccXbUsPY.o: in function `add(int, int)':
y.cpp:(.text+0x0): multiple definition of `add(int, int)'; /tmp/ccCmAlqs.o:x.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status
```

`/usr/bin/ld:` で始まるのがリンカのメッセージの目印です。
**コンパイラのエラーには行と桁とソースの抜粋が付きますが、リンカのエラーには付きません。**
リンカはソースを見ていないので、`.text+0x0` のようなオブジェクトファイル内のオフセットしか言えません。
この見た目の違いが、そのまま「どちらの段階で落ちたか」の判別に使えます。

`#pragma once` は**同じ翻訳単位内の重複**しか防げません。
翻訳単位をまたいだ重複は防げないのです。

`.hpp` に中身を書きたいときは `inline` を付けます。
`inline` は「複数の翻訳単位に同じ定義があってもよい。リンカは 1 つを選べ」という指示です。

```cpp
// good.hpp
#pragma once
inline int add(int a, int b) { return a + b; }
```

**クラス定義の中に書いたメンバ関数は自動的に `inline`** です。
だから次の形は問題ありません。

```cpp
class Foo
{
public:
  int add(int a, int b) { return a + b; }   // 暗黙に inline
};
```

テンプレートも同様に例外扱いされます（8章）。

## 1.5 リンクエラーの読み方

ビルドエラーの見分け方を整理します。**どちらの段階で落ちたかで原因の場所が変わります。**

| メッセージ | 段階 | 意味 | 直す場所 |
| --- | --- | --- | --- |
| `'x' was not declared in this scope` | コンパイル | **宣言**が見えていない | `#include` の追加、名前空間、綴り |
| `no matching function for call to ...` | コンパイル | 宣言はあるが引数の型が合わない | 呼び出し側の引数 |
| `redefinition of ...` | コンパイル | 同一翻訳単位に定義が 2 回（ODR） | インクルードガード |
| `undefined reference to 'f()'` | **リンク** | **定義**が見つからない | `.cpp` の実装漏れ、`CMakeLists.txt` のリンク指定 |
| `multiple definition of 'f()'` | **リンク** | 複数の翻訳単位に定義がある | `inline` を付ける、`.cpp` に移す |

**`undefined reference` はコンパイルエラーではありません。**
「文法は全部合っている。ただ中身がどこにも無い」と言われています。
だから見る場所はソースの文法ではなく、次の 3 つです。

1. その関数を `.cpp` に書き忘れていないか
2. 書いたが `MinimalPublisher::` のような修飾を忘れて、別の関数を定義していないか
3. `CMakeLists.txt` でその `.cpp` を `add_library` / `add_executable` に入れ忘れていないか

3 番目の型がドリルで実際に起きます。課題を追加したのに `CMakeLists.txt` に
ファイル名を書き忘れると、この形で出ます。

### 名前修飾（name mangling）を読む

リンカのメッセージが読みにくいのは、C++ が関数名を**変形**して保存しているからです。

```bash
$ g++ -std=c++17 -c minimal_publisher.cpp -o mp.o
$ nm -C mp.o | grep timer_callback
0000000000000000 T MinimalPublisher::timer_callback()
```

`nm` はオブジェクトファイル内のシンボル一覧を出します。
`-C` を付けないと `_ZN16MinimalPublisher14timer_callbackEv` という変形後の名前が出ます。
`-C`（demangle）を付ければ人間が読める形に戻ります。

`undefined reference` で困ったら、**`nm -C` でそのシンボルが本当に居ないかを直接確認する**のが
いちばん速い切り分けです。

- `T` — このファイルが定義を持っている（text section）
- `U` — このファイルは使っているが定義を持っていない（undefined）

`U` のまま誰も `T` を持っていなければ、それがリンクエラーの正体です。

## 1.6 CMake は何をしているのか

ドリルの各課題の `CMakeLists.txt` は、上の 2 段階をそのまま書いたものです。

```cmake
# exercises/01_publisher/CMakeLists.txt（抜粋・要約）
add_library(minimal_publisher src/minimal_publisher.cpp)   # ① コンパイルしてライブラリに
target_include_directories(minimal_publisher PUBLIC include) # ② .hpp を探す場所
ament_target_dependencies(minimal_publisher rclcpp std_msgs) # ③ 依存の include とライブラリ

add_executable(talker src/talker_main.cpp)                  # ④ main をコンパイル
target_link_libraries(talker minimal_publisher)              # ⑤ ①とリンク
```

- ② が足りないと **コンパイルエラー**（`.hpp` が見つからない）
- ⑤ が足りないと **リンクエラー**（`undefined reference to MinimalPublisher::...`）

エラーメッセージの段階から、`CMakeLists.txt` のどの行が足りないかまで逆算できます。

なぜクラスをライブラリにしているかというと、**`ros2 run` 用の実行ファイルと gtest の両方から
同じ実装をリンクしたい**からです。1 回コンパイルした `.o` を 2 箇所で使い回しています。

```
src/minimal_publisher.cpp ──▶ libminimal_publisher.a ──┬──▶ talker（ros2 run 用）
                                                       └──▶ test_exercise（採点用）
```

## 手元で試す

**ODR とリンクエラーを自分で起こしてみます。** 3 ファイル作ってください。

```cpp
// counter.hpp
#pragma once

int next_id();          // 宣言のみ
int twice(int x) { return x * 2; }   // ← わざと中身を書いた（罠）
```

```cpp
// counter.cpp
#include "counter.hpp"

int next_id()
{
  static int id = 0;
  return ++id;
}
```

```cpp
// main.cpp
#include "counter.hpp"
#include <iostream>

int main()
{
  std::cout << next_id() << next_id() << twice(21) << "\n";
  return 0;
}
```

**予想してください。`twice` は `#pragma once` で守られた `.hpp` の中に 1 回しか書いていません。
これはビルドが通るでしょうか。**

```bash
g++ -std=c++17 -Wall -Wextra counter.cpp main.cpp -o app && ./app
```

<details markdown="1"><summary>解答（コンパイルエラー）</summary>

```
/usr/bin/ld: /tmp/ccQCXdXD.o: in function `twice(int)':
main.cpp:(.text+0x0): multiple definition of `twice(int)'; /tmp/ccx244xq.o:counter.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status
```

</details>

**落ちます。** ソースには `twice` が 1 回しか書かれていないのに「multiple definition」です。
`counter.cpp` と `main.cpp` がそれぞれ `counter.hpp` を貼り付けた結果、
**オブジェクトファイルには 2 個**できているからです。
`#pragma once` は 1 翻訳単位内の重複しか防げない、という 1.4 節の話がここに出ています。

翻訳単位を増やすと、エラーも増えます。

```bash
sed 's/int main()/int other()/' main.cpp > other.cpp
g++ -std=c++17 counter.cpp main.cpp other.cpp -o app
```

```
/usr/bin/ld: ... main.cpp:(.text+0x0): multiple definition of `twice(int)'; ... counter.cpp: first defined here
/usr/bin/ld: ... other.cpp:(.text+0x0): multiple definition of `twice(int)'; ... counter.cpp: first defined here
```

`.cpp` 1 つにつき 1 個ずつ定義ができていることが、エラーの数から見て取れます。

では直します。`counter.hpp` の `twice` に `inline` を付けてください。

```bash
sed -i 's/^int twice/inline int twice/' counter.hpp
g++ -std=c++17 counter.cpp main.cpp other.cpp -o app && ./app
```

```
1242
```

通りました。何が変わったのかを `nm` で直接見ます。

```bash
$ g++ -std=c++17 -c main.cpp -o main.o && nm -C main.o | grep twice
```

| `inline` なし | `inline` あり |
| --- | --- |
| `0000000000000000 T twice(int)` | `0000000000000000 W twice(int)` |

**`T` が `W` に変わりました。**
`T` は「これが唯一の定義だ」、`W`（weak symbol）は「定義を持っているが、
他にも同じものがあってよい。リンカは好きな 1 つを選べ」という意味です。
`inline` はこの 1 文字を変えるためのキーワードです。

「関数呼び出しを展開して速くする」という説明を見たことがあるかもしれませんが、
**現代の `inline` の実質的な意味はこちらの ODR 緩和**です。
展開するかどうかは最適化器が独自に判断し、`inline` の有無を見ていません。

出力 `1242` も確認してください。`next_id()` が `1`、`2`、`twice(21)` が `42` で `1242` です。
`next_id` の `static int id` は**関数を抜けても消えない**変数で、しかも
`counter.cpp` に 1 個しかないので、呼ぶたびに増えます。

## つまずきポイント

**`.hpp` の変更が反映されない**
`.hpp` を直したのにビルドが変わらない場合、依存関係の記録が壊れています。
`rm -rf build install log` してやり直してください。
CMake は `.hpp` の依存を自動追跡しますが、ファイルを移動・改名すると取りこぼすことがあります。

**`error: 'size_t' was not declared in this scope`**
`size_t` は `<cstddef>` にあります。
運よく他のヘッダが間接的に include していると通り、include を整理した途端に落ちます。
**使う型は自分で include する**のが原則です（"include what you use"）。

**`#include "..."` と `#include <...>` の違い**
`"..."` は「まず自分と同じディレクトリを探し、次に include パス」。
`<...>` は「include パスだけ」。
自作のヘッダは `"..."`、システム・外部ライブラリは `<...>` が慣習です。
ドリルでは `#include "drill/minimal_publisher.hpp"` と `#include <gtest/gtest.h>` の
両方が出てきます。

**`undefined reference to 'main'`**
`main()` を含む `.cpp` をビルド対象に入れ忘れています。
ドリルでは `main()` は `src/*_main.cpp` に分離してあるので、
`add_executable` にそのファイルが入っているかを見てください。

## ドリルのどこで出るか

| 課題 | 関係する箇所 |
| --- | --- |
| 全課題 | `include/drill/*.hpp` が宣言、`src/*.cpp` が定義。編集するのは `.cpp` だけ |
| 01 | `talker_main.cpp` と `minimal_publisher.cpp` が別の翻訳単位。ライブラリ経由でリンク |
| 03 | `.msg` / `.srv` から `.hpp` が**自動生成**される。`build/` の下に生成物ができ、それを include する |
| 11 | 純粋関数 `limit_velocity` を `.hpp` で宣言し、`.cpp` を 2 つ（正しい版・バグ版）用意して、リンクを差し替えている |
| 15 | `RCLCPP_COMPONENTS_REGISTER_NODE` が共有ライブラリに登録用シンボルを埋め込む。実行時に `dlopen` で探される |

課題 11 の構造がこの章の総合演習になっています。

```
velocity_limiter.hpp（宣言 1 つ）
  ├── velocity_limiter.cpp        （正しい定義）  ──▶ test_exercise      … 通るべき
  └── velocity_limiter_mutant.cpp （バグ入り定義）──▶ test_exercise_mutant … 落ちるべき
```

同じ `.hpp`・同じテストコードのまま、**リンクする `.cpp` だけを差し替えて 2 つの実行ファイルを作る**。
宣言と定義が分かれているからこれができます。
「テストがバグを検出できているか」を機械的に確かめる仕掛けが、この章の仕組みの上に乗っています。
