# 13. 並行性の最小限

> **この章のねらい**: ドリルで `future` は **50 回**、`mutex` は **9 回**出てきます。
> 初心者は「スレッドを自分で作る」練習をしますが、ROS 2 では違います。
> rclcpp の `Executor` がスレッドを所有しており、あなたのコードはその中で**コールバックとして走ります**。
> つまり「スレッドを作る」ことはドリルで一度も出てきません。
> しかし Executor の中で何が起きているかを理解していないと、
> あるコールバックが別のコールバックの実行をブロックする「デッドロック」に引っかかります。
> この章は「並行処理の全貌」ではなく、ドリルで実際に踏む落とし穴を避けるための最小限です。

## 13.1 `std::thread` — スレッドの生成と終了

```cpp
#include <iostream>
#include <thread>

void worker(int id)
{
  std::cout << "スレッド " << id << " が実行\n";
}

int main()
{
  std::thread t1(worker, 1);
  std::thread t2(worker, 2);

  t1.join();   // t1 の完了を待つ
  t2.join();   // t2 の完了を待つ

  std::cout << "両スレッド終了\n";
  return 0;
}
```

```
スレッド 1 が実行
スレッド 2 が実行
両スレッド終了
```

`std::thread` にはコンストラクタに関数（または関数オブジェクト、ラムダ）と引数を渡します。
スレッドはすぐに実行開始します。

メインスレッドが先に終わっても構いませんが、`std::thread` オブジェクトのデストラクタが
`join()` も `detach()` も済んでいない状態で呼ばれると、**`std::terminate` を呼んでプログラムを強制終了します。**

```cpp
#include <iostream>
#include <thread>

void worker() { std::cout << "スレッド実行\n"; }

int main()
{
  std::thread t(worker);
  // join も detach もせずに main を抜ける
  return 0;  // ← t のデストラクタが std::terminate を呼ぶ
}
```

```
terminate called without an active exception
```

### `join()` と `detach()`

| 方法 | 動作 | 用途 |
| --- | --- | --- |
| `.join()` | 完了を待つ。スレッドの戻り値・例外を同期 | ドリルでほぼこれ |
| `.detach()` | 独立させる。メインが先に終わってもスレッド続行 | デーモンスレッド |

両者とも呼んだあとは `.joinable()` は `false` になります。
**2 回呼ぶと例外が飛ぶので気を付けてください。**

## 13.2 データレース — 保護なしで共有変数を書く

最初に注意を 1 つ。**データレースは「書けば必ず現れる」ものではありません。**
これがこのバグのいちばん厄介な性質なので、まず現れない例から見ます。

```cpp
#include <iostream>
#include <thread>
#include <vector>

int counter = 0;

void increment()
{
  for (int i = 0; i < 100000; ++i) {
    ++counter;                 // 保護なしで共有変数を書いている
  }
}

int main()
{
  std::vector<std::thread> threads;
  for (int i = 0; i < 5; ++i) {
    threads.emplace_back(increment);
  }
  for (auto & t : threads) {
    t.join();
  }
  std::cout << "結果:   " << counter << "\n";
  std::cout << "期待値: 500000\n";
  return 0;
}
```

```bash
$ g++ -std=c++17 -Wall -Wextra -pthread race1.cpp -o race1
$ for i in 1 2 3 4 5 6 7 8; do ./race1 | head -1; done
結果:   500000
結果:   500000
結果:   500000
結果:   500000
結果:   500000
結果:   500000
結果:   500000
結果:   500000
```

**8 回とも正解が出ました。** `-O2` を付けても、`-pthread` を外しても同じでした
（12 コアのマシンで実測）。

このコードは**壊れています**。それでも正しい答えが出るのは、
1 スレッドが 100000 回を回り終わるのに 0.5 ミリ秒もかからず、
`threads.emplace_back` でスレッドを 1 本ずつ作っている間に
**先のスレッドが終わってしまう**からです。競合する相手がいなければ競合しません。

**「動いたから正しい」が成り立たない**という、この章でいちばん重要な事実がここにあります。

### 本当に競合させる

スレッドを揃えてから一斉にスタートさせ、仕事量を増やします。

```cpp
#include <atomic>
#include <iostream>
#include <thread>
#include <vector>

int counter = 0;
std::atomic<bool> go{false};

void increment()
{
  while (!go) { }                    // 全スレッドが揃うまで待つ
  for (int i = 0; i < 1000000; ++i) {
    ++counter;
  }
}

int main()
{
  std::vector<std::thread> threads;
  for (int i = 0; i < 8; ++i) {
    threads.emplace_back(increment);
  }
  go = true;                          // 一斉にスタート
  for (auto & t : threads) {
    t.join();
  }
  std::cout << "結果:   " << counter << "\n";
  std::cout << "期待値: " << 8 * 1000000 << "\n";
  return 0;
}
```

```bash
$ g++ -std=c++17 -Wall -Wextra -pthread race2.cpp -o race2
$ for i in 1 2 3 4 5; do ./race2 | head -1; done
結果:   1352695
結果:   1408128
結果:   1427199
結果:   1436394
結果:   1467341
```

**期待値 8000000 に対して 140 万前後。8 割以上の増分が消えています。**
しかも毎回違う値です。

`++counter` は 1 つの動作に見えますが、機械語では
`load` → `add` → `store` の 3 ステップです。
2 つのスレッドが同じ値を `load` して、両方が同じ値に +1 して `store` すると、
**2 回増えるべきものが 1 回しか増えません。** それが大量に起きています。

### 検出する — ThreadSanitizer

「たまたま動く」バグを目視で探すのは無理です。**ツールを使います。**

```bash
$ g++ -std=c++17 -fsanitize=thread -g -pthread race2.cpp -o race2_ts
$ ./race2_ts
==================
WARNING: ThreadSanitizer: data race (pid=134773)
  Write of size 4 at 0x591893f74154 by thread T6:
    #0 increment() race.cpp:13
  Previous read of size 4 at 0x591893f74154 by thread T7:
    ...
```

**`-fsanitize=thread` は、実際に競合が現れなくても検出します。**
最初の `race1.cpp`（8 回とも正解が出たコード）でも報告されます。
「テストが通ったから大丈夫」ではなく、**TSan に通したから大丈夫**と言えるようにしてください。

実行速度は 5〜15 倍遅くなるので、本番ビルドには入れません。CI で回すのが定石です。

## 13.3 `std::mutex` と `std::lock_guard` — 排他制御

データレースを防ぐには、共有変数への access を一度に 1 スレッドだけに限ります。

```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <vector>

int counter = 0;
std::mutex counter_mutex;

void increment()
{
  for (int i = 0; i < 100000; ++i) {
    std::lock_guard<std::mutex> lock(counter_mutex);
    counter++;
  }
}

int main()
{
  std::vector<std::thread> threads;
  for (int i = 0; i < 5; ++i) {
    threads.emplace_back(increment);
  }
  for (auto & t : threads) {
    t.join();
  }

  std::cout << "結果: " << counter << "\n";
  std::cout << "期待値: 500000\n";
  return 0;
}
```

```
結果: 500000
期待値: 500000
```

`std::lock_guard` は 2 章の RAII パターンです。
コンストラクタで `mutex` をロックし、デストラクタで自動的に unlock します。

`{` で RAII スコープに入った時点でロック、`}` を抜ける時点で unlock。
例外が飛んでもデストラクタは呼ばれるので、**デッドロック（自分がロックしたままプログラムが止まる）も防げます。**

## 13.4 `std::atomic` — ロック不要な原子操作

`int` 1 個のカウンタなら `mutex` より `atomic` のほうが軽いです。

```cpp
#include <iostream>
#include <thread>
#include <atomic>
#include <vector>

std::atomic<int> counter(0);

void increment()
{
  for (int i = 0; i < 100000; ++i) {
    counter++;  // atomic なので thread-safe
  }
}

int main()
{
  std::vector<std::thread> threads;
  for (int i = 0; i < 5; ++i) {
    threads.emplace_back(increment);
  }
  for (auto & t : threads) {
    t.join();
  }

  std::cout << "結果: " << counter << "\n";
  std::cout << "期待値: 500000\n";
  return 0;
}
```

```
結果: 500000
期待値: 500000
```

`std::atomic<T>` は `T` をラップして、すべての操作を**アトミック**（不可分）にします。
`++` や `=` が「読んで→書く」ではなく 1 ステップの CPU 命令になるため、データレースが起きません。

ただ `mutex` より応用範囲が狭いです。複数の変数を一度にロックしたい場合は `mutex` を使います。

## 13.5 `std::promise` / `std::future` — 未来の値

スレッド間で値を受け渡すには、`promise` と `future` を使います。

```cpp
#include <iostream>
#include <thread>
#include <future>
#include <chrono>

int main()
{
  std::promise<int> prom;
  std::future<int> fut = prom.get_future();

  std::thread worker([&prom]() {
    std::cout << "ワーカー: 計算中...\n";
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    prom.set_value(42);
    std::cout << "ワーカー: 完了\n";
  });

  std::cout << "メイン: 結果を待機\n";
  int result = fut.get();  // ブロック
  std::cout << "メイン: 結果 = " << result << "\n";

  worker.join();
  return 0;
}
```

```
メイン: 結果を待機
ワーカー: 計算中...
ワーカー: 完了
メイン: 結果 = 42
```

**`future` は「値がまだ無いが、後で来る」という約束です。**

- `promise` は「約束を作る側」。`set_value()` で値を設定します
- `future` は「約束を待つ側」。`get()` で結果を受け取ります（ブロック）

### `wait_for` でタイムアウト

```cpp
#include <iostream>
#include <thread>
#include <future>
#include <chrono>

int main()
{
  std::promise<int> prom;
  std::future<int> fut = prom.get_future();

  std::thread worker([&prom]() {
    std::cout << "ワーカー: 長く待つ\n";
    std::this_thread::sleep_for(std::chrono::seconds(10));
  });

  std::cout << "メイン: 2秒待つ\n";
  auto status = fut.wait_for(std::chrono::seconds(2));

  if (status == std::future_status::ready) {
    std::cout << "完了: " << fut.get() << "\n";
  } else if (status == std::future_status::timeout) {
    std::cout << "タイムアウト\n";
  } else if (status == std::future_status::deferred) {
    std::cout << "遅延実行\n";
  }

  worker.join();
  return 0;
}
```

```
メイン: 2秒待つ
ワーカー: 長く待つ
タイムアウト
```

`wait_for` は `std::future_status` enum で状態を返します。

| 戻り値 | 意味 |
| --- | --- |
| `ready` | 値が揃っている |
| `timeout` | 時間切れ（値はまだ来てない） |
| `deferred` | まだ実行されていない（async で `std::launch::deferred` の場合） |

ROS 2 のコードで `wait_for` は**デッドロック避けのタイムアウト**として使われます。

## 13.6 デッドロック — Executor での罠

さて、ここからがドリルで実際に踏む落とし穴です。

**ドリルでは rclcpp の Executor がスレッドを管理しており、あなたのコールバックはその上で走ります。**
コールバックの中から `future.wait_for()` を呼ぶときには注意が必要です。

### 実例：課題 13

```cpp
// solutions/13_executors/src/relay_with_service.cpp（抜粋）

void RelayWithService::trigger_callback(const std_msgs::msg::Int32 & msg)
{
  auto request = std::make_shared<AddTwoInts::Request>();
  request->a = msg.data;
  request->b = msg.data;

  auto future = client_->async_send_request(request);

  if (future.wait_for(2s) != std::future_status::ready) {
    RCLCPP_ERROR(this->get_logger(), "add_two_ints の応答がタイムアウト");
    return;
  }

  std_msgs::msg::Int32 out;
  out.data = future.get()->sum;
  publisher_->publish(out);
}
```

このコード自体は安全です。理由は、これが書かれた時点で、
**`subscription_group_` と `client_group_` が別々の `MutuallyExclusive` で、
`MultiThreadedExecutor` で実行されている**からです。

#### ヘッダファイルより

```cpp
// drill/relay_with_service.hpp（抜粋）

RelayWithService::RelayWithService()
: Node("relay_with_service")
{
  subscription_group_ = this->create_callback_group(
    rclcpp::CallbackGroupType::MutuallyExclusive);
  client_group_ = this->create_callback_group(
    rclcpp::CallbackGroupType::MutuallyExclusive);

  // ...subscription を subscription_group_ で、
  // client を client_group_ で作成
}
```

### デッドロックの原理

もし両方が**同じ `MutuallyExclusive` callback group** に属していたら？

```
スレッドプール（1スレッド）
  ↓
  subscription_group （MutuallyExclusive）
    ├─ trigger_callback が実行中
    │   └─ future.wait_for() で待機...
    │       （client の応答を待つ）
    │
    └─ client の完了ハンドラは実行できない
        （グループがロックされている）
```

`trigger_callback` が完了コールバックを待っているのに、そのコールバックが同じグループで走っていて、
グループは「`trigger_callback` が終わるまで」他のコールバックを実行しません。

**永遠に待ちます。それがデッドロックです。**

### 解決：別々のグループ

ドリルの解答では 2 つの `MutuallyExclusive` グループに分け、
`MultiThreadedExecutor` で**複数スレッドを使う**ことで避けています。

```cpp
subscription_group_ = this->create_callback_group(
  rclcpp::CallbackGroupType::MutuallyExclusive);  // スレッド 1
client_group_ = this->create_callback_group(
  rclcpp::CallbackGroupType::MutuallyExclusive);  // スレッド 2
```

2 つのスレッドがいれば、片方が待機している間にもう片方が client 完了ハンドラを走せます。

### C++ だけで見るデッドロック

promise/future で同じパターンを再現します。

```cpp
#include <iostream>
#include <thread>
#include <future>
#include <chrono>

// 1つのワーカースレッド が、自分自身に set_value できない
std::promise<int> shared_prom;

void worker()
{
  std::cout << "ワーカー: set_value する必要あり\n";
  std::cout << "ワーカー: でも future.wait_for() で待機中...\n";
  // ← ここが問題。このスレッドは future に拘束されている
  // だから set_value を実行できない
}

int main()
{
  std::future<int> fut = shared_prom.get_future();

  std::thread w(worker);

  // set_value を呼びたいが、worker スレッドが持っていない
  // （メインスレッドが持っている）

  w.join();
  return 0;
}
```

実務では、**「コールバックの中で `future` を待つなら、そのコールバックが別スレッド池にいることを確認する」**が基本です。

詳しくは [rclcpp の設計思想](../rclcpp-の設計思想.md) 5 章「コールバックグループ」を読んでください。

## 手元で試す

**並行性のすべての概念を 1 つのプログラムで見てください。**

```cpp
// concurrency.cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <atomic>
#include <future>
#include <vector>
#include <chrono>

void example_join_detach()
{
  std::cout << "\n-- 1. join と detach\n";

  auto worker = []() { std::cout << "  ワーカー実行\n"; };

  std::thread t1(worker);
  t1.join();
  std::cout << "  join 後: joinable = " << t1.joinable() << "\n";

  std::thread t2(worker);
  t2.detach();
  std::cout << "  detach 後: joinable = " << t2.joinable() << "\n";
}

void example_data_race()
{
  std::cout << "\n-- 2. データレース\n";

  int counter = 0;
  std::atomic<bool> go{false};
  auto inc = [&counter, &go]() {
    while (!go) { }                    // 全スレッドを揃えてから走らせる
    for (int i = 0; i < 1000000; ++i) {
      ++counter;
    }
  };

  std::vector<std::thread> threads;
  for (int i = 0; i < 8; ++i) {
    threads.emplace_back(inc);
  }
  go = true;
  for (auto & t : threads) {
    t.join();
  }

  std::cout << "  結果: " << counter << " (期待: " << 8 * 1000000 << ")\n";
}

void example_mutex()
{
  std::cout << "\n-- 3. mutex\n";

  int counter = 0;
  std::mutex m;

  auto inc = [&counter, &m]() {
    for (int i = 0; i < 10000; ++i) {
      std::lock_guard<std::mutex> lock(m);
      counter++;
    }
  };

  std::vector<std::thread> threads;
  for (int i = 0; i < 3; ++i) {
    threads.emplace_back(inc);
  }
  for (auto & t : threads) {
    t.join();
  }

  std::cout << "  結果: " << counter << " (期待: 30000)\n";
}

void example_atomic()
{
  std::cout << "\n-- 4. atomic\n";

  std::atomic<int> counter(0);

  auto inc = [&counter]() {
    for (int i = 0; i < 10000; ++i) {
      counter++;
    }
  };

  std::vector<std::thread> threads;
  for (int i = 0; i < 3; ++i) {
    threads.emplace_back(inc);
  }
  for (auto & t : threads) {
    t.join();
  }

  std::cout << "  結果: " << counter << " (期待: 30000)\n";
}

void example_promise()
{
  std::cout << "\n-- 5. promise/future\n";

  std::promise<int> prom;
  std::future<int> fut = prom.get_future();

  std::thread w([&prom]() {
    std::this_thread::sleep_for(std::chrono::milliseconds(50));
    prom.set_value(123);
  });

  int result = fut.get();
  std::cout << "  結果: " << result << "\n";

  w.join();
}

void example_wait_for()
{
  std::cout << "\n-- 6. wait_for\n";

  std::promise<int> prom;
  std::future<int> fut = prom.get_future();

  std::cout << "  1秒待つ...\n";
  auto status = fut.wait_for(std::chrono::seconds(1));

  if (status == std::future_status::timeout) {
    std::cout << "  タイムアウト\n";
  }
}

int main()
{
  std::cout << "=== 並行性デモ ===\n";

  example_join_detach();
  example_data_race();
  example_mutex();
  example_atomic();
  example_promise();
  example_wait_for();

  std::cout << "\n完了\n";
  return 0;
}
```

**予想: 各例でどの出力が出るか。特に:**

1. `join` 後の `joinable()` は 0 か 1 か
2. データレースの結果は 8000000 か、それより小さいか
3. mutex と atomic の結果は同じか

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -pthread concurrency.cpp -o concurrency && ./concurrency
```

**5 回続けて実行してください。** データレースの行だけが毎回違う値になり、
mutex と atomic の行は毎回同じ値になることを確認します。

確認したら 3 つの変更をしてください。

**① スタートを揃えるのをやめる。**

`while (!go) { }` の行と `go = true;` の行を消して、スレッド数を 8 から 3 に、
繰り返しを 1000000 から 10000 に戻してください。

```cpp
  auto inc = [&counter]() {
    for (int i = 0; i < 10000; ++i) {
      ++counter;
    }
  };
```

**今度は毎回正しい 30000 が出ます。** 13.2 節で見たのと同じ現象です。
コードは壊れたままなのに、結果が正しくなります。
**「動いたから正しい」がなぜ成り立たないか**を、自分の手で 2 回確認してください。

**② `-fsanitize=thread` を付ける。**

①の「毎回正しい値が出る」状態のまま、TSan を通してください。

```bash
g++ -std=c++17 -g -pthread -fsanitize=thread concurrency.cpp -o concurrency_ts && ./concurrency_ts
```

**結果が正しくても `WARNING: ThreadSanitizer: data race` が出ます。**
これが「テストを通す」と「正しさを確かめる」の違いです。

（mutex 版と atomic 版では報告されないことも確認してください。
TSan は「保護されていない同時アクセス」を見ているので、正しく保護されていれば黙ります。）

**③ `wait_for` の例で `promise` を値で作る:**

```cpp
std::promise<int> prom;
std::future<int> fut = prom.get_future();

std::thread w([prom = std::move(prom)]() mutable {
  // ...
});
```

これは promise の所有権をスレッドに移します。メインスレッドは set_value できなくなるため、
future は永遠に待ちます。タイムアウトが確実に起きることを確認してください。

## つまずきポイント

**`error: std::thread::thread(const std::thread&)' is deleted`**

`std::thread` をコピーしようとしています。スレッドはムーブセマンティクスのみです。
`std::vector<std::thread>` に追加するときは `emplace_back` を使ってください。

**`error: call to 'lock_guard::lock_guard(const lock_guard&)' is deleted`**

`lock_guard` をコピーしています。RAII オブジェクトなので、コピーできません。
スコープの中だけで使ってください。

**異常終了 `terminate called`**

3 つの定番があります。

1. `std::thread` をデストラクト時に `join` も `detach` もしていない
2. `std::lock_guard` が 2 回 lock しようとした（同じ mutex 上で）
3. `future.get()` を 2 回呼んだ

すべて「順序を間違えた」または「ロジックの穴」です。
`gdb` でスタックトレースを見ると、どこで止まっているか分かります。

**`std::bad_weak_ptr` — `weak_ptr` から `lock()` が失敗した**

所有者がいない `weak_ptr` から `shared_ptr` に昇格しようとしました。
`lock()` の戻り値が `nullptr` でないか確認してください。

**プログラムが突然止まる（デッドロック）**

タイムアウトなしで `future.wait()` / `future.get()` を呼んでいませんか。
またはコールバックの中から `wait_for(long_time)` を呼んでいませんか。
「このスレッド上でコールバックの完了を待つ → コールバックが同じスレッド上で走る」
という循環参照です。

デッドロック検出は難しいので、**タイムアウトを常に付ける**が予防策です。
