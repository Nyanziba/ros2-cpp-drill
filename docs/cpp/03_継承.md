# 3. 継承 — `rclcpp::Node` を継承するとはどういうことか

> **この章のねらい**: ドリルの 15 課題すべてが、この 1 行から始まります。
>
> ```cpp
> class MinimalPublisher : public rclcpp::Node
> ```
>
> この行が読めないと、「なぜ `create_publisher` を自分で書いていないのに呼べるのか」
> 「`: Node("minimal_publisher")` は何なのか」「なぜ `std::make_shared<MinimalPublisher>()` で作るのか」が
> すべて謎のままになります。
> この章は 1 行を左から右まで完全に読み下すことから始めて、
> **仮想関数**、**仮想デストラクタ**、**コピー禁止**、**スライシング** まで進みます。
> ドリルで最も使う C++ の機能なので、他の章より長めです。

## 3.1 1 行を読み下す

```cpp
class MinimalPublisher : public rclcpp::Node
```

| 部分 | 意味 |
| --- | --- |
| `class MinimalPublisher` | `MinimalPublisher` という名前のクラスを定義する |
| `:` | 「以下を継承する」。**2 章の初期化子リストの `:` とは別物** |
| `public` | **継承のしかた**。基底クラスの `public` メンバを、派生クラスでも `public` のままにする |
| `rclcpp::Node` | 基底クラス（base class）。`rclcpp` 名前空間の `Node` |

用語を揃えます。

- **基底クラス（base class）** = `rclcpp::Node`。親クラス、スーパークラスとも
- **派生クラス（derived class）** = `MinimalPublisher`。子クラス、サブクラスとも

**`:` が 2 種類あることに注意してください。** 混ざると読めなくなります。

```cpp
class MinimalPublisher : public rclcpp::Node    // ← ① 継承の :（クラス宣言のところ）
{
  MinimalPublisher();
};

MinimalPublisher::MinimalPublisher()
: Node("minimal_publisher"), count_(0)          // ← ② 初期化子リストの :（定義のところ）
{
}
```

① は「何を継承するか」、② は「基底クラスとメンバをどう初期化するか」です。
別の場所に、別の目的で出てきます。

## 3.2 継承すると何が起きるか

継承した派生クラスは、**基底クラスのメンバを自分のものとして持ちます。**

```cpp
#include <iostream>
#include <string>

class Base
{
public:
  explicit Base(std::string name) : name_(std::move(name)) {}

  void greet() const { std::cout << "こんにちは、" << name_ << "\n"; }
  const std::string & name() const { return name_; }

private:
  std::string name_;
};

class Derived : public Base
{
public:
  Derived() : Base("派生") {}

  void work() const
  {
    greet();                                    // 基底のメンバ関数がそのまま呼べる
    std::cout << name() << " が働く\n";
  }
};

int main()
{
  Derived d;
  d.work();
  d.greet();      // 外からも呼べる（public 継承なので）
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/Wo57fdPn7)

```
こんにちは、派生
派生 が働く
こんにちは、派生
```

`Derived` は `greet()` を 1 行も書いていませんが呼べます。これが継承です。

ドリンで言えば、`MinimalPublisher` は `create_publisher` も `get_logger` も
`create_wall_timer` も書いていませんが、全部 `rclcpp::Node` から来ています。

```cpp
publisher_ = this->create_publisher<std_msgs::msg::String>("topic", 10);
//            ^^^^^^^^^^^^^^^^^^^^^ rclcpp::Node のメンバ関数
RCLCPP_INFO(this->get_logger(), "Publishing: '%s'", message.data.c_str());
//                ^^^^^^^^^^ これも rclcpp::Node のメンバ関数
```

**`this->` が付いているのは、これらが「自分で書いていないメンバ」だと分かりやすくするため**でもあります
（2 章のとおり省略可能です）。

`rclcpp::Node` が何を提供しているかは、ヘッダを直接見るのが確実です。

```bash
grep -n "^  [a-z].*(" /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp | head -40
```

### `private` メンバは継承しても見えない

継承しても、基底クラスの `private` メンバには触れません。

```cpp
class Derived : public Base
{
public:
  void bad() { std::cout << name_; }   // エラー
};
```

```
error: ‘std::string Base::name_’ is private within this context
```

`rclcpp::Node` も、実データは全部 `private` です。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp:1633 以降
private:
  RCLCPP_DISABLE_COPY(Node)

  rclcpp::node_interfaces::NodeBaseInterface::SharedPtr node_base_;
  rclcpp::node_interfaces::NodeGraphInterface::SharedPtr node_graph_;
  // ...
```

だから `MinimalPublisher` から `node_base_` は触れません。
触りたければ `public` な `get_node_base_interface()` を使います。
**「データは private、操作は public」が守られているので、
継承しても基底クラスの内部を壊せません。**

### `protected` — 派生クラスにだけ見せる

3 つ目の公開範囲が `protected` です。「外からは見えないが、派生クラスからは見える」。

| 指定 | 外部から | 派生クラスから |
| --- | --- | --- |
| `public` | ○ | ○ |
| `protected` | × | ○ |
| `private` | × | × |

`rclcpp::Node` にも `protected` セクションがあります。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp:1620
protected:
  /// Construct a sub-node, which will extend the namespace of all entities created with it.
  Node(
    const Node & other,
    const std::string & sub_namespace);
```

サブノードを作るためのコンストラクタで、**`Node` を継承したクラスからしか呼べません。**
外部の誰かが勝手にサブノードを作ることを防いでいます。

## 3.3 基底クラスのコンストラクタは必ず呼ばれる

派生クラスを作ると、**基底クラスのコンストラクタが先に走ります。**

```cpp
#include <iostream>

class Base
{
public:
  Base() { std::cout << "Base()\n"; }
  ~Base() { std::cout << "~Base()\n"; }
};

class Derived : public Base
{
public:
  Derived() { std::cout << "Derived()\n"; }
  ~Derived() { std::cout << "~Derived()\n"; }
};

int main()
{
  Derived d;
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/M7x91hcoP)

```
Base()
Derived()
~Derived()
~Base()
```

**生成は基底 → 派生、破棄は派生 → 基底。** 逆順です。

理にかなっています。派生クラスのコンストラクタは基底クラスのメンバを使えるので、
基底が先に完成していなければなりません。破棄はその逆で、
派生が基底を使い終わってから基底を壊します。

### 引数が必要な基底クラスは、初期化子リストで呼ぶ

上の例では `Base()` に引数がなかったので、自動で呼ばれました。
**引数が必要な場合は、自分で書かなければなりません。**

`rclcpp::Node` のコンストラクタを見てください。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp:91
explicit Node(
  const std::string & node_name,
  const NodeOptions & options = NodeOptions());
```

**引数なしのコンストラクタがありません。** ノード名は必須です（当然です。名前のないノードは作れません）。
だから初期化子リストで渡すしかありません。

```cpp
MinimalPublisher::MinimalPublisher()
: Node("minimal_publisher"), count_(0)
//^^^^^^^^^^^^^^^^^^^^^^^^^ 基底クラスのコンストラクタ呼び出し
{
}
```

`Node(...)` を書き忘れると、コンパイラは「引数なしの `Node()` を呼ぼう」として失敗します。

```
error: no matching function for call to ‘rclcpp::Node::Node()’
note: candidate: ‘rclcpp::Node::Node(const std::string&, const rclcpp::NodeOptions&)’
note:   candidate expects 2 arguments, 0 provided
```

**「candidate expects 2 arguments, 0 provided」が出たら、基底クラスの呼び出しを忘れています。**

書く順番は、**基底クラスを先、メンバを後**です。実際の初期化順もそうなります。
`-Wall` を付けていれば、逆に書くと `-Wreorder` で警告が出ます。

### `NodeOptions` を素通しする作法

課題 14・15 のコンストラクタはこの形です。

```cpp
// solutions/15_composition/src/composable_talker.cpp
ComposableTalker::ComposableTalker(const rclcpp::NodeOptions & options)
: Node("composable_talker", options), count_(0)
```

受け取った `options` を**そのまま基底に渡しています**。ここを

```cpp
: Node("composable_talker")     // options を捨ててしまった
```

と書くと、コンパイルは通り、`ros2 run` でも動き、**コンポーネントとして載せたときだけ壊れます。**
`use_intra_process_comms` やパラメータの上書きが `options` に入っていて、
それを捨てているからです。

課題 14 のテストはこれを検出するように作られています。
「コンパイルが通るのに落ちる」タイプなので、エラーメッセージからは原因が分かりません。
**引数で受け取った `NodeOptions` は必ず基底に素通しする**、と型で覚えてください。

## 3.4 仮想関数 — 派生クラスに処理を差し替えさせる

ここまでは「基底の機能を借りる」だけの継承でした。
継承のもう 1 つの用途は、**基底クラスが定めた枠に派生クラスが中身を入れる**ことです。

```cpp
#include <iostream>
#include <memory>
#include <vector>

class Shape
{
public:
  virtual ~Shape() = default;                  // 3.5 節で説明します
  virtual double area() const = 0;             // = 0 は「中身は派生が書く」
  virtual const char * name() const { return "図形"; }   // 既定の実装あり
};

class Circle : public Shape
{
public:
  explicit Circle(double r) : r_(r) {}
  double area() const override { return 3.14159 * r_ * r_; }
  const char * name() const override { return "円"; }
private:
  double r_;
};

class Square : public Shape
{
public:
  explicit Square(double s) : s_(s) {}
  double area() const override { return s_ * s_; }
  // name() は override していない → 基底の "図形" が使われる
private:
  double s_;
};

int main()
{
  std::vector<std::unique_ptr<Shape>> shapes;
  shapes.push_back(std::make_unique<Circle>(1.0));
  shapes.push_back(std::make_unique<Square>(2.0));

  for (const auto & s : shapes) {
    std::cout << s->name() << " の面積 = " << s->area() << "\n";
  }
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/YWd1PWvfa)

```
円 の面積 = 3.14159
図形 の面積 = 4
```

**`Shape` のポインタしか持っていないのに、`Circle` の `area()` と `Square` の `area()` が
それぞれ呼ばれています。** これが仮想関数です。

用語を整理します。

| 書き方 | 呼び名 | 意味 |
| --- | --- | --- |
| `virtual double area() const = 0;` | **純粋仮想関数** | 中身が無い。派生クラスは必ず実装しなければならない |
| `virtual const char * name() const { ... }` | **仮想関数** | 既定の実装がある。派生クラスは差し替えてもよい |
| `double area() const override` | **オーバーライド** | 基底の仮想関数を差し替える |

純粋仮想関数を 1 つでも持つクラスを**抽象クラス**といい、**インスタンスを作れません。**

```cpp
Shape s;   // エラー
```

```
error: cannot declare variable ‘s’ to be of abstract type ‘Shape’
note:   because the following virtual functions are pure within ‘Shape’:
note:     ‘virtual double Shape::area() const’
```

「インタフェースだけ決めて実装は差し替えられるようにする」ための道具です。

### `override` は必ず書く

`override` は無くても動きます。**書いてください。**

`override` は「これは基底の仮想関数を差し替えているつもりだ」という宣言で、
**そうでなければコンパイルエラーにする**という指示です。

```cpp
class Circle : public Shape
{
public:
  double area() override { return 3.14159 * r_ * r_; }   // const を書き忘れた
};
```

```
error: ‘double Circle::area()’ marked ‘override’, but does not override
```

`override` を書かないとどうなるか。**エラーになりません。**
`area() const`（基底）と `area()`（派生）は別のシグネチャなので、
「オーバーライドしていない、まったく新しい関数」として通ります。
そして `Shape *` 経由で呼ぶと基底の `area() const` が呼ばれ、
純粋仮想なので… 今回は抽象クラスのままになってコンパイルは落ちますが、
基底に既定実装がある場合は**静かに間違った関数が呼ばれます。**

`const` の付け忘れ、引数の型の 1 文字違い、`&` の有無。
これらは全部「別の関数」になります。`override` はそれを機械的に検出する唯一の手段です。

同様に、**これ以上派生させたくない**場合は `final` を付けます。

```cpp
double area() const override final { ... }
```

### ROS 2 の中の純粋仮想関数

ドリルでは自分で仮想関数を書く場面がほとんどありませんが（`override` は
`tools/drill_harness.hpp` に 2 箇所だけ）、**ROS 2 のエコシステムはこれで動いています。**

| 何 | 基底クラス | 派生クラスを書くのは |
| --- | --- | --- |
| プランナプラグイン | `mbf_simple_core::SimplePlanner` | 経路計画アルゴリズムの実装者 |
| コントローラプラグイン | `mbf_simple_core::SimpleController` | 追従制御の実装者 |
| ハードウェアインタフェース | `hardware_interface::SystemInterface` | ロボットの実機ドライバの実装者 |
| ros2_control のコントローラ | `controller_interface::ControllerInterface` | 制御器の実装者 |
| Executor | `rclcpp::Executor` | rclcpp 自身（`SingleThreadedExecutor` など） |

`pluginlib` が実行時に共有ライブラリを `dlopen` して、
**基底クラスのポインタとしてインスタンスを受け取る**のがこの仕組みです。
上の `std::vector<std::unique_ptr<Shape>>` と構造は同じで、
`Circle` に当たるクラスが実行時に決まるだけです。

`move_base_flex` のプランナ／コントローラのプラグインがまさにこの形なので、
**自律移動のコードを読む段階になったらこの節に戻ってきてください。**

### 仮想関数はどう実現されているか

知らなくても書けますが、知っていると納得しやすいので触れます。

仮想関数を持つクラスのオブジェクトには、**vptr** という隠しポインタが 1 つ足されます。
それが指す先が **vtable** で、「この型の `area()` はどの関数か」という表です。

```
Circle のオブジェクト          Circle の vtable
+----------------+           +---------------------------+
| vptr           |─────────▶ | ~Circle                   |
+----------------+           | Circle::area              |
| r_ (double)    |           | Circle::name              |
+----------------+           +---------------------------+
```

`s->area()` は「`s` の vptr を辿って、表の 2 番目を呼ぶ」という間接呼び出しになります。
確かめられます。

```cpp
#include <iostream>
struct NoVirtual { double x; };
struct WithVirtual { virtual ~WithVirtual() = default; double x; };

int main()
{
  std::cout << sizeof(NoVirtual) << " " << sizeof(WithVirtual) << "\n";
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/P6vhPe6MP)

```
8 16
```

`double` 1 個 = 8 バイトのはずが、仮想関数を持つと 16 バイトになりました。
vptr の 8 バイトが足されています。

だから **`virtual` は無料ではありません。**
オブジェクトが 8 バイト増え、呼び出しが 1 段間接になり、インライン展開されにくくなります。
とはいえ、この差が問題になるのは「1 秒に何千万回呼ぶ」規模の話です。
プラグイン境界のような、1 制御周期に数回の呼び出しでは無視できます。

## 3.5 仮想デストラクタ — 忘れると静かにリークする

`Shape` の例で `virtual ~Shape() = default;` と書いていました。
これを外すと何が起きるか、実際に見ます。

```cpp
#include <iostream>
#include <memory>

class Base
{
public:
  ~Base() { std::cout << "~Base()\n"; }        // virtual を付けていない
};

class Derived : public Base
{
public:
  ~Derived() { std::cout << "~Derived()\n"; }
};

int main()
{
  std::unique_ptr<Base> p = std::make_unique<Derived>();
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/Pqhaf8fqW)

```
~Base()
```

**`~Derived()` が呼ばれていません。**
`Derived` が確保していた資源は、これで永久に解放されません。

`virtual ~Base()` にすると直ります。

```
~Derived()
~Base()
```

規則は単純です。**継承される可能性があるクラスのデストラクタは `virtual` にする。**
`rclcpp::Node` も当然そうしています。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp:109
virtual ~Node();
```

これがあるから、`std::shared_ptr<rclcpp::Node>` として保持している
`MinimalPublisher` が破棄されるときに、`~MinimalPublisher()` が正しく呼ばれます。
`rclcpp::spin(std::make_shared<MinimalPublisher>())` が成り立つのはこのおかげです。

### `shared_ptr` は例外的に助けてくれる

細かい話ですが、混乱の元なので明示します。

`std::shared_ptr` は、**作ったときの型**のデストラクタを覚えています。

```cpp
std::shared_ptr<Base> p = std::make_shared<Derived>();   // virtual なしでも ~Derived() が呼ばれる
std::unique_ptr<Base> q = std::make_unique<Derived>();   // ~Base() だけ
```

`shared_ptr` は型消去された deleter を内部に持つのでこうなります。
**ただしこれに頼らないでください。** `unique_ptr` では効きませんし、
生ポインタの `delete` でも効きません。`virtual ~` を書くのが正解です。

## 3.6 コピー禁止とスライシング — なぜ全部 `shared_ptr` なのか

`rclcpp::Node` の `private` セクションの 1 行目を見てください。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/node.hpp:1634
private:
  RCLCPP_DISABLE_COPY(Node)
```

このマクロの中身はこうです。

```cpp
// /opt/ros/jazzy/include/rclcpp/rclcpp/macros.hpp:26
#define RCLCPP_DISABLE_COPY(...) \
  __VA_ARGS__(const __VA_ARGS__ &) = delete; \
  __VA_ARGS__ & operator=(const __VA_ARGS__ &) = delete;
```

展開すると

```cpp
Node(const Node &) = delete;
Node & operator=(const Node &) = delete;
```

**`rclcpp::Node` はコピーできません。** 2 章で見た `= delete` です。

当然です。ノードをコピーしたら DDS の participant が 2 つになるのか、
同じ名前のノードが 2 つ現れるのか、意味が決まりません。

そして `MinimalPublisher` は `Node` を継承しているので、
**`MinimalPublisher` も自動的にコピー不能になります。**
コピーコンストラクタは自動生成されようとして、基底のコピーが `delete` されているので失敗します。

```cpp
MinimalPublisher a;
MinimalPublisher b = a;    // エラー
```

```
error: use of deleted function ‘MinimalPublisher::MinimalPublisher(const MinimalPublisher&)’
note: ‘MinimalPublisher::MinimalPublisher(const MinimalPublisher&)’ is implicitly deleted
      because the default definition would be ill-formed
error: use of deleted function ‘rclcpp::Node::Node(const rclcpp::Node&)’
```

**これが「なぜ ROS 2 のコードは何でも `shared_ptr` なのか」の直接の答えです。**
値として持ち回せないので、ポインタで扱うしかありません。

```cpp
rclcpp::spin(std::make_shared<MinimalPublisher>());
```

### スライシング — コピーできてしまう場合の罠

もしコピーが禁止されていなかったら何が起きるか。これも知っておく価値があります。

```cpp
#include <iostream>

class Base
{
public:
  virtual const char * name() const { return "Base"; }
};

class Derived : public Base
{
public:
  const char * name() const override { return "Derived"; }
  int extra_ = 42;
};

void by_value(Base b)          // ← 値で受けている
{
  std::cout << "by_value: " << b.name() << "\n";
}

void by_ref(const Base & b)    // ← const 参照で受けている
{
  std::cout << "by_ref:   " << b.name() << "\n";
}

int main()
{
  Derived d;
  by_value(d);
  by_ref(d);
  return 0;
}
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/MP6cbrKKP)

```
by_value: Base
by_ref:   Derived
```

**値で受けると `Derived` の部分が切り落とされて `Base` になります。**
これを**スライシング（object slicing）** といいます。
`extra_` も消え、仮想関数も基底のものが呼ばれます。

コンパイルは通り、警告も出ません。静かに間違った動作になります。

対策は単純です。**多態を使うクラスは、値ではなく参照かポインタで扱う。**

| 受け取り方 | 多態が効くか |
| --- | --- |
| `void f(Base b)` | × スライシング |
| `void f(const Base & b)` | ○ |
| `void f(Base * b)` | ○ |
| `void f(std::shared_ptr<Base> b)` | ○ |

`rclcpp` が `Node` のコピーを `delete` しているのは、
**この事故を「静かな誤動作」ではなく「コンパイルエラー」に変えている**とも読めます。
4 章で扱う `const &` の話と、5 章の所有権の話がここで交わります。

## 3.7 継承すべきか、持つべきか

最後に設計の話をします。**継承は「唯一の正解」ではありません。**

C++ の継承は "is-a"（〜の一種である）を表します。
`MinimalPublisher` は「ノードの一種」なので継承が自然です。

一方 "has-a"（〜を持っている）ならメンバとして持つべきです。

```cpp
// 継承（is-a）
class MinimalPublisher : public rclcpp::Node { };

// メンバとして持つ（has-a / composition）
class MyRobot
{
private:
  rclcpp::Node::SharedPtr node_;
};
```

実は **rclcpp は後者も許しています。**
`RCLCPP_COMPONENTS_REGISTER_NODE` のマクロのコメントにこう書かれています。

> Valid arguments for NodeClass shall have a constructor that takes a single argument that is a `rclcpp::NodeOptions` instance, and a method of the signature `rclcpp::node_interfaces::NodeBaseInterface::SharedPtr get_node_base_interface`. Note: NodeClass does not need to inherit from `rclcpp::Node`, but it is the easiest way.

**「`rclcpp::Node` を継承する必要はない。ただしそれがいちばん簡単な方法だ」** と明言されています。
`get_node_base_interface()` を持っていれば何でもよいのです。

これが成り立つ理由は [rclcpp の設計思想](../rclcpp-の設計思想.md)の 2 章に書いてあります。
`Node` は 11 個のインタフェースを束ねたファサードで、
`create_publisher()` などのフリー関数は「必要なインタフェースだけ」を要求します。

実務では次の判断になります。

| 状況 | 選択 |
| --- | --- |
| ふつうのノードを書く | `public rclcpp::Node` を継承（ドリルの全課題） |
| 既存クラスに ROS の口を付けたい | `Node::SharedPtr` をメンバに持つ |
| ライフサイクル管理が必要 | `rclcpp_lifecycle::LifecycleNode` を継承 |
| プラグインを実装する | 指定された基底クラスを継承（選択肢なし） |

### 多重継承は避ける

C++ は複数の基底クラスを持てます。

```cpp
class Foo : public Base1, public Base2 { };
```

**`rclcpp::Node` を含む多重継承はしないでください。**
2 つの基底が両方 `Node` を継承していると `Node` が 2 個できる（ダイヤモンド継承）など、
仮想継承の知識が必要な領域に入ります。

例外は「純粋仮想関数だけの基底クラス（インタフェース）を複数実装する」場合で、
これは Java の `implements` に相当し、安全です。

## 手元で試す

**`override` を書かないと何が起きるか、自分で見ます。**

```cpp
// inherit.cpp
#include <iostream>
#include <memory>
#include <vector>

class Sensor
{
public:
  virtual ~Sensor() = default;

  // 既定の実装がある仮想関数
  virtual double read() const { return 0.0; }
  virtual const char * label() const { return "sensor"; }

  void report() const
  {
    std::cout << label() << " = " << read() << "\n";
  }
};

class Encoder : public Sensor
{
public:
  double read() const override { return 12.5; }
  const char * label() const override { return "encoder"; }
};

class Imu : public Sensor
{
public:
  // 罠: const を書き忘れた。override も書いていない
  double read() { return 99.9; }
  const char * label() const override { return "imu"; }
};

int main()
{
  std::vector<std::unique_ptr<Sensor>> sensors;
  sensors.push_back(std::make_unique<Encoder>());
  sensors.push_back(std::make_unique<Imu>());

  for (const auto & s : sensors) {
    s->report();
  }
  return 0;
}
```

**予想: `imu` の行には何が出るか。`99.9` か、それ以外か。**

```bash
g++ -std=c++17 -Wall -Wextra inherit.cpp -o inherit && ./inherit
```

[▶ ブラウザで実行する（gcc 13.3）](https://godbolt.org/z/dT4s7qvGY)

**`-Wall -Wextra` でも警告は出ません。** これが `override` を書く理由です。

確認したら `Imu::read()` に `override` を付けてください。
コンパイルエラーになります。エラーメッセージを読んで、`const` を足して直します。

続けて 3 つ試してください。

**① 仮想デストラクタを外す**

`virtual ~Sensor() = default;` を `~Sensor() = default;` に変えて、
`Encoder` に次を足します。

```cpp
  ~Encoder() { std::cout << "~Encoder\n"; }
```

`unique_ptr<Sensor>` 経由で破棄したとき `~Encoder` が出るか。`virtual` を戻すとどうなるか。

**② スライシングを起こす**

`report()` の中身を次に変えます。

```cpp
  void report() const
  {
    print_value(*this);       // Sensor の値として渡す
  }
```

```cpp
void print_value(Sensor s)         // 値で受ける
{
  std::cout << s.label() << " = " << s.read() << "\n";
}
```

**予想: `encoder` と出るか、`sensor` と出るか。**
`Sensor s` を `const Sensor & s` に変えて、出力が変わることを確認してください。

**③ コピーを禁止する**

`Sensor` に次を足します。

```cpp
  Sensor(const Sensor &) = delete;
  Sensor & operator=(const Sensor &) = delete;
```

② の値渡し版がコンパイルエラーになります。
**これが `rclcpp::Node` がやっていることです。**
`Sensor(const Sensor &) = delete;` を足すと既定コンストラクタも消えるので、
`Sensor() = default;` も必要になります。理由は 2 章の「引数付きコンストラクタを
1 つでも書くと既定が生成されない」と同じ規則です。

## つまずきポイント

**`error: no matching function for call to ‘rclcpp::Node::Node()’`**
初期化子リストで `Node("名前")` を呼び忘れています。3.3 節。

**`error: ‘create_publisher’ was not declared in this scope`**
`: public rclcpp::Node` を書き忘れているか、継承の `public` を書き忘れています。
`class Foo : rclcpp::Node` と書くと **`private` 継承**になり、
`create_publisher` が `private` 扱いになるので外からも派生からも呼べません。
**`class` の継承の既定は `private`** です（`struct` は `public`）。
ROS 2 で `private` 継承を使う場面はありません。**必ず `public` と書いてください。**

**`error: cannot declare variable ‘x’ to be of abstract type**
純粋仮想関数を実装し忘れています。
`note: because the following virtual functions are pure within ...` に、
実装すべき関数が並んでいます。

**`marked ‘override’, but does not override`**
基底の仮想関数とシグネチャが違います。よくある原因は
`const` の有無、引数の型（`int` と `int &`）、`noexcept` の有無です。
基底の宣言をコピーして持ってくるのが確実です。

**基底と同じ名前の関数を派生に書いたら、基底の別のオーバーロードが呼べなくなった**
**名前隠蔽（name hiding）** です。派生クラスで同じ名前を宣言すると、
基底のその名前の**すべてのオーバーロードが隠れます**（シグネチャが違っても）。

```cpp
class Base
{
public:
  void f(int) {}
  void f(double) {}
};

class Derived : public Base
{
public:
  void f(int) {}      // Base::f(double) も隠れる
};

Derived d;
d.f(1.5);             // Derived::f(int) が呼ばれる（double → int に変換される）
```

`using Base::f;` を派生クラスに書くと基底のオーバーロードが復活します。

**派生クラスのコンストラクタを継承したい**
C++11 以降は `using Base::Base;` で基底のコンストラクタをそのまま引き継げます。
`rclcpp::Node` では使いません（ノード名を固定したいので）。

## ドリルのどこで出るか

| 課題 | この章の何が出るか |
| --- | --- |
| 01〜15（全課題） | `class X : public rclcpp::Node` と、初期化子リストでの `Node("名前")` |
| 01, 02 | 継承した `create_publisher` / `create_subscription` / `get_logger` を呼ぶ |
| 06, 07 | 継承した `declare_parameter` / `get_parameter` を呼ぶ |
| 13 | 継承した `create_callback_group` を呼ぶ |
| 14, 15 | `Node("名前", options)` — 受け取った `NodeOptions` の素通し。ここを崩すとテストが落ちる |
| 15 | `RCLCPP_COMPONENTS_REGISTER_NODE` が「`Node` の継承は必須でない」と明記している |
| 11 | **継承を使わない例**。`limit_velocity` は自由関数。テストしやすさが理由 |

この講習を終えたあと、`move_base_flex` のプランナ／コントローラを自分で書く段階に
なると、3.4 節の純粋仮想関数が主役になります。
`SimplePlanner` / `SimpleController` のような基底クラスを継承したクラスが
`plugins.xml` で登録され、`move_base_flex` が実行時に基底クラスのポインタとして
受け取る、という構造です。

`ros2_control` の `hardware_interface::SystemInterface` も同じです。
サーボやモータドライバごとのハードウェアクラスが、これを継承した実装になります。
**継承は「ドリルのため」ではなく「実機のコードを読むため」に必要**になります。
