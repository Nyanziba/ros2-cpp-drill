# ROS2講習18: TF2と座標系

## はじめに

この記事を終えると、ロボットの中に複数の座標系が同時に存在する理由を理解し、`tf2`ツール（`tf2_echo`、`view_frames`）で座標変換の実態を確認できるようになります。`static_transform_publisher`で自分で座標変換を1本流せるようにもなります。

前提は[17_テストとデバッグ](17_テストとデバッグ.md)までの内容と、LiDARやカメラなどセンサをトピックで扱った経験があることです。TF2はセンサ統合の土台になる仕組みなので、[21_センサ統合](21_センサ統合.md)より前に必ず押さえておいてください。

## 講習目標

- なぜロボットに複数の座標系が必要なのかを自分の言葉で説明できる
- `map`→`odom`→`base_link`という標準構成（REP 105）の役割分担を理解する
- 静的TFと動的TFの違いを理解し、`static_transform_publisher`をCLIで実行できる
- `tf2_echo`と`view_frames`でTFツリーの状態を確認できる
- `lookup_transform`で`ExtrapolationException`が起きる理由を説明できる

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境（[02_環境構築](02_環境構築.md)完了）
- `ros-jazzy-turtlesim`パッケージ
- `ros-jazzy-turtle-tf2-py`パッケージ（`sudo apt install ros-jazzy-turtle-tf2-py`。turtlesimの公式TF2デモが入っている）
- `ros-jazzy-tf2-tools`パッケージ（`view_frames`が入っている。`sudo apt install ros-jazzy-tf2-tools`）
- PDFビュワー（`view_frames`が出力する`frames.pdf`を見るため。GUI環境が前提）

### 時間配分の目安

- なぜ座標変換が要るのかの説明: 10分
- map/odom/base_linkの役割分担の説明: 10分
- 静的TF・`static_transform_publisher`演習: 10分
- turtle_tf2デモを動かして`tf2_echo`/`view_frames`で確認: 15分
- `lookup_transform`と時刻の話、口頭試問: 10分

### 口頭試問

**Q1. LiDARで検出した障害物の座標を、そのままロボットの前進判断に使ってはいけないのはなぜですか。**

模範解答: LiDARが返す座標は`laser`（あるいは`lidar_link`など）というLiDAR自身を原点にした座標系での値であり、ロボットの車体や、ロボットが移動する空間全体の座標系とは基準点も向きも異なる。ロボットが「前に0.5m進む」といった判断をするには、障害物の位置を`base_link`や`map`のような、ロボット・環境を基準にした座標系に変換してから使う必要がある。この変換をせずにLiDARの生座標をそのまま使うと、LiDARの取り付け位置や向きがずれた分だけ判断がずれる。

**Q2. `odom`座標系と`map`座標系はどちらも「ロボットが今どこにいるか」を表しますが、何が違いますか。**

模範解答: `odom`はホイールオドメトリやIMUの積分など、ロボット自身の推定だけから作られる座標系で、値が連続的に滑らかに変化する（ジャンプしない）という保証がある一方、時間が経つと誤差が積もってドリフトし、実際の位置とずれていく。`map`はSLAMや自己位置推定によって環境全体に対する「正しい」位置を表す座標系で、ループクロージャなどで位置推定が更新された瞬間に値が飛ぶことがあるが、長期的には`odom`より正確です。短期的な滑らかさが要る制御（局所的な走行制御）は`odom`を基準にし、長期的な正しさが要る処理（大域的な経路計画）は`map`を基準にするという役割分担がある。

**Q3. `lookup_transform`を呼んだら`ExtrapolationException: Lookup would require extrapolation into the future`というエラーが出ました。何が起きていますか、どう対処しますか。**

模範解答: 指定した時刻のTFがまだTFツリーに届いていない、つまり「まだ来ていない未来の時刻の変換を計算しろ」と要求してしまっている状態。TF2は基本的に過去から現在までの変換履歴をバッファに保持して補間する仕組みなので、まだpublishされていない時刻や、逆に古すぎてバッファから消えた時刻を指定すると失敗する。対処は、`rclpy.time.Time()`（時刻指定なし、つまり「最新の利用可能な変換」を意味する）を使うか、`lookup_transform`の代わりに`wait_for_transform_async`などで変換が来るまで待つ、あるいはメッセージの`header.stamp`をそのまま使わずに現在時刻に寄せる、といった方法がある。

## 本文

### 学習内容：なぜ座標変換が要るのか

学習内容：ロボットの中には複数の座標系が同時に存在することを理解する。

準備：特になし。

内容：

LiDARが「障害物がここにある」と返してくる座標は、LiDARというセンサ自身を原点とした座標系での値です。センサの取り付け位置がロボットの中心からずれていれば、その分だけLiDARが見ている「原点」もロボットの中心からずれています。ロボットが「障害物を避けて前進する」という判断をするには、この座標をロボットの車体基準（`base_link`）や、走り回っている空間全体の基準（`map`）に変換しなければなりません。

センサがLiDAR1つだけならまだ手計算でも何とかなりますが、実際のロボットにはカメラ、IMU、複数のホイールエンコーダなどが載り、それぞれが自分の座標系でデータを返してきます。これを全部手作業で変換していたら破綻するので、ROS2には「どの座標系とどの座標系がどういう関係にあるか」を一元管理する仕組みがあります。これがTF2（Transform Frameworkの2代目）です。

TF2は各座標系（frame）の間の並行移動と回転をツリー構造で管理し、「`laser`座標系の点を`map`座標系に変換したい」といったリクエストに対して、ツリーを辿って計算した結果を返してくれます。個々の変換を自分で書く必要はなく、TF2に「今の`laser`から`map`への変換を教えて」と聞けばよいわけです。

### 学習内容：標準フレーム構成（REP 105）

学習内容：`map`→`odom`→`base_link`という標準的なフレーム構成と、それぞれの役割を理解する。

準備：特になし。

内容：

ROS2には座標系の命名と親子関係についての標準規約があり、これはREP 105（REP: ROS Enhancement Proposal）で定義されています。多くのナビゲーションスタックがこの規約に従っているので、初見のロボットでもTFツリーを見れば大体の構造が読めるようになります。中心となる3つのフレームは次の通りです。

| フレーム | 意味 | 特徴 |
|---|---|---|
| `map` | 環境全体を基準にした固定座標系 | 長期的に正確。ただしSLAM/自己位置推定の更新で値が飛ぶことがある |
| `odom` | ロボットの起動時点を原点にした座標系 | 値は連続的・滑らか（ジャンプしない）。時間が経つとドリフトして実際の位置からずれる |
| `base_link` | ロボット車体そのものを基準にした座標系 | ロボットの中心や重心などに固定。センサ類の座標系（`laser`など）はこの下にぶら下がる |

親子関係は`map`→`odom`→`base_link`という順です。つまり`base_link`は`odom`から見た相対位置として表され、`odom`は`map`から見た相対位置として表されます。

なぜ`odom`を`map`と`base_link`の間に挟むのか、というのがこの構成の要点です。局所的な走行制御（すぐ前の障害物を避ける、直進を維持するなど）は「値が滑らかで急に飛ばない」ことが重要で、多少ドリフトしていても短時間なら実用上問題になりません。逆に大域的な経路計画（今どの部屋にいて、どの通路を通ってゴールへ向かうか）は「長期的に正しい」ことが重要で、多少値が飛んでも構いません。`odom`が前者を、`map`が後者を担当することで、それぞれの用途に適した座標系を使い分けられるようにしているわけです。

> コラム: `map`から見て`odom`がどれだけずれているか（`map`→`odom`の変換）を計算し続けるのが自己位置推定（localization）の仕事です。`odom`→`base_link`はホイールオドメトリなどから素直に計算できますが、`map`→`odom`は環境の地図と現在のセンサ値を照合しないと出せません。この見取り図は[22_自己位置推定](22_自己位置推定の考え方.md)で詳しく扱います。

### 学習内容：静的TFを流す

学習内容：`static_transform_publisher`で固定された座標変換を1本publishする。

準備：turtlesimは使わないターミナルを1枚用意してください。

内容：

ロボットの車体とLiDARの位置関係のように、ロボットが動いている間ずっと変わらない変換は「静的TF」として扱います。静的TFは1回publishすれば十分で、`tf2_ros`パッケージの`static_transform_publisher`を使えばコード1行も書かずにCLIから流せます。

```bash
ros2 run tf2_ros static_transform_publisher --frame-id base_link --child-frame-id laser --x 0.1 --y 0.0 --z 0.2 --roll 0 --pitch 0 --yaw 0
```

これは「`base_link`から見て`laser`はx方向に10cm、z方向に20cm離れた位置にある（回転なし）」という変換を流し続けます。`--frame-id`が親フレーム、`--child-frame-id`が子フレームです。実際のロボットでは、LiDARを車体のどこに何cm、どの向きで取り付けたかをメジャーで測るか、CADの図面から読み取ってこの数値を決めます。

### 学習内容：turtle_tf2デモを動かす

学習内容：turtlesimの公式TF2デモを動かし、動的TFの実例を観察する。

準備：`ros-jazzy-turtle-tf2-py`パッケージがインストールされていること。

内容：

`turtle_tf2_py`はturtlesim上で動くTF2の公式デモです。まず起動します。

```bash
ros2 launch turtle_tf2_py turtle_tf2_demo.launch.py
```

亀が2匹（`turtle1`、`turtle2`）表示されます。別のターミナルからキー入力で`turtle1`を動かしてみましょう。

```bash
ros2 run turtlesim turtle_teleop_key
```

`turtle1`を動かすと、`turtle2`が一定の距離を保ちながら`turtle1`を追いかけてきます。これはデモの中で「`turtle1`から見た`turtle2`の相対位置」をTF2で計算し、その結果を`turtle2`への速度指令に変換しているためです。つまり各亀の座標系（`turtle1`、`turtle2`）と、それらの親である`world`座標系がTFツリーとして管理されており、`turtle2`を制御するノードは`lookup_transform`で「今`turtle1`から見て`turtle2`はどこにいるか」を毎フレーム問い合わせています。

このデモが動的TFの実例です。`turtle1`や`turtle2`の座標系は亀が動くたびに更新され続けるので、`static_transform_publisher`のような1回きりのpublishでは表現できません。動的TFは`TransformBroadcaster`（Python/C++のライブラリAPI）を使い、ノードの中で位置が変わるたびにbroadcastします。

### 学習内容：tf2_echoとview_framesで確認する

学習内容：TFツリーの状態を`tf2_echo`と`view_frames`で確認する。

準備：turtle_tf2デモを起動したままにしておきます。

内容：

2つの座標系の間の変換を今すぐ知りたいときは`tf2_echo`が手軽です。

```bash
ros2 run tf2_ros tf2_echo turtle1 turtle2
```

`turtle1`から見た`turtle2`の位置・向きが一定周期で表示され続けます。`teleop`で`turtle1`を動かすと数値が変化するのを確認してください。

TFツリー全体をまとめて見たいときは`view_frames`を使います。

```bash
ros2 run tf2_tools view_frames
```

実行すると`frames.pdf`というファイルがカレントディレクトリに生成されます。これを開くと、`world`を根として`turtle1`と`turtle2`がぶら下がっているツリー図が見られ、各フレーム間の変換がいつ最後にpublishされたか、どのくらいの周期でpublishされているかも書かれています。実機のロボットでこのPDFを開くと、`map`→`odom`→`base_link`から`laser`や`camera_link`まで枝分かれしたツリーが見えるはずです。「TFが繋がっていない気がする」というトラブルのときは、まずこの1枚を出力する癖をつけてください。フレームが孤立していたり、想定した親子関係と違っていたりすれば、それが原因です。

### 学習内容：lookup_transformと時刻

学習内容：`lookup_transform`が時刻を伴う理由と、`ExtrapolationException`が起きる仕組みを理解する。

準備：特になし。

内容：

TF2の変換は「今」だけでなく「ある時刻において」という形で管理されています。`lookup_transform`を呼ぶときは、変換元・変換先のフレーム名に加えて時刻を渡します。

```python
transform = tf_buffer.lookup_transform(
    'map',            # 変換先フレーム
    'laser',          # 変換元フレーム
    rclpy.time.Time(),  # 時刻（Time()は「最新の利用可能な変換」を意味する）
)
```

なぜ時刻が要るのかというと、TFは過去から現在までの変換の履歴をバッファに溜めていて、指定した時刻に一番近い変換を補間して返す仕組みになっているからです。センサのメッセージには`header.stamp`にそのセンサ値を取得した時刻が入っているので、「そのセンサ値を取得した瞬間のTFで変換したい」という場合は`header.stamp`をそのまま渡すのが正確です。

ここでよく詰まるのが`ExtrapolationException`です。指定した時刻がバッファにまだ届いていない未来の時刻だったり、逆にバッファの保持期間（デフォルトで数秒程度）より古い時刻だったりすると、TF2は「補間できない、外挿が必要になる」と判断してこの例外を投げます。センサのメッセージがネットワークや処理の遅延で少し遅れて届いた場合、そのタイムスタンプを使って変換しようとすると発生しやすいです。まずは`rclpy.time.Time()`を渡して「最新の変換でいい」という指定に変え、それで問題が解決するなら遅延が原因だったと判断できます。厳密に「そのタイムスタンプの瞬間」の変換が必要な場合は、`wait_for_transform_async`などで変換が届くまで待つ実装にします。

## 発展

自己位置推定（localization）とは、結局「`map`→`odom`の変換を誰かが出し続けること」です。`odom`→`base_link`はホイールオドメトリなどから素直に計算できる一方、`map`→`odom`は環境の地図とセンサ値を照合しないと出せません。この「誰か」の実体はAMCLやSLAMのノードであり、これらが動いていない状態では`map`フレームは存在せず、`odom`が唯一の頼れる座標系になります。この見取り図は[22_自己位置推定](22_自己位置推定の考え方.md)で具体的に扱います。


## おわりに

TF2はロボットのソフトウェアの中で最も裏方に近い仕組みですが、ナビゲーション・センサ統合・アーム制御などほぼすべての機能がTF2の上に成り立っています。「今どのフレームがどう繋がっているか」を`view_frames`で確認する癖をここでつけておくと、あとの記事でのデバッグが早くなります。わからなければ先輩に聞きましょう。

次は[19_URDFの書き方](19_URDFの書き方.md)で、ロボットの形状とフレーム構成をXMLで記述する方法を扱います。
