# ROS2講習13: カスタムインターフェース

## はじめに

この記事を終えると、`.msg`/`.srv`ファイルの文法を理解し、自分専用のメッセージ型を定義してパッケージとしてビルドし、他のノードから使えるようになります。トピックもサービスもすでに触っているはずですが、そこで使っていたのは`geometry_msgs/msg/Twist`のような既製のメッセージ型でした。今回はその型自体を自分で作ります。

前提は[06_サービス](06_サービス.md)まで完了していることと、[12_Pythonでpub_subを書く](12_Pythonでpub_subを書く.md)でPythonのpub/subノードを一通り書けることです。

## 講習目標

- `.msg`/`.srv`の文法（型、配列、定数）を読み書きできる
- `rosidl_default_generators`を使ったカスタムインターフェースパッケージを1から作れる
- 「まず標準型を探す、なければ自作する」の順番を身につける
- 自作したmsgをpub/subし、`ros2 interface show`で構造を確認できる

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境
- ワークスペース（`~/ros2_ws`など、[02_環境構築](02_環境構築.md)で作成済みのもの）
- `sudo apt install ros-jazzy-rosidl-default-generators`が入っていること（`ros-jazzy-desktop`を入れていれば通常は同梱済み）

### 口頭試問

**Q1. 新しいデータをやり取りしたくなったとき、最初にすべきことは何ですか。**

模範解答: 自分でmsgを作る前に、既存の標準メッセージパッケージ（`std_msgs`、`geometry_msgs`、`sensor_msgs`など）に該当する型がないか`ros2 interface list`や`ros2 interface package geometry_msgs`で探す。速度なら`Twist`、姿勢なら`Pose`のように、世の中の大半のロボットが必要とする型はすでに標準化されている。標準型を使えば他パッケージ・他ツール（`rviz2`や`tf2`など）とそのまま繋がるが、自作型は自分のパッケージにしか通用しない。探しても無ければ自作する、の順番を守る。

**Q2. `int32[]`と`int32[3]`と`int32[<=5]`の違いを説明してください。**

模範解答: `int32[]`は要素数に制限のない可変長配列。`int32[3]`は要素数が必ず3の固定長配列（3個ぴったりでなければ生成時・実行時にエラーになる）。`int32[<=5]`は上限5までの可変長配列（0〜5個）。エンコーダ値のように必ず4輪分揃っているデータなら固定長`float64[4]`が適切で、可変長にすると受け手が要素数チェックを書く必要が出てくる。

**Q3. なぜ`.msg`ファイルを置くパッケージと、それを使うパッケージを分けるのが一般的なのですか。**

模範解答: メッセージ定義（`rosidl_generate_interfaces`でC++/Pythonのコードを自動生成する処理）はビルドの依存関係が特殊で、msg専用パッケージに切り出しておくと複数のノードパッケージから同じ型を`find_package`するだけで使い回せる。ロジックとインターフェース定義を同じパッケージに混ぜると、型だけ使いたい別パッケージが不要な依存を抱え込むことになる。公式チュートリアルの`tutorial_interfaces`もこの分離構成になっている。

## 本文

### 学習内容：まず標準型を探す

学習内容：自作する前に標準メッセージ型で足りないか確認する。

準備：特になし。

内容：

ROS2には`std_msgs`、`geometry_msgs`、`sensor_msgs`、`nav_msgs`など、よく使うデータ構造がすでに標準パッケージとして用意されています。速度なら`geometry_msgs/msg/Twist`、姿勢なら`geometry_msgs/msg/Pose`、バッテリー残量なら`sensor_msgs/msg/BatteryState`といった具合です。

パッケージごとにどんな型があるか一覧するには次のコマンドを使います。

```bash
ros2 interface package geometry_msgs
```

インストールされている全パッケージから型を検索したいときは`ros2 interface list`を`grep`に通すのが手早いです。

```bash
ros2 interface list | grep -i battery
```

**標準型で表現できるなら標準型を使ってください。** 自作型は自分のパッケージの外では通用しないので、`rviz2`や`tf2`のような既存ツールと連携させたい場合はまず標準型で表現できないか考えます。それでも表現できないデータ（部独自のセンサ値、独自プロトコルのフィールドなど）が出てきたときだけ、次の手順で自作します。

### 学習内容：msg/srvファイルの文法

学習内容：`.msg`/`.srv`の型・配列・定数の書き方を理解する。

準備：特になし。

内容：

`.msg`ファイルは1行に1フィールドを「型 名前」の順で書くだけの単純なテキストです。

```
# Num1.msg
int64 num
```

複数フィールドも同様に並べます。

```
# AddThreeInts.srv（サービスの場合。リクエストとレスポンスを---で区切る）
int64 a
int64 b
int64 c
---
int64 sum
```

使える型は`int8`/`int32`/`int64`/`float32`/`float64`/`string`/`bool`などの基本型のほか、他パッケージのメッセージ型もそのまま使えます。

```
# 他のmsgをフィールドとして埋め込む例
geometry_msgs/Vector3 position
string name
```

配列は3種類の書き方があります。

| 書き方 | 意味 |
|---|---|
| `int32[]` | 可変長配列（要素数の制限なし） |
| `int32[3]` | 固定長配列（必ず3個） |
| `int32[<=5]` | 上限付き可変長配列（0〜5個） |

定数は大文字で定義し、値の変更を許さないフィールドとして使います。ステータス値のようにあらかじめ決まった選択肢を表現するときによく使われます。

```
# 定数の例
int32 STATUS_IDLE=0
int32 STATUS_RUNNING=1
int32 STATUS_ERROR=2
int32 status
```

コメントは`#`で書けます。フィールドの単位（`# rad/s`など）はコメントで明記しておくと、後で使う人が迷いません。**単位を書き忘れると、後から見た人が`rad`か`deg`か`rad/s`か分からず事故る**のでここは省略しないでください。

### 学習内容：カスタムインターフェースパッケージを作る

学習内容：`rosidl_default_generators`を使って`.msg`/`.srv`をビルドできるパッケージを1から作る。

準備：ワークスペースの`src`にいることを確認します。

```bash
cd ~/ros2_ws/src
```

内容：

公式チュートリアルの`tutorial_interfaces`相当のパッケージを作ります。C++/Pythonどちらのノードからも使えるインターフェース専用パッケージなので、ビルドタイプは`ament_cmake`一択です（Pythonノードから使う場合でも、msg/srv自体はCMakeでビルドします）。

```bash
ros2 pkg create --build-type ament_cmake tutorial_interfaces
```

作成されたパッケージの中に`msg`ディレクトリと`srv`ディレクトリを作り、それぞれファイルを置きます。`ros2 pkg create`はカレントディレクトリを変えないので、**先にパッケージの中へ移動する**のを忘れないでください。忘れると`msg`/`srv`が`src/`直下にできてしまい、後述の`rosidl_generate_interfaces`がファイルを見つけられずビルドが壊れます。

```bash
cd tutorial_interfaces
mkdir msg srv
```

`msg/Num.msg`を作ります。

```
int64 num
```

`srv/AddThreeInts.srv`も作ります。

```
int64 a
int64 b
int64 c
---
int64 sum
```

次に`package.xml`に依存関係を追加します。`<buildtool_depend>`の下あたりに次の3行を入れてください。

```xml
<buildtool_depend>rosidl_default_generators</buildtool_depend>
<exec_depend>rosidl_default_runtime</exec_depend>
<member_of_group>rosidl_interface_packages</member_of_group>
```

最後に`CMakeLists.txt`を編集します。`find_package(ament_cmake REQUIRED)`の下に以下を追加します。

```cmake
find_package(rosidl_default_generators REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/Num.msg"
  "srv/AddThreeInts.srv"
)
```

`rosidl_generate_interfaces`が、`.msg`/`.srv`ファイルからC++/Pythonの型定義コードを自動生成してくれるビルド処理です。ここに書いたファイルパスがそのままビルド対象になるので、新しいmsgを追加したら必ずこのリストにも追記してください（**忘れるとファイルはあるのにビルドされず「型が見つからない」エラーになる**、よくあるハマりどころです）。

ワークスペースのルートに戻ってビルドします。

```bash
cd ~/ros2_ws
colcon build --packages-select tutorial_interfaces
source install/setup.bash
```

ビルドが通ったら`ros2 interface show`で自分の型を確認できます。

```bash
ros2 interface show tutorial_interfaces/msg/Num
```

```
int64 num
```

### 学習内容：自作msgを他パッケージから使う

学習内容：自作した型をノードのパッケージから参照してpub/subする。

準備：`tutorial_interfaces`のビルドが完了していること。[12_Pythonでpub_subを書く](12_Pythonでpub_subを書く.md)で作ったパッケージ（またはこの講習用に新規作成したパッケージ）を使います。

内容：

自作msgを使うパッケージ側の`package.xml`に依存を追加します。

```xml
<exec_depend>tutorial_interfaces</exec_depend>
```

`CMakeLists.txt`（C++の場合）や`setup.py`（Pythonの場合）に依存を追加する作業は、標準のメッセージパッケージ（`std_msgs`など）に依存を追加するときと全く同じ手順です。特別なことは何もありません。

Pythonノードでのimportもいつも通りです。

```python
from tutorial_interfaces.msg import Num
```

publisherの中身は`std_msgs/msg/Int64`を使っていたところを`Num`に置き換えるだけです。

```python
msg = Num()
msg.num = self.count
self.publisher_.publish(msg)
```

**練習問題**: `msg/Num.msg`を持つ`tutorial_interfaces`パッケージを作成し、1秒ごとにカウントアップする`Num`型を配信するpublisherノードと、受け取った値をログ出力するsubscriberノードを書いてください。`ros2 topic echo`で値が流れていることを確認してください。

<details markdown="1"><summary>解答</summary>

パッケージ作成とビルドは本文の手順通りです。publisherノードの骨格は次の通りです。

```python
import rclpy
from rclpy.node import Node
from tutorial_interfaces.msg import Num


class NumPublisher(Node):
    def __init__(self):
        super().__init__('num_publisher')
        self.publisher_ = self.create_publisher(Num, 'topic', 10)
        self.timer_ = self.create_timer(1.0, self.timer_callback)
        self.count_ = 0

    def timer_callback(self):
        msg = Num()
        msg.num = self.count_
        self.publisher_.publish(msg)
        self.get_logger().info(f'Publishing: {msg.num}')
        self.count_ += 1


def main(args=None):
    rclpy.init(args=args)
    node = NumPublisher()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()
```

subscriberも`create_subscription(Num, 'topic', callback, 10)`とするだけで、他はいつものpub/subの書き方と変わりません。`ros2 topic echo /topic`で`num: 0`、`num: 1`と増えていくのが見えれば成功です。

</details>

### 学習内容：ロボコンにおけるカスタムインターフェースの意義

学習内容：マイコンとのCAN通信の内容をROS側のmsgにどう対応させるか、設計の観点を持つ。

準備：特になし。

内容：

自作msgが本当に必要になるのは、マイコン側と通信する場面です。うちのロボットはモータ指令やエンコーダ値をCAN経由でマイコンとやり取りしていますが、CANのフレームはバイト列であって、それ自体はROS2のトピックではありません。CAN側のブリッジノードが受け取ったバイト列をパースして、意味のあるフィールドを持つROS2のmsgに変換し直す必要があります。

このとき、標準型で表現できるものは標準型に寄せるのが基本です。速度指令なら`geometry_msgs/msg/Twist`、単純なON/OFFなら`std_msgs/msg/Bool`で足りることが多いです。一方で、エンコーダの生値や、CANフレームIDごとに複数のセンサ値がパックされているようなデータは、標準型に無理に押し込めるよりも自作msgで素直に表現したほうが読みやすくなります。

```
# 自作msgの例: モータのエンコーダ値をそのまま伝える想定
# (実際のフィールド構成は自分たちの CAN プロトコル定義に合わせること。ここは例示)
float64[4] encoder_position
float64[4] encoder_velocity
bool[4] motor_enabled
```

どのCANフレーム・どのビット位置がどのmsgフィールドに対応するのかは、部で定めているCAN通信のプロトコル仕様に従う必要があります。ここで架空の対応表を書くと実物と食い違って事故るので、必ず一次情報を確認してください。


## 発展

複数のmsgファイルをまとめて1つのパッケージに入れず、`base_interfaces`のように機能ごとに分けて管理しているプロジェクトもあります。パッケージが増えるほど依存関係の管理は複雑になるので、どこまで分割するかは運用次第です。

また、`.msg`だけでなく`.action`（アクション用のインターフェース）も同じ`rosidl_generate_interfaces`の仕組みで生成できます。アクション自体は[08_アクション](08_アクション.md)で扱っていますが、自作アクション型の作り方はそちらでは触れていません。


## おわりに

標準型で足りるかを最初に確認する癖をつけてください。自作msgは便利ですが、増やしすぎると依存関係もドキュメントも保守しきれなくなります。わからなければ先輩に聞きましょう。
