# ROS2講習14: サービスの実装

## はじめに

[06_サービス](06_サービス.md)では`ros2 service call`を使う側として動かしました。今回は逆に、自分でサービスサーバーとクライアントを実装します。この記事が終わると、`add_two_ints`サービスをPythonで書いてビルドし、非同期呼び出しの正しい書き方と、やってはいけない書き方（デッドロックする書き方）の両方を説明できるようになります。

言語はPythonを使います。[12_Pythonでpub_subを書く](12_Pythonでpub_subを書く.md)でrclpyのパッケージ構成とsetup.pyの書き方は済んでいるはずなので、今回はその続きとして読めます。公式チュートリアルにはC++版もありますが、サービスサーバーの中身はほとんどの場合「受け取った値を使って上位ロジックを呼ぶだけ」の薄い層になることが多く、この層はPythonで書くのが一般的です。C++で書きたい場合は`rclcpp`版チュートリアルを参照してください。

環境はUbuntu 24.04 / ROS 2 Jazzy Jaliscoを前提とします。

## 講習目標

- `create_service`と`create_client`でサーバー・クライアントの両方を書ける
- クライアントの非同期呼び出し（`call_async` + `spin_until_future_complete`）を実装できる
- コールバック内で同期的にサービスを呼ぶとデッドロックする理由を説明できる
- `ros2 service call`で自作サービスの動作確認ができる

## 講習として使う場合

### 準備物

- Ubuntu 24.04 / ROS 2 Jazzyがセットアップ済みの端末（[02_環境構築](02_環境構築.md)完了）
- [12_Pythonでpub_subを書く](12_Pythonでpub_subを書く.md)のワークスペースが手元にあること（`~/ros2_ws`を想定）
- `example_interfaces`パッケージ（`add_two_ints`の型はこれに標準で入っている。`sudo apt install ros-jazzy-example-interfaces`が必要な場合あり）

### 口頭試問（模範解答つき）

**Q1. `call_async`が返すのは何ですか。呼んだ直後にレスポンスの値を取り出せますか。**

模範解答: `call_async`は`Future`オブジェクトを即座に返す。呼んだ直後の時点ではリクエストはまだサーバーに送られただけで、レスポンスは返ってきていない。値を取り出すには`spin_until_future_complete`などでFutureが完了する（`future.done()`が真になる）まで待ってから`future.result()`を呼ぶ必要がある。

**Q2. コールバック関数の中で同じノードのサービスクライアントを同期的に（`spin_until_future_complete`を使わずFutureの完了をブロッキングで待つ形で）呼ぶと何が起きますか。**

模範解答: 成立しない。`spin_until_future_complete`はエグゼキュータをブロッキングで回してFutureの完了を待つ関数だが、呼び出し元がすでにそのエグゼキュータをスピンさせている状態でコールバックの中から呼ぶと、レスポンスを受け取るために必要な次のスピンが実行できない。Jazzyのrclpyはこの再入を検出してガードするため、無言で固まるのではなく`RuntimeError: Executor is already spinning`が送出されてノードが異常終了する（ガードの実体は`/opt/ros/jazzy/lib/python3.12/site-packages/rclpy/executors.py`の`Executor._enter_spin`）。単一スレッドのエグゼキュータでは特に踏みやすい。

**Q3. サーバーを実装し忘れたままクライアントだけ起動して`call_async`を呼ぶと何が起きますか。**

模範解答: エラーで即座に落ちるわけではない。リクエストは送られるが、サーバーが存在しないためレスポンスが永遠に返らず、Futureが完了しないまま待ち続ける。`wait_for_service`でサーバーの存在を確認してから呼ぶのが正しい書き方であり、これを省略すると「動いているのか固まっているのか分からない」状態になりやすい。

## 本文

### パッケージを作る

`add_two_ints`という名前のリクエスト（`int64 a`, `int64 b`）とレスポンス（`int64 sum`）を持つサービス型は、`example_interfaces`パッケージにすでに定義されています。今回はカスタムインターフェースを作らず、この既存の型を使います（カスタムの`.srv`を自作する話は[13_カスタムインターフェース](13_カスタムインターフェース.md)を参照してください）。

ワークスペースの`src`に新しいPythonパッケージを作ります。

```bash
cd ~/ros2_ws/src
ros2 pkg create --build-type ament_python --license Apache-2.0 py_srvcli
```

`package.xml`に依存を追加します。

```xml
<depend>rclpy</depend>
<depend>example_interfaces</depend>
```

### サーバーを書く

`py_srvcli/py_srvcli/service_member_function.py`を作成します。

```python
from example_interfaces.srv import AddTwoInts

import rclpy
from rclpy.node import Node


class MinimalService(Node):

    def __init__(self):
        super().__init__('minimal_service')
        self.srv = self.create_service(
            AddTwoInts, 'add_two_ints', self.add_two_ints_callback)

    def add_two_ints_callback(self, request, response):
        response.sum = request.a + request.b
        self.get_logger().info(
            'Incoming request\na: %d b: %d' % (request.a, request.b))

        return response


def main():
    rclpy.init()

    minimal_service = MinimalService()

    rclpy.spin(minimal_service)

    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

`create_service`の第1引数がサービスの型、第2引数がサービス名、第3引数がリクエストを受け取って処理するコールバックです。コールバックは`request`と`response`の2つのオブジェクトを受け取り、`response`にフィールドを詰めて`return`するという形になっています。トピックのサブスクライバコールバックが値を受け取るだけだったのに対し、サービスのコールバックは値を返す点が構造上の違いです。

`setup.py`の`entry_points`に実行ファイルを登録します。

```python
entry_points={
    'console_scripts': [
        'service = py_srvcli.service_member_function:main',
    ],
},
```

### サーバーをビルドして動かす

```bash
cd ~/ros2_ws
colcon build --packages-select py_srvcli
source install/setup.bash
ros2 run py_srvcli service
```

別の端末から、06で使った`ros2 service call`で動作確認します。

```bash
ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 3, b: 4}"
```

```

response:
example_interfaces.srv.AddTwoInts_Response(sum=7)
```

サーバー側の端末にも`Incoming request`のログが出ているはずです。ここまでで「作ったサービスが正しく応答している」ことがコマンドラインだけで確認できます。今回は`ros2 service call`が確認手段そのもので、練習問題として別途課すほどの分量はありません。

### クライアントを書く

サーバーを叩く側もノードとして書きます。`py_srvcli/py_srvcli/client_member_function.py`を作成します。

```python
import sys

from example_interfaces.srv import AddTwoInts
import rclpy
from rclpy.node import Node


class MinimalClientAsync(Node):

    def __init__(self):
        super().__init__('minimal_client_async')
        self.cli = self.create_client(AddTwoInts, 'add_two_ints')
        while not self.cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().info('service not available, waiting again...')
        self.req = AddTwoInts.Request()

    def send_request(self, a, b):
        self.req.a = a
        self.req.b = b
        return self.cli.call_async(self.req)


def main():
    rclpy.init()

    minimal_client = MinimalClientAsync()
    future = minimal_client.send_request(int(sys.argv[1]), int(sys.argv[2]))
    rclpy.spin_until_future_complete(minimal_client, future)
    response = future.result()
    minimal_client.get_logger().info(
        'Result of add_two_ints: for %s + %s = %s' %
        (sys.argv[1], sys.argv[2], response.sum))

    minimal_client.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

流れを分解すると次の3段階です。

1. `create_client`でクライアントを作る。`wait_for_service`でサーバーが立っているか確認する（立っていなければ1秒ごとにログを出しながら待つ）
2. `call_async`でリクエストを送る。この時点で返ってくるのは**まだ結果ではなくFuture**
3. `spin_until_future_complete`でFutureが完了するまでエグゼキュータを回し、完了後に`future.result()`で実際のレスポンスを取り出す

`wait_for_service`を省くとどうなるか試してみてください。サーバーを起動せずにクライアントだけ実行すると、口頭試問Q3の通り、エラーにはならず単に応答が返らないまま止まります。「エラーが出ないから動いている」と早合点しないための良い実験です。

`setup.py`にも追加します。

```python
entry_points={
    'console_scripts': [
        'service = py_srvcli.service_member_function:main',
        'client = py_srvcli.client_member_function:main',
    ],
},
```

ビルドして両方動かします。サーバーを立てたまま、別端末で実行します。

```bash
colcon build --packages-select py_srvcli
source install/setup.bash
ros2 run py_srvcli client 2 3
```

```
[INFO] [minimal_client_async]: Result of add_two_ints: for 2 + 3 = 5
```

### コールバックの中で同期的に呼ぶとデッドロックする

ここが今回の一番重要な罠です。`spin_until_future_complete`は「エグゼキュータを回しながらFutureの完了を待つ」関数です。これを別のコールバックの外、つまり`main`のような場所で呼ぶ分には問題ありません。しかし、次のような書き方をすると危険です。

```python
class BadExample(Node):

    def __init__(self):
        super().__init__('bad_example')
        self.cli = self.create_client(AddTwoInts, 'add_two_ints')
        self.timer = self.create_timer(1.0, self.timer_callback)

    def timer_callback(self):
        req = AddTwoInts.Request()
        req.a = 1
        req.b = 2
        future = self.cli.call_async(req)
        rclpy.spin_until_future_complete(self, future)  # ここで RuntimeError になる
        self.get_logger().info(f'sum: {future.result().sum}')
```

`timer_callback`はすでにエグゼキュータのスピンによって呼ばれています。その中でさらに`spin_until_future_complete`を呼ぶと、レスポンスを受け取るための次のスピンが必要なのに、今のスピンの中で身動きが取れないまま待ち続けることになります。単一スレッドのエグゼキュータでは、コールバックが1つ実行されている間は他のコールバック（サブスクリプションのコールバックや、Futureの完了処理）は実行されません。つまりコールバックの中から同じノードのサービスを同期的に待つと、そのノード自身が答えを受け取れる状態になれません。Jazzyのrclpyはこの状況を検出して`RuntimeError: Executor is already spinning`を投げるので、実際には「固まる」のではなく**その場で例外を出して落ちます**。黙ってハングするより親切ですが、いずれにせよこの書き方は成立しません。

正しい対処は次のいずれかです。

- コールバックの中では`call_async`だけ呼んでFutureを保持し、完了確認は別の仕組み（`future.add_done_callback`でコールバックを登録する、または別のタイマーで`future.done()`をポーリングする）に任せる
- サービスクライアント用に別のノード・別のエグゼキュータ・別スレッドを用意する（`MultiThreadedExecutor`を使う、または別プロセスに分ける）
- そもそも「コールバックの中から同期的にサービスを呼ぶ必要がある設計」自体を見直す。アクションで作るべき処理をサービスで無理に組んでいないか確認する

> コラム: `add_done_callback`を使うと、Futureが完了した時点で自動的に呼ばれる関数を登録できます。ブロッキングせずに結果を受け取れるので、コールバック内からサービスを呼びたい場合の基本パターンになります。`future.add_done_callback(self.response_callback)`のように書き、`response_callback(self, future)`の中で`future.result()`を取り出します。

**練習問題**: 上記の`BadExample`を実際に動かしてエラーで落ちることを確認し、`add_done_callback`を使って成立する形に書き直してください。

<details markdown="1"><summary>解答</summary>

壊れる版はサーバーを起動した状態で`BadExample`を`rclpy.spin(node)`で回すと、`timer_callback`の最初の呼び出しで`RuntimeError: Executor is already spinning`が送出され、`[ros2run]: Process exited with failure 1`でプロセスが落ちることで確認できます。Humble以前の資料では「固まる」と説明されていることがありますが、Jazzyではガードが入っているため即エラーになります。

書き直し版の骨格は次のようになります。

```python
def timer_callback(self):
    req = AddTwoInts.Request()
    req.a = 1
    req.b = 2
    future = self.cli.call_async(req)
    future.add_done_callback(self.response_callback)

def response_callback(self, future):
    self.get_logger().info(f'sum: {future.result().sum}')
```

`timer_callback`は`call_async`を呼んだらすぐ返る。レスポンスが実際に届いたタイミングでエグゼキュータが`response_callback`を呼び出す。コールバックの中でブロッキング待ちをしない、という点が固まる版との違いです。

</details>

## 発展

06記事の使い分け表（連続的なデータはトピック、1回きりの操作はサービス）は実装してみるとより実感が持てるはずです。実装視点で1つ補足すると、サービスは「サーバー側の処理がどれくらいの時間で終わるか」を呼び出す側が事前に知っておく必要があります。今回の`add_two_ints`は足し算なので一瞬で終わりますが、これが数百msかかる処理だと、同期的に待つ設計ではその間クライアントのそのスレッドが丸ごと固まります。数秒〜数分かかる処理、途中経過を知りたい処理、キャンセルしたい処理は、サービスではなくアクションで作るべきというのが06発展で触れた結論で、[16_アクションサーバの実装](16_アクションサーバの実装.md)で扱います。

また、今回のサーバーはリクエストを受けてから同期的に計算して即座に`response`を返す構成でした。サーバー内部で別のサービスをさらに呼ぶような多段構成にする場合は、今回のデッドロックの罠がサーバー側にもそのまま当てはまります。サーバーのコールバックの中で別サービスを同期呼び出ししないように注意してください。
