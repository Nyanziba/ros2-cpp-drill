# ROS2講習22: 自己位置推定の考え方

## はじめに

この記事を終えると、「ロボットは今map上のどこにいるか」をどう計算するかと、その結果を現在のmove_base_flex構成へどのTFで渡すかを説明できるようになります。

前提は[21_センサ統合](21_センサ統合.md)を読み終えていることです。前記事で伏線として置いた「map→odom変換を出し続ける仕組みが必要」という話を、ここで実際に回収します。

## 講習目標

- map座標系・odom座標系・base座標系の関係と、自己位置推定が具体的に何を出力しているかを説明できる
- ホイールオドメトリ・IMU・LiDARスキャンマッチングそれぞれの得意・不得意を言える
- NDTスキャンマッチングが「何を最適化しているか」を直感的に説明できる
- move_base_flexが要求する`map → odom → base_link`のTF契約を確認できる

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境
- 実機で採用するlocalizationパッケージと、`map → odom → base_link` TFを確認できる環境
- 可能であれば録れたrosbag（odom/imu/scan/mapが含まれるもの）。無ければ座学中心の進行になる
- ホワイトボードか紙。座標変換の図を手で書く時間を確保する


### 時間配分の目安

- map/odom/baseの座標系と問題設定の説明: 10分
- 3つの情報源の性質の比較: 15分
- NDTスキャンマッチングの直感的説明: 15分
- move_base_flexとのTF接続確認: 15分
- 口頭試問: 10分

### 口頭試問

**Q1. 自己位置推定ノードは結局何を計算して、何をpublishしていますか。**

模範解答: map座標系での姿勢を推定し、通常は`map → odom`を出力する。オドメトリ側の`odom → base_link`と連結することで、move_base_flexが必要な`map → base_link`を解決できる。

**Q2. ホイールオドメトリだけで自己位置推定をしないのはなぜですか。**

模範解答: ホイールオドメトリは車輪の回転数（あるいは駆動指令）から移動量を積分して求めるため、スリップや車輪径の誤差、地面の凹凸などの小さな誤差が時間とともに積み重なる。これをドリフトと呼ぶ。短時間・高頻度の相対移動量としては信頼できるが、絶対位置の基準を持たないため、走り続けるほど実際の位置とのずれが広がっていく。

**Q3. NDTスキャンマッチングは何を探索していますか。1文で説明してください。**

模範解答: 事前に作った地図の点群をボクセルごとの正規分布（ガウス分布）の集合として表現しておき、今取得したスキャンをその分布に重ね合わせたときの当てはまりの良さ（対数尤度）が最大になる位置・姿勢を探索している。

**Q4. localizationをmove_base_flexから交換可能にするため、何を共通インターフェースにしますか。**

模範解答: 独自の内部状態や推定アルゴリズムではなく、`map → odom → base_link` TFと必要な時刻整合性を共通契約にする。

## 本文

### map・odom・baseの3つの座標系

自己位置推定の話をする前に、ロボットが持っている座標系を整理します。ROS2のナビゲーションスタックでは、次の3つのTFフレームが基本になります。

- `map`: 世界に固定された、動かない座標系。事前に作った地図の原点
- `odom`: オドメトリの原点。起動時のロボット位置を原点として、車輪やIMUの積分でここからの相対位置を出す
- `base_link`: ロボット本体に固定された座標系

`odom → base_link`はホイールオドメトリ（と場合によってIMU）が計算してくれます。問題は`map → odom`です。これは誰も直接測れません。地図の原点から見て、いま自分がどこにいるか——これを求め続けるのが自己位置推定の仕事です。

現在のmove_base_flex構成も、このTF treeが成立していることを前提にします。localizationの内部実装ではなく、`tf2_echo map base_link`で時刻を含めて解決できることを確認します。

### 3つの情報源、それぞれの性質

自己位置推定に使える情報源は主に3つあります。それぞれ得意・不得意が違うので、1つに頼らず組み合わせます。

| 情報源 | 頻度 | 特徴 | 弱点 |
|---|---|---|---|
| ホイールオドメトリ | 高頻度（数十〜百Hz） | 短時間の相対移動を高い精度で出せる | スリップや誤差の積分でドリフトする。絶対位置の基準を持たない |
| IMU | 高頻度（百Hz以上） | 角速度は比較的信頼できる | 積分すると角度もドリフトする。加速度からの位置推定はさらに発散が速い |
| LiDARスキャンマッチング | 低頻度（数〜十数Hz、計算負荷次第） | 絶対位置が得られる。ドリフトしない | 計算が重い。特徴の少ない環境（長い直線の壁だけなど）では合わない姿勢でも一致してしまうことがある |

ホイールオドメトリとIMUは高頻度ですが積分誤差が蓄積します。一方、LiDARスキャンマッチングは事前地図と現在スキャンを直接比較して大域的な補正に使えますが、一般に計算量が大きく更新頻度は低くなります。

典型的には、高頻度のオドメトリ・IMUで予測し、低頻度のLiDARマッチング結果で補正します。具体的な実装は実機で採用するlocalizationパッケージを正とします。

### NDTスキャンマッチングの直感

LiDARスキャンマッチングの代表的な手法がNDT（Normal Distributions Transform）です。仕組みを直感的に説明します。

1. 事前に作った地図の点群を、一定サイズのボクセル（立方体の格子）に分割する
2. 各ボクセルに入っている点の分布を、1つの正規分布（ガウス分布）として近似する。つまり地図全体が「正規分布の集合」に置き換わる
3. 今取得したLiDARスキャンの各点を、候補の位置・姿勢で地図座標系に変換する
4. 変換後の各点が、対応するボクセルの正規分布にどれだけ「ありそうか」（対数尤度）を全点で合計する
5. この合計値が最大になる位置・姿勢を、勾誤（ニュートン法など）で探索する

要するに「今のスキャンを、事前地図が期待する形に一番よく重ねられる位置・姿勢はどこか」を数値最適化で探しています。生の点群同士を距離で比較するICP（Iterative Closest Point）と役割は似ていますが、NDTは点そのものではなくボクセルごとの分布を比較するため、点群密度のばらつきに強く、収束も速い傾向があります。

> コラム: NDTは点群を分布に圧縮するので、地図の点群を毎回全部持ち歩く必要がありません。大きな地図でも比較的軽量に扱えるのは、この事前計算のおかげです。

### ナビゲーションスタックとの接続

一般的なナビゲーションスタックでは、自己位置推定の実装と経路計画・プラグインレイヤが分かれています。自己位置推定器そのものはmove_base_flexには含まれません。move_base_flex側が必要とする契約は、自己位置推定方式の種類ではなく次のTFが継続して解決できることです。

```text
map → odom → base_link
```

自己位置推定ノードはセンサ構成に応じて別途選び、最終結果をTFとして供給します。move_base_flexは`global_frame`（既定`map`）と`robot_frame`（既定`base_link`）を使って現在姿勢を取得します。独自の`/pose`トピックを前提にしない点に注意してください。

確認には次を使います。

```bash
ros2 run tf2_ros tf2_echo map base_link
ros2 topic hz /odom
ros2 topic hz /imu
```

NDT・EKFの原理説明は、採用するlocalization実装が変わっても利用できます。ただし具体的なtopic名、QoS、初期姿勢設定方法は、実機で選定したlocalizationパッケージのREADMEとlaunchを正として確認してください。

### 課題

**課題1**: 実機で使うlocalizationを起動し、`ros2 run tf2_ros tf2_echo map base_link`が継続して更新されることを確認してください。

**課題2**: localizationを停止したとき、`/move_base_flex/move_base`へ送ったゴールがどのoutcomeで失敗するかを確認し、TFエラーのログと対応づけてください。

**課題3**: ナビゲーション設定ファイルの`global_frame`と`robot_frame`を確認し、実機のTF treeと一致しているか図にしてください。

## 発展

- **AMCL**: ROS2 Navigation2に標準で入っているパーティクルフィルタ方式の自己位置推定です。占有格子地図に対して多数の姿勢仮説（パーティクル）をばらまき、センサ観測との一致度で重みづけ・再サンプリングを繰り返して位置を絞り込みます。NDTのような勾配法ではなく確率的サンプリングで解を探すため、初期位置が大きくずれていても収束しやすいのが特徴です。
- **robot_localization（EKF/UKF）**: 複数のオドメトリ・IMUソースを任意の組み合わせで融合できる汎用パッケージです。一般的なナビゲーションスタックではlocalization実装をmove_base_flexから分離しているため、有力な選択肢です。
- **SLAMとの違い**: 自己位置推定は「既にある地図を使って自分の位置を求める」問題で、SLAM（Simultaneous Localization and Mapping）は「地図を作りながら同時に自分の位置も求める」問題です。地図を作る段階（探索走行時）と、作った地図を使って走る段階（大会本番など）は別の問題として区別してください。混同すると「なぜ今地図を更新していないのか」のような的外れな疑問にはまります。


## おわりに

自己位置推定は「map→odomを出し続ける」という一言に尽きますが、その裏では複数のセンサの性質を理解して組み合わせる判断が積み重なっています。今回はEKFとNDTの考え方、およびmove_base_flexが要求するTF契約を見ました。次の記事では自律移動全体の中でこの自己位置推定がどう使われるかを見ていきます。わからなければチームメンバーに相談するか、関連パッケージのドキュメントを参照してください。
