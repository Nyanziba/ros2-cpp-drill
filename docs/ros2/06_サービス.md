# ROS2講習06: サービス

## はじめに

前回の[05_トピック](05_トピック.md)では、流れ続けるデータをpub/subで受け渡す方法を扱いました。今回はもう一つの通信手段、サービスを扱います。この記事が終わると、`ros2 service call`で亀を呼び出せるようになり、「トピックとサービスをどう使い分けるか」を自分の言葉で説明できるようになります。

環境はUbuntu 24.04 / ROS 2 Jazzy Jaliscoを前提とします。

- 所要時間: 自習で1〜1.5時間程度

## 講習として使う場合

### 口頭試問（模範解答つき）

**Q1. トピックとサービスの一番の違いは何ですか。**

模範解答: トピックはpublisherが流し続けるデータをsubscriberが受け取る一方通行の通信で、送信側は受信側の有無を意識しません。サービスはクライアントがリクエストを送り、サーバーがそれに対する処理をしてレスポンスを1回返す、リクエスト/レスポンス型の通信です。呼び出しには相手（サーバー）が必要で、応答が返るまでクライアントは待ちます。

**Q2. センサの値を配信する処理と、「地図をリセットする」処理は、それぞれトピックとサービスのどちらで実装すべきですか。理由も答えてください。**

模範解答: センサ値はトピックです。値は常に変化し続け、誰が見ていなくても配信し続けるべきものだからです。地図のリセットはサービスです。リセットは「たまに起きて、成功したかどうかの結果が必要な操作」であり、続けて配信する必要はなく、1回のリクエストに対して1回の応答が返れば十分だからです。

**Q3. `ros2 service call`でturtlesimの亀を増やしたとき、コマンドはどのタイミングで制御を返しましたか。それはなぜですか。**

模範解答: サーバー側の処理（亀の生成）が完了してレスポンスが返ってきたタイミングで制御が返る。サービスはリクエストを送ってから応答が返るまでブロッキングで待つ通信方式だからです。

## 本文

### サービスとは何か

サービスは「リクエストを送ると、サーバー側が何らかの処理をして、レスポンスを1回返してくれる」通信方式です。トピックが「配信し続ける」ものだったのに対して、サービスは「呼び出したら1回answerが返ってくる」関数呼び出しに近い感覚で使えます。

構造は次のようになっています。

- サービスサーバー: リクエストを受け取り、処理してレスポンスを返すノード
- サービスクライアント: リクエストを送り、レスポンスを待つノード
- サービスの型: リクエストの型とレスポンスの型のセット。`.srv`ファイルで定義されている

重要なのは、クライアントはレスポンスが返るまで待つという点です。これをブロッキングと呼びます。トピックのpublishは相手の有無に関係なく即座に処理が終わりますが、サービスコールはサーバーが応答するまで呼び出し元の処理が止まります。この性質は後で効いてきます。

### turtlesimを起動する

まだ動いていなければ、いつも通り2つの端末を用意します。

```bash
ros2 run turtlesim turtlesim_node
```

```bash
ros2 run turtlesim turtle_teleop_key
```

### サービス一覧を見る

3つ目の端末で、動いているサービスを一覧します。

```bash
ros2 service list
```

`/clear`、`/kill`、`/reset`、`/spawn`、`/turtle1/set_pen`、`/turtle1/teleport_absolute`、`/turtle1/teleport_relative`などが出てきます。トピックが`ros2 topic list`だったのに対して、サービスは`ros2 service list`です。コマンド体系がそのまま対応しているので覚えやすいはずです。

型を確認するには`type`を使います。

```bash
ros2 service type /spawn
```

`turtlesim/srv/Spawn`が返ってきます。トピックのときと同様、`ros2 service list -t`で一覧と型を同時に見ることもできます。

```bash
ros2 service list -t
```

`info`でノードとの関係を見ることもできます。

```bash
ros2 service info /spawn
```

このサービスをどのノード（turtlesim_node）が提供しているかが分かります。

### サービスの型を調べる

`/spawn`を呼ぶ前に、リクエストとレスポンスの中身を確認します。

```bash
ros2 interface show turtlesim/srv/Spawn
```

出力は次のようになります。

```
float32 x
float32 y
float32 theta
string name
---
string name
```

`---`の上がリクエスト（呼ぶときに渡す値）、下がレスポンス（返ってくる値）です。トピックの`.msg`は1つのデータ構造だけでしたが、サービスの`.srv`はリクエストとレスポンスの2つに分かれている点が構造上の違いです。

`x`, `y`, `theta`が新しい亀の座標と向き、`name`が名前です。空文字を渡すと`turtle2`のように自動で名前が振られ、レスポンスの`name`で実際に付いた名前が返ってきます。

### 課題: 亀を増やす

`/spawn`を呼んで亀を増やします。

```bash
ros2 service call /spawn turtlesim/srv/Spawn "{x: 2, y: 2, theta: 0.2, name: ''}"
```

turtlesimのウィンドウにもう1匹亀が出現し、端末には次のようなレスポンスが表示されます。

```
requester: making request: turtlesim.srv.Spawn_Request(x=2.0, y=2.0, theta=0.2, name='')

response:
turtlesim.srv.Spawn_Response(name='turtle2')
```

コマンドの構造は`ros2 service call <サービス名> <型> "<YAML形式のリクエスト>"`です。トピックの`ros2 topic pub`とほぼ同じ形なので、迷ったら05の記事に戻って比較してください。

もう一度呼ぶとどうなるか試してみましょう。`name`を指定せずに何度か`/spawn`を呼び、`ros2 topic list`で`/turtle3/pose`のようにトピックが増えていくことを確認してください。1匹の亀につき`pose`や`cmd_vel`などのトピック一式が生えることが分かります。

同じ名前を指定して呼ぶとどうなるか（エラーになるはずです）も試してみてください。エラーメッセージから何が起きているかを読み取れるようになると、後々のデバッグが楽になります。

### `/clear`と`/reset`を試す

リクエストが空のサービスも試します。

```bash
ros2 interface show turtlesim/srv/Empty
```

型自体に何もフィールドがないため、リクエストは空でよいです。

```bash
ros2 service call /clear std_srvs/srv/Empty
```

亀が描いた軌跡の線が消えます。亀自体の位置や台数は変わりません。

```bash
ros2 service call /reset std_srvs/srv/Empty
```

こちらは亀が最初の1匹・初期位置に戻ります。`/spawn`で増やした亀も消えます。`/clear`は見た目（描画）のリセット、`/reset`はシミュレーション状態そのもののリセットという違いがあります。両方空リクエストのサービスですが、サーバー側で何をリセットするかが違うということです。

### トピックとサービスの使い分け

ここまで触ってみると分かる通り、判断基準は単純です。

| 観点 | トピック | サービス |
|---|---|---|
| データの性質 | 連続的に流れ続ける | たまに起きる1回の操作 |
| 通信の向き | 一方通行（pub→sub） | 往復（リクエスト→レスポンス） |
| 待ち方 | 待たない（配信し続けるだけ） | レスポンスまでブロッキングで待つ |
| ロボコンの例 | センサ値、`cmd_vel`、ロボットの姿勢 | 「マップをリセットしろ」「キャリブレーションを実行しろ」 |

センサ値のように「今の値が知りたい、常に更新され続ける」ものはトピックです。逆に「マップをリセットしろ」「原点復帰しろ」のように、頼んだら1回実行して結果（成功/失敗）を返してほしいものはサービスです。迷ったら「これは配信し続けるべきデータか、それとも1回きりの操作か」を自問してください。

## 発展

サービスはブロッキングだという点に注意が必要です。処理に時間がかかる操作（数秒〜数分かかるナビゲーションのゴール移動など）をサービスで実装すると、クライアントは応答が返るまで固まってしまいます。長時間タスクにはフィードバック付きでキャンセルもできるアクションという仕組みが用意されており、これは[08_アクション](08_アクション.md)で扱います。今の時点では「サービスは短時間で終わる処理向き、長時間かかる処理はアクション」と覚えておいてください。
