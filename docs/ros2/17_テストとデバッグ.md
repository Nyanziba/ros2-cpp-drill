# ROS2講習17: テストとデバッグ

## はじめに

この記事を終えると、ノードが動かないときに「どこで詰まっているか」を自分で切り分けられるようになり、ROSに依存しないロジックを普通の単体テストとして書き、colconでまとめて実行できるようになります。

第2部（ノード〜アクション、Launch）はここが最後です。実装した内容が正しく動くことを確かめる手段が今回のテーマになります。

## 講習目標

- ログレベル（DEBUG/INFO/WARN/ERROR）を使い分けてノードの状態を追える
- `rqt_console`・`ros2 doctor`・`ros2 topic echo/hz`で問題箇所を上流から辿って切り分けられる
- pytest（ament_python）とgtest（ament_cmake）で最小限のテストを書き、`colcon test`で実行できる
- ROSに依存しないロジックを普通の関数に切り出す設計方針を理解する

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境（[02_環境構築](02_環境構築.md)完了）
- `rqt_console`（未インストールなら`sudo apt install ros-jazzy-rqt-console`）
- `ros2 doctor`はROS 2本体に同梱されているため追加インストール不要
- pytestが動く環境（ament_pythonパッケージのビルドにpytest系のフックが含まれるので、通常はcolcon経由で自動的に入る。手元で単体実行する場合は`pip install pytest`）
- サンプル用の壊れたノード（片方のノードだけ起動していない、トピック名をtypoした、など事前に用意して見せると効果的）

### 時間配分の目安

- ログレベルとRCLCPP_INFO/get_logger()の説明: 10分
- rqt_console/ros2 doctor/echo/hzでの切り分け演習: 20分
- pytest最小例の作成と実行: 15分
- gtest最小例の作成と`colcon test`: 15分
- ROS非依存設計の話とCIの紹介、口頭試問: 10分

### 口頭試問

**Q1. `RCLCPP_INFO`と`RCLCPP_DEBUG`の違いは何ですか。DEBUGログを仕込んでも本番では表示されないことがありますが、なぜですか。**

模範解答: どちらもログレベルの違いで、`RCLCPP_DEBUG` < `RCLCPP_INFO` < `RCLCPP_WARN` < `RCLCPP_ERROR` < `RCLCPP_FATAL`の順に重要度が上がる。ノードのデフォルトログレベルはINFO以上のことが多く、DEBUGログはデフォルトでは出力されない。表示させたい場合は`ros2 run <package> <node> --ros-args --log-level debug`のようにログレベルを明示的に下げる必要がある。本番でDEBUGログを常時出しっぱなしにすると出力量が膨らんで肝心のWARN/ERRORが埋もれるので、普段はINFO以上にしておくのが基本。

**Q2. トピックが繋がっていないとき、上流から辿るとはどういう手順ですか。具体的に説明してください。**

模範解答: まず`ros2 node list`で目的のノードが立っているか確認する。立っていなければノード自体が起動に失敗しているので、そのノードの標準出力・ログを見る。ノードが立っているなら`ros2 topic list`で該当トピックが存在するか確認し、存在しなければpublisher側のコードでトピック名をtypoしていないか確認する。トピックが存在するなら`ros2 topic info -v <topic>`でpublisher/subscriberの数とQoSを確認し、`ros2 topic hz <topic>`で実際にデータが流れているかを見る。流れていればsubscriber側のコールバックの中身を疑う、という順で「データの発生源に近い方から」確認していく。逆に受信側のコードから疑ってしまうと、そもそもpublisherが動いていないだけの単純なミスに気づくのが遅れる。

**Q3. `ros2 doctor`は何を確認してくれるツールですか。**

模範解答: ROS 2環境自体の健全性（インストールされているパッケージのバージョン整合性、ネットワーク設定、`ROS_DOMAIN_ID`の設定状況、稼働中のトピックの警告など）をまとめて診断してくれるツール。ノード固有のロジックのバグは見つけられないが、「そもそも環境がおかしい」という可能性を早い段階で潰すのに使う。`ros2 doctor --report`で詳細レポートが出せる。

**Q4. なぜROSに依存しないロジックを普通の関数に切り出すのですか。**

模範解答: `rclpy`や`rclcpp`のノードを介したテストはノードの起動・実行が必要で、書くのも実行するのも重くなる。純粋な計算（経路の曲率を求める、姿勢からyaw角を復元する、waypointsのYAMLをパースするなど）を普通の関数として切り出しておけば、ROSを一切起動せずに素のpytestやgtestで高速に検証できる。副次的に、ロジックの再利用や他プロジェクトへの移植もしやすくなる。

## 本文

### 学習内容：ログレベルを使い分ける

学習内容：`RCLCPP_INFO`系マクロ（C++）と`self.get_logger()`（Python）でログレベルを意識して書く。

準備：C++・Pythonどちらか普段使っている方でノードを1つ用意しておきます。

内容：

ROS2のログには5段階のレベルがあります。重要度の低い方から`DEBUG < INFO < WARN < ERROR < FATAL`の順です。C++では次のように書きます。

```cpp
RCLCPP_DEBUG(this->get_logger(), "cmd_vel computed: v=%.2f w=%.2f", v, w);
RCLCPP_INFO(this->get_logger(), "goal reached");
RCLCPP_WARN(this->get_logger(), "path is empty, skipping this cycle");
RCLCPP_ERROR(this->get_logger(), "failed to load costmap: %s", e.what());
```

Pythonでは`self.get_logger()`から同名のメソッドを呼びます。

```python
self.get_logger().debug(f"cmd_vel computed: v={v:.2f} w={w:.2f}")
self.get_logger().info("goal reached")
self.get_logger().warn("path is empty, skipping this cycle")
self.get_logger().error(f"failed to load costmap: {e}")
```

DEBUGは開発中の詳細な状態確認、INFOは「正常に動いている節目」、WARNは「異常ではないが気にすべき状態」、ERRORは「処理が続けられない失敗」に使うのが基本です。全部INFOで埋めると、実際に重要なログが埋もれて見つけられなくなります。

ヒント：ログレベルはノード起動時に`--ros-args --log-level debug`で変更できます。普段はINFO以上、デバッグ中だけDEBUGを覗く、という使い方をしてください。

### 学習内容：rqt_consoleでログを一覧する

学習内容：複数ノードのログを1画面にまとめて見る。

準備：適当なノードをいくつか起動しておきます。turtlesim + teleopでも構いません。

内容：

ターミナルを何枚も並べてログを目で追うのは大変です。`rqt_console`を起動すると、動いているノードのログが1つのGUIウィンドウに集約され、レベルでフィルタしたり検索したりできます。

```bash
rqt_console
```

複数ノードが絡む問題（「このノードのWARNがどのタイミングで出ているか」を他のノードの動きと合わせて追いたい、など）では、ターミナルを1枚ずつ追うよりこちらの方が速いです。

### 学習内容：ros2 doctorで環境を疑う

学習内容：ノードのロジックより先に環境自体を疑う手順を知る。

準備：特になし。

内容：

「昨日まで動いていたのに今日は動かない」「他のPCでは動くのに自分のPCでは動かない」というときは、コードのバグより環境の違いを疑った方が早いことがあります。

```bash
ros2 doctor
```

`ros2 doctor --report`でより詳細な情報（OS、ROSディストリビューション、ネットワーク設定など）が出ます。`ROS_DOMAIN_ID`が意図せず他の環境と被っている、必要なパッケージのバージョンが噛み合っていない、といった「コードを読んでも気づけない」種類の問題を先に潰しておくと、後のデバッグが無駄に長引きません。

### 学習内容：上流から辿って切り分ける

学習内容：「どのノードまでデータが来ているか」を発生源から追う切り分け手順を身につける。

準備：意図的に壊したノード構成（片方のノードを起動していない、トピック名をtypoしている等）を用意しておくと演習になります。

内容：

トピックが繋がらない、値がおかしいというとき、闇雲にコードを読むより先に、データの流れを上流から辿るのが確実です。手順は次の通りです。

1. `ros2 node list` — 目的のノードは立っているか
2. `ros2 topic list` — 目的のトピックは存在するか
3. `ros2 topic info -v <topic>` — publisher/subscriberの数とQoSは噛み合っているか
4. `ros2 topic hz <topic>` — 実際にデータが流れているか
5. `ros2 topic echo <topic>` — 流れている値そのものは正しいか

この順番が重要です。受信側のコールバックから疑い始めると、そもそもpublisherが起動していないだけの単純な原因を見逃しがちです。データの発生源に近い方から確認すれば、「どこまでは正常で、どこから壊れているか」の境界がすぐに見つかります。

**練習問題**: teleopを起動せずに`ros2 topic echo /turtle1/cmd_vel`を実行すると何も表示されません。この状態から上の5手順を順に実行し、「正常」と判断できる境界がどこかを説明してください。

<details><summary>解答</summary>

`ros2 node list`ではturtlesim_nodeが表示される（正常）。`ros2 topic list`には`/turtle1/cmd_vel`が表示される（正常、トピック自体は定義されている）。`ros2 topic info -v /turtle1/cmd_vel`ではPublisher count: 0と出る。ここが境界で、トピックは存在するがpublisherが1つもいない状態だとわかる。`hz`も`echo`も何も表示されないのは当然の結果であり、これらの手順で初めて調べる必要はない。原因は「teleopを起動していない」というだけで、コードのバグではない。

</details>

### 学習内容：pytestで最小限の単体テストを書く（ament_python）

学習内容：ament_pythonパッケージにpytestベースの単体テストを追加する。

準備：ament_pythonのパッケージ構成（`setup.py`、`<package>/`、`test/`ディレクトリ）を用意します。

内容：

ament_pythonパッケージでは`test/`ディレクトリに`test_*.py`を置くと、`colcon test`が自動でpytestを実行してくれます。ROSに依存しない関数のテスト例です。

```python
# test/test_yaw_utils.py
import math
import pytest

from my_package.yaw_utils import yaw_to_quaternion, yaw_from_quaternion


def test_yaw_to_quaternion_zero():
    assert yaw_to_quaternion(0.0) == pytest.approx((0.0, 0.0, 0.0, 1.0))


def test_yaw_round_trip():
    for yaw in [0.0, 0.5, -0.5, math.pi - 0.01]:
        qx, qy, qz, qw = yaw_to_quaternion(yaw)
        assert yaw_from_quaternion(qx, qy, qz, qw) == pytest.approx(yaw, abs=1e-9)
```

`yaw_to_quaternion`と`yaw_from_quaternion`は`rclpy`を一切importしていない普通の関数です。ノードを起動せずにこのテストだけ単体で走らせられます。

```bash
pytest test/test_yaw_utils.py -v
```

### 学習内容：gtestで最小限の単体テストを書く（ament_cmake）

学習内容：ament_cmakeパッケージにGoogleTestベースの単体テストを追加する。

準備：ament_cmakeパッケージ構成（`CMakeLists.txt`、`src/`、`test/`）を用意します。

内容：

C++側はGoogleTest（gtest）を使います。`CMakeLists.txt`に次のような設定を追加します。

```cmake
if(BUILD_TESTING)
  find_package(ament_cmake_gtest REQUIRED)
  ament_add_gtest(test_path_utils test/test_path_utils.cpp)
  target_link_libraries(test_path_utils path_utils)
endif()
```

テスト本体はこうなります。

```cpp
// test/test_path_utils.cpp
#include <gtest/gtest.h>
#include "my_package/path_utils.hpp"

TEST(PathUtilsTest, CurvatureOfStraightLineIsZero)
{
  std::vector<Point2D> straight_path = {{0.0, 0.0}, {1.0, 0.0}, {2.0, 0.0}};
  EXPECT_NEAR(computeMaxCurvature(straight_path), 0.0, 1e-9);
}

TEST(PathUtilsTest, EmptyPathReturnsZero)
{
  std::vector<Point2D> empty_path;
  EXPECT_EQ(computeMaxCurvature(empty_path), 0.0);
}
```

`computeMaxCurvature`は`rclcpp::Node`を継承していない普通の関数として`path_utils.hpp`に切り出してあります。ノードを起動する必要がないので、ビルドが終わればミリ秒単位で結果が出ます。

### 学習内容：colcon testでまとめて実行する

学習内容：ワークスペース内のテストを一括実行し、結果を確認する。

準備：pytest・gtestのテストを含むパッケージがビルド済みであること。

内容：

パッケージを個別にビルドしたら、テストは`colcon test`でまとめて実行します。

```bash
colcon build
colcon test
```

結果の詳細（失敗したテストの中身）は`colcon test-result`で確認します。

```bash
colcon test-result --verbose
```

`--verbose`を付けないと「失敗した」という事実しか出てこず、どのアサーションで落ちたかがわからないので、テストが失敗したら必ず`--verbose`を付け直してください。特定のパッケージだけテストしたい場合は`colcon test --packages-select <package_name>`と絞り込めます。

**練習問題**: CIのスクリプトに`colcon test`と書いておいたのに、テストが失敗しているのにCIがグリーンになってしまいました。なぜでしょうか。

<details><summary>解答</summary>

`colcon test`は**テストが失敗しても終了コード0を返す**からです。CIは終了コードで合否を判断するので、これでは失敗を検知できません。

実際に、わざと落ちるgtestを1つ入れたパッケージで確認するとこうなります。

```
Finished <<< failpkg [0.14s]	[ with test failures ]

Summary: 1 package finished [0.29s]
  1 package had test failures: failpkg
$ echo $?
0
```

画面には`[ with test failures ]`と`1 package had test failures`が出ているので、人間が読めば気づけます。しかし終了コードは0です。`colcon test`にとっては「テストの実行というジョブ自体は完遂した」ので成功、という扱いなのです。

対処は2つあります。

```bash
# (a) colcon test に明示的にフラグを付ける（終了コード1になる）
colcon test --return-code-on-test-failure

# (b) 実行と判定を分ける。test-result は失敗があれば終了コード1を返す
colcon test
colcon test-result --verbose
```

CIでは(a)か(b)のどちらかを必ず入れてください。`colcon test`だけを書いたCIは、何も検証していないのと同じです。

また`colcon test-result`に`--verbose`を付けると、どのアサーションで落ちたかまで表示されます。付けないと「1 failure」という事実しか出ません。

```
build/failpkg/test_results/failpkg/t.gtest.xml: 2 tests, 0 errors, 1 failure, 0 skipped
- failpkg.A DeliberatelyFails (src/failpkg/test/t.cpp:3)
  <<< failure message
    Expected equality of these values:
      1
      2
    これは意図的な失敗
  >>>
```

</details>

### 学習内容：ROSに依存しないロジックを切り出す設計

学習内容：テストしやすい設計方針を理解する。

準備：特になし。

内容：

ここまでのpytest・gtestの例に共通する点があります。テスト対象の関数が`rclpy.node.Node`や`rclcpp::Node`を継承していない、ただの関数だということです。ROSのノードをテストしようとすると、`rclpy.init()`やノードの起動、executorのspinが必要になり、テスト1つ書くだけで一気に重くなります。

そこで、ノードのコールバック内で計算しているロジック（経路の曲率計算、座標変換、YAMLのパース、状態遷移の判定など）は、可能な限りノードのクラスから外に出して普通の関数やクラスとして書くのが良い設計です。ノード側はその関数を呼んでpublish/subscribeするだけの薄い層にします。こうすればロジックはROSを起動せずにテストでき、ノード側は「ちゃんと繋がっているか」だけを見ればよくなります。

多くのナビゲーションライブラリがROSに一切依存しないC++/Pythonライブラリとして作られているのも、この考え方が理由の一つです。move_base_flexのプラグインとして薄くラップする層と、経路計画や高度な計算アルゴリズムなどを行う層を分けているからこそ、ROSを一切起動しない単体テストがそのまま書けます。このあたりの分離は第4部の発展編で詳しく扱います。

> コラム: 高度なナビゲーションライブラリのテストは実際に「純粋単体テスト → 状態遷移シナリオテスト → シミュレータE2E」の三層構造になっています。ROS非依存の関数を土台にして、その上にどんどん統合度の高いテストを積んでいく発想です。

### 学習内容：実際のプロジェクトでの実例

学習内容：実際のロボティクスプロジェクトでテストとCIがどう組まれているかを見る。

準備：特になし。

内容：

本格的なナビゲーションプロジェクトでは、`tests/`に`test_core_smoke.cpp`や`test_planning.cpp`などのgtestを、`tests_python/`に`test_smoke.py`や`test_bindings.py`などのpytestを分けて置いています。ローカル実行の手順は`docs/contributing/testing.md`にまとまっていて、C++側は

```bash
cmake -S . -B build -DNAV_CORE_BUILD_TESTS=ON
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Python側は

```bash
pip install '.[sim,test]'
MPLBACKEND=Agg pytest
```

という手順です（`docs/contributing/testing.md`より）。テスト戦略として「純粋単体テスト（GoogleTest/pytest）→ 状態管理シナリオテスト → シミュレータE2E」の三層構造を明記しているのも同じファイルにあります。

プラグインレイヤ側には`tools/test/test_utils.py`、`sim/test/test_kinematics.py`などにpytestが置かれています。CIは`.github/workflows/ci.yml`にGitHub Actionsとして定義されており、コアライブラリのワークフローでは複数のプラットフォーム（Ubuntu/macOS）や機能フラグ（MPPI ON/OFF など）の組み合わせを行列（matrix）で掛け合わせてビルドし、`ctest --test-dir build --output-on-failure`でC++テストを、`pytest`でPythonテストを実行しています。プラグインレイヤのワークフローでは`pytest tools/test -v`のようにパッケージごとにpytestを回すジョブと、実際にROS 2ノードを起動してゴールに到達できるかを確認する`sim-e2e`ジョブが分かれています。CIで人がpushするたびにテストを自動実行しておけば、レビュー前に壊れているコードに気づけます。

## 発展

今回は`colcon test`単体の話に留めましたが、実際のCIではビルドキャッシュ（`actions/cache@v4`でccacheやビルド済みの依存パッケージをキャッシュしている）や、シミュレータを使ったE2Eテストまで組まれています。GitHub Actions自体の書き方や、YAMLのvalidationをCIに組み込む発想（設定ファイルのスキーマ検証ジョブなど）は、それ自体を掘るとCI/CD講習1本分になります。ここでは「実際のロボティクスプロジェクトでどう使われているか」の紹介に留め、CIの構築方法自体は別記事に譲ります。


## おわりに

デバッグは「どこまで正常か」を上流から確認していくだけで、多くの場合は原因の見当がついてきます。テストは書くのが面倒に見えても、ROS非依存のロジックを切り出しておけば実はそう手間はかかりません。今回で第2部は終わりです。
