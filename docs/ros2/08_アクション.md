# ROS2講習08: アクション

## はじめに

トピックとサービスは前回までで触りました。この記事では3つ目の通信手段「アクション」を扱います。この記事が終わると、キャンセル可能な長時間タスクをコマンドラインから投げて、進行状況をリアルタイムに受け取れるようになります。

前提: [07_パラメータ](07_パラメータ.md)を終えていること。turtlesimが動く環境（[03_turtlesimとrqtで感覚を掴む](03_turtlesimとrqtで感覚を掴む.md)参照）が必要です。

## 講習目標

- アクションがgoal/feedback/resultの3点セットで構成されていることを説明できる
- `ros2 action list` / `ros2 action info` でアクションサーバの情報を調べられる
- `ros2 action send_goal` でgoalを送り、`--feedback`で進行状況を受け取れる
- トピック・サービス・アクションを、要件に応じて選び分けられる

所要時間の目安は1時間です。対象は新入生。前提知識はトピック・サービスの基本操作です。

## 講習として使う場合

準備物:

- Ubuntu 24.04 / ROS 2 Jazzy Jalisco がインストール済みの環境
- `ros-jazzy-turtlesim` パッケージ（`sudo apt install ros-jazzy-turtlesim` で導入済みのはず）
- ターミナル2枚以上を並べられる環境（tmux推奨だが必須ではない）

口頭試問（質問と模範解答）:

Q1. トピック・サービス・アクションはそれぞれどう使い分けますか。

A1. トピックは継続的なデータの流れ（センサ値、cmd_velなど）に使う。サービスは即座に終わる単発の処理（設定変更、状態の問い合わせ）に使う。アクションは完了までに時間がかかり、途中経過を知りたい、かつ中断したくなる可能性がある処理（経路走行、アーム動作など）に使う。判断基準は「処理に時間がかかるか」と「キャンセルしたいか」の2点。

Q2. アクションのgoal/feedback/resultはそれぞれ何を運びますか。

A2. goalはクライアントからサーバへの依頼内容（例: 「1.57ラジアン回転して」）。feedbackはサーバからクライアントへの進行状況の継続的な通知（例: 「現在の残り角度」）。resultはタスク完了時にサーバから返る最終結果（例: 「実際に回転した角度」）。goalとresultは1回きり、feedbackは処理中に何度も送られる点が違う。

Q3. サービスではなくアクションを使うべき場面を1つ挙げてください。

A3. 例えば経路走行。目的地に着くまで数秒〜数十秒かかり、走行中の残距離を知りたく、障害物を検知したら止めたい（キャンセルしたい）。サービスだと呼び出し元がブロックされたまま結果を待つだけになり、進行状況もキャンセルも扱えない。

時間配分の目安:

- 概念説明（goal/feedback/result、使い分け表）: 15分
- `ros2 action list/info` での調査: 10分
- turtlesim回転課題: 25分
- 口頭試問: 10分

## 本文

### アクションとは何か

学習内容: アクションの3点セット構成と、トピック・サービスとの違い

準備: 特になし（turtlesimは次節で使います）

内容:

トピックは一方向のデータの流れ、サービスは同期的な単発リクエストでした。アクションはこの2つを組み合わせたような構造をしていて、以下の3つの通信要素からできています。

- goal: クライアントがサーバに送る依頼内容。「これをやってほしい」というパラメータ
- feedback: サーバがクライアントに継続的に送る進行状況。処理が終わるまで何度も送られる
- result: サーバがクライアントに送る最終結果。処理完了（またはキャンセル、失敗）時に1回だけ送られる

内部的には、アクションはトピックとサービスの組み合わせで実装されています。goalの送信と結果の取得にはサービスに似た仕組み（goal受付、result取得）を使い、feedbackの配信にはトピックを使っています。`ros2 topic list`でアクション実行中に覗くと、`/turtle1/rotate_absolute/_action/feedback`のようなトピックが見えるのはこのためです。

サービスとの決定的な違いは2つあります。ひとつはfeedbackの有無、もうひとつはキャンセル可能かどうかです。サービスはリクエストを送ったら結果が返るまで待つしかありませんが、アクションは処理の途中経過を受け取れるうえ、途中でキャンセルもできます。

### トピック・サービス・アクションの使い分け

学習内容: 通信手段の選定基準

内容:

3つの使い分けを表にまとめます。

| 通信手段 | 用途 | 応答 | 例 |
|---|---|---|---|
| トピック | 継続的なデータの流れ | なし（配信のみ） | センサ値、cmd_vel |
| サービス | 即座に終わる単発の処理 | 同期的に1回 | パラメータの取得、状態の問い合わせ |
| アクション | 時間のかかる処理、キャンセルしたい処理 | goal受付→feedback（複数回）→result | 経路走行、アーム動作 |

判断基準は「処理に時間がかかるか」と「途中でやめたくなるか」の2点です。時間がかからず即座に終わるならサービス、時間はかかるが放っておいて後で結果だけ見ればいいならトピックで状態を流す設計もあり得ますが、進行状況の把握とキャンセルの両方が必要ならアクション一択です。

### ros2 action list / info でアクションサーバを調べる

学習内容: 稼働中のアクションサーバの調べ方

準備: turtlesimを起動します。

```bash
ros2 run turtlesim turtlesim_node
```

内容:

別のターミナルで、稼働中のアクションを一覧できます。

```bash
ros2 action list
```

`/turtle1/rotate_absolute`が表示されます。詳細情報は`info`で見られます。

```bash
ros2 action info /turtle1/rotate_absolute -t
```

`-t`をつけると、アクションの型（`turtlesim/action/RotateAbsolute`）も表示されます。アクションサーバ・クライアントの数もここで確認できます。

アクションの型定義（goal/feedback/resultの内訳）は`ros2 interface show`で確認します。

```bash
ros2 interface show turtlesim/action/RotateAbsolute
```

出力は以下のような構造になっています（`---`で3区分に分かれている点に注目してください）。

```
float32 theta
---
float32 delta
---
float32 remaining
```

上から順にgoal（目標角度theta）、result（実際に回転した角度delta）、feedback（残り角度remaining）です。この`---`区切りはmsg/srv/actionファイルの共通の書式で、アクションはgoal/result/feedbackの3ブロックを持つ点がサービス（goal/resultの2ブロック相当）と違います。

### 練習問題: turtlesimを回転させる

学習内容: `ros2 action send_goal`によるgoal送信とfeedback受信

準備: turtlesimが起動していること（前節で起動済みのはず）。

内容:

`/turtle1/rotate_absolute`にgoalを送って、亀を指定角度まで回転させます。

```bash
ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.57}" --feedback
```

`--feedback`をつけると、処理中のfeedback（remaining、残り角度）がターミナルに流れ続けます。つけない場合はgoal送信後に何も表示されず、result（delta、実際に回転した角度）だけが最後に返ってきます。

ヒント: thetaの単位はラジアンです。1.57はおよそ90度（π/2）です。一周させたいなら6.28（2π）近辺を指定してみましょう。

<details markdown="1"><summary>解答（実行結果の例）</summary>

```
Waiting for an action server to become available...
Sending goal:
     theta: 1.57

Goal accepted with ID: xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Feedback:
    remaining: 1.2999999523162842

Feedback:
    remaining: 0.9099999666213989

...(remainingが0に近づいていく)...

Result:
    delta: -1.5700000524520823

Goal finished with status: SUCCEEDED
```

亀がその場で90度回転すれば成功です。deltaが負の値になるのは、turtlesimの回転方向の符号の都合です（実行環境や初期姿勢によって符号は変わります）。remainingが徐々に減っていく様子が見えていれば、feedbackが正しく受信できています。

</details>

キャンセルも試してみましょう。goal送信中のターミナルで`Ctrl+C`を押すと、クライアント側の待受は止まりますが、サーバ側で処理中のgoal自体をキャンセルするには別途キャンセル要求を送る必要があります。コマンドラインからの明示的なキャンセルは`ros2 action`サブコマンドには用意されていないため、この段階では「feedbackを見ながらCtrl+Cで待受をやめる」だけを体験しておけば十分です。実際にサーバ側の処理を止めるキャンセル処理の実装は、パッケージ開発編（[16_アクションサーバの実装](16_アクションサーバの実装.md)）で扱います。

## 発展

`rqt`のActionプラグイン（rqt_action系）を使うと、GUIからgoal送信とfeedback監視ができます。コマンドラインに慣れたら触ってみてください。

アクションの実装側（サーバをどう書くか、キャンセル処理をどう受けるか）は本記事では扱いません。第2部の[16_アクションサーバの実装](16_アクションサーバの実装.md)で詳しく取り上げます。

このアクションの仕組みは、自律移動スタックで実際に使われています。move_base_flexが「この経路を走れ」という依頼をExePathアクションで受け取り、走行中は残距離をfeedbackとして返し続けます。goal/feedback/resultの構造がそのまま「経路とパラメータ」「残距離」「走行結果」に対応している形です。
