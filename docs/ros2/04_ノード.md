# ROS2講習04: ノード

## はじめに

前回はturtlesimを動かして、ノードとトピックが画面上でどう繋がっているかを眺めました。今回はその「ノード」という単位そのものに焦点を当てます。この記事が終わると、ノードが何を表しているかを人に説明できるようになり、`ros2 run`や`ros2 node`系のコマンドを自分で組み立てて使えるようになります。

## 講習目標 / 講習の進め方

- 所要時間: 40分程度（自習なら1時間弱を想定）
- 対象: [03_turtlesimとrqtで感覚を掴む](03_turtlesimとrqtで感覚を掴む.md)まで完了した新入生
- 前提知識: ROS 2 Jazzy Jalisco導入済み、turtlesimパッケージが動く状態（`ros2 run turtlesim turtlesim_node`が通ること）

## 講習として使う場合

準備物:
- Ubuntu 24.04 + ROS 2 Jazzy Jalisco がインストール済みのPC（各自）
- `turtlesim`パッケージ（`sudo apt install ros-jazzy-turtlesim`で入る。ros-baseだけの環境では入っていないことがあるので事前確認）
- ターミナルを2枚以上並べて操作できる環境（tmuxでもタブでもよい）

口頭試問（質問と模範解答をセットで記載）:

1. Q. 「1つのノードに何でも機能を詰め込んでもいいのに、なぜ分けるのか」
   A. 責務を分けると、ノード単位でテスト・再起動・置き換えができるようになるため。例えば経路計画ノードだけ落として直すあいだ、自己位置推定ノードは動かし続けられる。逆に1つのノードに全部詰めると、どこかで例外が起きた瞬間に全機能が止まる。
2. Q. 「`ros2 node list`に自分の起動したノードが出てこない。何を確認するか」
   A. まずそのノードが本当に起動し続けているか（クラッシュして終了していないか）を確認する。次に別のROS_DOMAIN_IDで動いていないか、ネットワーク越しのマシンで動かしていないかを確認する。同一マシンでも環境変数`ROS_DOMAIN_ID`が食い違うと互いに見えない。
3. Q. 「`--remap __node:=xxx`と`ros2 node list`上の名前が食い違うことはあるか」
   A. ある。remapはノード生成時の名前を上書きするコマンドラインオプションであり、パッケージ内でコードとして名前を決めている場合（`Node("固定名")`のように書いている場合）は無視されることがある。実際に動かして`ros2 node info`で確認する習慣をつけさせること。

時間配分の目安:
- ノードの概念説明: 5分
- `ros2 run`/`ros2 node list`/`ros2 node info`の実演: 10分
- remapping課題: 15分
- 口頭試問と責務分割の議論: 10分

## 本文

### 課題1: ノードを起動して確認する

学習内容: ノードとは1つの責務を持って動き続けるプロセスであること。`ros2 run`でノードを起動し、`ros2 node list`で存在を確認する手順。

準備: ターミナルを2枚開く。

内容:

ROS 2で言う「ノード」は、計算を実行する1つのプロセスです。カメラから画像を読む、モータに指令値を送る、自己位置を推定する、といった処理をそれぞれ独立したプロセスとして立ち上げ、トピックやサービスを介して繋ぎます。プロセスなので、OSから見れば普通の実行ファイルと同じです。`ps aux`で見ればちゃんとPIDを持ったプロセスとして存在しています。

1枚目のターミナルでturtlesimのノードを起動します。

```bash
ros2 run turtlesim turtlesim_node
```

これで亀が表示されたウィンドウが立ち上がります。このプロセスが終了する（Ctrl+Cで殺す）まで、このターミナルは占有されます。

2枚目のターミナルで、いま動いているノードの一覧を見ます。

```bash
ros2 node list
```

```
/turtlesim
```

`/turtlesim`という名前のノードが1つ動いていることが分かります。先頭の`/`はグローバルな名前空間を表しています（名前空間については本記事では扱いません。名前空間を切ってロボットを複数台区別する話は発展的な内容として別途扱います）。

さらに詳しい情報を見るには`ros2 node info`を使います。

```bash
ros2 node info /turtlesim
```

出力にはこのノードが持つPublisher・Subscriber・Service・Actionの一覧が並びます。turtlesimノードは`/turtle1/cmd_vel`をSubscribeし、`/turtle1/pose`をPublishし、`/turtle1/teleport_absolute`などのServiceを提供している、といった情報がそのまま読めます。前回rqt_graphで見た絵の中身が、コマンドラインからも同じ粒度で確認できるということです。

注意: `ros2 node info`には、ノード名を先頭の`/`付きのフルネームで渡してください。`/`を省略して`ros2 node info turtlesim`とすると`Unable to find node 'turtlesim'`というエラーになり、動きません（Jazzyで確認済み）。`ros2 node list`の出力をそのままコピーすれば`/`付きになります。

### 課題2: remappingでノード名を変える

学習内容: ノード名やトピック名は起動時に上書きできること（remapping）。1つのパッケージから複数のノードを別名で立てる考え方。

準備: 課題1のノードはCtrl+Cで一度終了しておきます。

内容:

同じ`turtlesim_node`という実行ファイルから、名前だけ変えたノードを起動してみます。

```bash
ros2 run turtlesim turtlesim_node --ros-args --remap __node:=my_turtle
```

`ros2 node list`で確認すると、今度は`/turtlesim`ではなく`/my_turtle`という名前で登録されています。

```bash
ros2 node list
```

```
/my_turtle
```

`--ros-args --remap __node:=新しい名前`が、ノード名を上書きするコマンドラインオプションです。`__node`はROS 2が特別扱いする予約された名前で、これを使うとソースコードを一切書き換えずにノード名だけ差し替えられます。

これがなぜ嬉しいかというと、同一パッケージのノードを複数立ち上げて名前が衝突するのを避けたいときに使えるからです。ここは誤解しやすいところですが、**ROS 2は同じ名前のノードが2つ存在するのを止めてくれません。** 実際に同名のノードを2つ起動すると両方とも普通に動き続け、`ros2 node list`にも重複して並びます。出るのは次の警告だけです。

```
WARNING: Be aware that there are nodes in the graph that share an exact name, which can have unintended side effects.
/turtlesim
/turtlesim
```

エラーにならないぶん気づきにくく、通信先の解決が不安定になって原因不明の挙動につながります。だからこそ、こちらで名前を分けておく必要があります。複数台の亀を動かす講習（発展編で扱う予定）では、この`--remap __node:=`を亀ごとに変えて使うことになります。

トピック名も同様にremapできます。試しにcmd_velのremapも一緒にやってみましょう。

```bash
ros2 run turtlesim turtlesim_node --ros-args --remap __node:=my_turtle --remap /turtle1/cmd_vel:=/my_turtle/cmd_vel
```

`ros2 node info /my_turtle`で確認すると、Subscribeしているトピック名が`/my_turtle/cmd_vel`に変わっているはずです。ノード名とトピック名は別々に管理されている、という点を意識してください。

<details markdown="1"><summary>解答（うまくremapできているかの確認方法）</summary>

`ros2 node info /my_turtle`を実行し、出力中の`Subscribers:`セクションに`/my_turtle/cmd_vel: geometry_msgs/msg/Twist`という行が現れていればremap成功です。元の`/turtle1/cmd_vel`が残っていたらremapのオプション名（`--remap`の後ろのコロン区切りの書式`旧名:=新名`）を見直してください。

</details>

### ロボコンでの責務分割の考え方

ここまではturtlesimという1個のノードの話でしたが、実際のロボットでは複数のノードに機能を分けて動かします。例えば自己位置推定・経路計画・モータ指令をそれぞれ別ノードにする構成を考えます。

なぜ分けるのか。理由は「独立にテスト・再起動できる」ことにあります。経路計画のアルゴリズムを直している最中に自己位置推定ノードまで一緒に落ちてしまうと、デバッグ中にロボットの姿勢そのものが分からなくなり、原因の切り分けが難しくなります。ノードを分けておけば、経路計画ノードだけ`Ctrl+C`して直して再起動すれば済みます。自己位置推定ノードはそのまま動き続けているので、直した直後にすぐ経路計画の動作確認に移れます。

もう1つの理由は交換可能性です。経路計画をA\*から別のplannerへ変えたい、controllerをLookaheadからMPPIへ変えたい、あるいは自己位置推定を実機用のものへ置き換えたい場合も、インターフェースが同じなら対象だけを差し替えられます。これは前回までに見た「疎結合」の実利的な側面です。

一方で、分けすぎるとノード間通信のオーバーヘッドや、起動順序の管理が面倒になります。何でも1ノードにまとめるか全部バラバラにするかは極端で、実際のロボット開発では「独立に検証したい・独立に落としたい単位」で切るのが実務上のバランスです。

## 発展

1ノード1プロセスというROS 2の基本モデルには、実は例外があります。**component（コンポーネントノード）**という仕組みを使うと、複数のノードを同じプロセス内に共存させられます。同じプロセスに載せたうえでプロセス内通信（intra-process communication）を有効にすると、ノード間のデータをコピーなしで受け渡せるようになり、画像やLiDARの点群のような大きなデータを流すときの負荷を削減できます。

ここで1つ注意があります。**componentにしただけでは自動的にコピーが消えるわけではありません。** `rclcpp::NodeOptions`の`use_intra_process_comms`は既定で`false`（`/opt/ros/jazzy/include/rclcpp/rclcpp/node_options.hpp`）なので、明示的に有効化しない限り、同一プロセスに載っていても通信はDDSを経由します。公式の`composition_demo_launch.py`も有効化していないため、あのlaunchで起動したtalker/listenerは同一プロセスにいながらDDS越しに通信しています。有効にするには、コンテナに読み込ませる時点で`NodeOptions`に流し込みます。

```python
ComposableNode(
    package='composition',
    plugin='composition::Talker',
    name='talker',
    extra_arguments=[{'use_intra_process_comms': True}],   # これが無いと効かない
)
```

CLIから読み込む場合は`ros2 component load /ComponentManager composition composition::Talker -e use_intra_process_comms:=true`のように渡します。つまりcomponentは「同一プロセスに載せる」という**前提条件を満たす仕組み**であって、ゼロコピー自体は別途オプトインする、という関係です。

今回は「そういう仕組みが存在する」というところまでに留めます。componentの実装は`rclcpp_components`パッケージやComposableNodeの書き方など、これ単独で1記事になる規模のテーマなので、別記事として扱う予定です。
