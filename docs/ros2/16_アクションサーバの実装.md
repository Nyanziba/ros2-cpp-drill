# ROS2講習16: アクションサーバの実装

## はじめに

この記事を終えると、アクション（Action）の定義ファイルを自分で書き、ActionServer/ActionClientをPythonで実装し、フィードバックの受信とキャンセルを一通り扱えるようになります。

前提は[06_サービス](06_サービス.md)を読み終えていることです。アクションはサービスに「途中経過の報告」と「キャンセル」を足したものなので、サービスの同期リクエスト/レスポンスがわかっていないと差分が見えません。

## 講習目標

- `.action`ファイル（goal/result/feedbackの3セクション）を自分で書ける
- `rclpy.action.ActionServer`を実装し、`execute_callback`内で`publish_feedback`と`succeed`を使い分けられる
- `rclpy.action.ActionClient`で`send_goal_async`からgoal応答・feedback・resultまでの流れを実装できる
- キャンセル要求を受け取り、`CancelResponse.ACCEPT`と`is_cancel_requested`で安全に処理を打ち切れる

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境（[02_環境構築](02_環境構築.md)完了）
- `ros-jazzy-example-interfaces`（Fibonacciアクションの型を含む。未インストールなら`sudo apt install ros-jazzy-example-interfaces`）
- 自作アクション定義をビルドするための`ament_cmake`パッケージ一式（[15_パラメータとlaunchの実践](15_パラメータとlaunchの実践.md)でColcon workspaceが手元にあることを前提とする）
- ターミナルを3枚（サーバ・クライアント・`ros2 action`確認用）

### 時間配分の目安

- アクションのpub/sub+サービス的な構造の説明: 10分
- `.action`ファイルとrosidl設定: 15分
- ActionServer実装（`execute_callback`）: 20分
- ActionClient実装とフィードバック確認: 15分
- キャンセル処理と口頭試問: 15分

### 口頭試問

**Q1. トピック・サービス・アクションの違いを一言で説明してください。**

模範解答: トピックは非同期の一方向配信、サービスは同期的なリクエスト/レスポンス、アクションは非同期のゴール指向通信で、実行に時間がかかる処理に対して途中経過（フィードバック）とキャンセルを提供する。サービスを「時間のかかる処理」に使うとクライアントが応答をブロックして待ち続けてしまうため、そこにアクションが必要になる。

**Q2. `execute_callback`の中で`goal_handle.succeed()`を呼ばずに`return`してしまうとどうなりますか。**

模範解答: アクションのステータスが`SUCCEEDED`に遷移しないため、クライアント側は結果を受け取れても、goalの状態は`EXECUTING`のまま止まって見える。`succeed()`（または失敗時は`abort()`、キャンセル時は`canceled()`）を明示的に呼んで状態を確定させることが必須で、呼び忘れはこのパターンで一番多いミス。

**Q3. キャンセルを受け付けるには何を実装すればよいですか。**

模範解答: `ActionServer`のコンストラクタに`cancel_callback`を渡し、そこで`CancelResponse.ACCEPT`を返すことでキャンセル要求自体を受理する。実際の処理停止は`execute_callback`側の責任で、ループの中で`goal_handle.is_cancel_requested`を都度チェックし、真になったら`goal_handle.canceled()`を呼んでからreturnする。`cancel_callback`を実装しないとデフォルトで拒否（`CancelResponse.REJECT`）される。

## 本文

### 学習内容：アクションとは何か

学習内容：アクションが解決する問題と、内部の3チャンネル構造を理解する。

準備：[06_サービス](06_サービス.md)まで完了していること。

内容：

サービスは呼び出したら結果が返るまでブロックします。これはロボットのナビゲーションのような、数秒から数分かかる処理には向きません。呼び出し側が固まってしまいますし、「途中でやめたい」も表現できません。アクションはこの2つの問題を解決するために、サービスの上に3つの通信チャンネルを重ねた仕組みです。

- **Goal**: クライアントがサーバに送る目標（サービスのリクエストに相当）
- **Result**: 処理が終わったときの最終結果（サービスのレスポンスに相当）
- **Feedback**: 処理中に定期的に流れる途中経過（トピックのpublishに相当）

つまりアクションは「サービス+トピック」を1つのインターフェースにまとめたものだと考えると理解が早いです。加えてゴールの受理/拒否、キャンセル要求、実行中/完了/失敗といった状態遷移も標準で持っています。

> コラム: `ros2 action list`、`ros2 action info`、`ros2 action send_goal`はトピック・サービスのコマンド群と対になっています。動いているアクションを確認するときはまずこれらを打つ癖をつけてください。

### 学習内容：アクション定義ファイルを書く

学習内容：`.action`ファイルの3セクション構造とrosidlのビルド設定を理解する。

準備：Colcon workspace（例: `~/ros2_ws`）が用意済みであること。

内容：

公式チュートリアルに倣い、Fibonacci数列を計算するアクションを作ります。パッケージ内に`action`ディレクトリを作り、`Fibonacci.action`を置きます。

```
mkdir -p ~/ros2_ws/src/custom_action_interfaces/action
```

```
# Fibonacci.action
int32 order
---
int32[] sequence
---
int32[] partial_sequence
```

`---`で区切られた3セクションが、そのままGoal/Result/Feedbackに対応します。上から順に「何番目まで計算するか（goal）」「最終的な数列（result）」「計算中の途中までの数列（feedback）」です。フィールド名や型は`.msg`ファイルと同じ書き方です。

`package.xml`に依存を追加します。

```xml
<buildtool_depend>rosidl_default_generators</buildtool_depend>
<depend>action_msgs</depend>
<member_of_group>rosidl_interface_packages</member_of_group>
```

`CMakeLists.txt`には次を追加します。

```cmake
find_package(rosidl_default_generators REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "action/Fibonacci.action"
)
```

ビルドしてインターフェースが生成されるか確認します。

```bash
cd ~/ros2_ws
colcon build --packages-select custom_action_interfaces
source install/setup.bash
ros2 interface show custom_action_interfaces/action/Fibonacci
```

3セクションが表示されれば成功です。`action_msgs`への依存を書き忘れるとビルドが通らないので、エラーが出たらまずここを疑ってください。

### 学習内容：ActionServerを実装する

学習内容：`rclpy.action.ActionServer`で`execute_callback`を実装し、`publish_feedback`と`succeed`を使う。

準備：`custom_action_interfaces`パッケージがビルド済みであること。加えて、サーバ／クライアントを置くPythonパッケージをまだ作っていないので、ここで作成します。

```bash
cd ~/ros2_ws/src
ros2 pkg create --build-type ament_python --license Apache-2.0 custom_action_python \
  --dependencies rclpy custom_action_interfaces
```

以降の`ros2 run custom_action_python ...`はこのパッケージを指しています。`setup.py`の`entry_points`への登録も忘れないでください。

内容：

サーバ側のノードを書きます。

```python
import time

import rclpy
from rclpy.action import ActionServer
from rclpy.node import Node

from custom_action_interfaces.action import Fibonacci


class FibonacciActionServer(Node):

    def __init__(self):
        super().__init__('fibonacci_action_server')
        self._action_server = ActionServer(
            self,
            Fibonacci,
            'fibonacci',
            self.execute_callback)

    def execute_callback(self, goal_handle):
        self.get_logger().info('Executing goal...')

        feedback_msg = Fibonacci.Feedback()
        feedback_msg.partial_sequence = [0, 1]

        for i in range(1, goal_handle.request.order):
            feedback_msg.partial_sequence.append(
                feedback_msg.partial_sequence[i] + feedback_msg.partial_sequence[i - 1])
            self.get_logger().info(f'Feedback: {feedback_msg.partial_sequence}')
            goal_handle.publish_feedback(feedback_msg)
            time.sleep(1)

        goal_handle.succeed()

        result = Fibonacci.Result()
        result.sequence = feedback_msg.partial_sequence
        return result


def main(args=None):
    rclpy.init(args=args)
    fibonacci_action_server = FibonacciActionServer()
    rclpy.spin(fibonacci_action_server)


if __name__ == '__main__':
    main()
```

`ActionServer`のコンストラクタには`self`、アクション型、アクション名（`fibonacci`）、そして実行本体である`execute_callback`を渡します。ゴールが受理されると`execute_callback`が呼ばれ、この中でフィボナッチ数列を1項ずつ計算しながら`goal_handle.publish_feedback(feedback_msg)`で途中経過をクライアントに流します。`time.sleep(1)`は本来の計算時間を模しているだけで、これがないとアクションを使う意味が薄れる（一瞬で終わる処理にアクションは大袈裟）ので講習用の演出だと理解してください。

ループを抜けたら`goal_handle.succeed()`を呼んでからResultを返します。**この呼び忘れが一番多いバグ**で、返り値だけ書いてステータス遷移を忘れるとクライアント側からは「結果は来たのに実行中扱いのまま」という中途半端な状態に見えます。

### 学習内容：ActionClientを実装する

学習内容：`send_goal_async`からgoal応答・feedback・resultまでの非同期フローを実装する。

準備：ActionServerを別ターミナルで起動しておきます。

```bash
ros2 run custom_action_python fibonacci_action_server
```

内容：

クライアント側は同期的に書けないのがポイントです。goal送信、goal受理の確認、feedbackの受信、result取得がすべて別々のコールバックに分かれます。

```python
import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node

from custom_action_interfaces.action import Fibonacci


class FibonacciActionClient(Node):

    def __init__(self):
        super().__init__('fibonacci_action_client')
        self._action_client = ActionClient(self, Fibonacci, 'fibonacci')

    def send_goal(self, order):
        goal_msg = Fibonacci.Goal()
        goal_msg.order = order

        self._action_client.wait_for_server()

        self._send_goal_future = self._action_client.send_goal_async(
            goal_msg,
            feedback_callback=self.feedback_callback)

        self._send_goal_future.add_done_callback(self.goal_response_callback)

    def goal_response_callback(self, future):
        goal_handle = future.result()
        if not goal_handle.accepted:
            self.get_logger().info('Goal rejected')
            return

        self.get_logger().info('Goal accepted')

        self._get_result_future = goal_handle.get_result_async()
        self._get_result_future.add_done_callback(self.get_result_callback)

    def get_result_callback(self, future):
        result = future.result().result
        self.get_logger().info(f'Result: {result.sequence}')
        rclpy.shutdown()

    def feedback_callback(self, feedback_msg):
        feedback = feedback_msg.feedback
        self.get_logger().info(f'Received feedback: {feedback.partial_sequence}')


def main(args=None):
    rclpy.init(args=args)
    action_client = FibonacciActionClient()
    action_client.send_goal(10)
    rclpy.spin(action_client)


if __name__ == '__main__':
    main()
```

流れを整理すると次の順番でコールバックが呼ばれます。

| 順番 | 呼ばれるもの | 役割 |
|---|---|---|
| 1 | `send_goal_async` | goalを送信し、futureを返す |
| 2 | `goal_response_callback` | サーバがgoalを受理/拒否したかを確認する |
| 3 | `feedback_callback` | 実行中、複数回呼ばれる。途中経過を受け取る |
| 4 | `get_result_callback` | 実行完了後に1回呼ばれる。最終結果を受け取る |

実行してみます。

```bash
ros2 run custom_action_python fibonacci_action_client
```

**課題**: クライアントを実行し、`feedback_callback`の内容がターミナルに1秒おきに流れ続けることを確認してください。サーバ側のログにも同じタイミングで出力が出ているはずです。

### 学習内容：キャンセル処理を実装する

学習内容：`cancel_callback`でキャンセル要求を受理し、`is_cancel_requested`で実行中の処理を安全に打ち切る。

準備：ActionServer実装ファイルを編集できる状態にしておきます。

内容：

先ほどのサーバは`ActionServer`のコンストラクタに`cancel_callback`を渡していないため、キャンセル要求はデフォルトで拒否されます。まずキャンセルを受理するコールバックを追加します。

```python
from rclpy.action import CancelResponse

def cancel_callback(self, goal_handle):
    self.get_logger().info('Received cancel request')
    return CancelResponse.ACCEPT
```

コンストラクタに渡します。

```python
self._action_server = ActionServer(
    self,
    Fibonacci,
    'fibonacci',
    execute_callback=self.execute_callback,
    cancel_callback=self.cancel_callback)
```

`cancel_callback`は「キャンセル要求を受け付けるかどうか」を決めるだけで、実際に処理を止めるのは`execute_callback`側の責任です。ループの中でキャンセル要求が来ていないかを都度チェックする必要があります。

```python
def execute_callback(self, goal_handle):
    self.get_logger().info('Executing goal...')

    feedback_msg = Fibonacci.Feedback()
    feedback_msg.partial_sequence = [0, 1]

    for i in range(1, goal_handle.request.order):
        if goal_handle.is_cancel_requested:
            goal_handle.canceled()
            self.get_logger().info('Goal canceled')
            return Fibonacci.Result()

        feedback_msg.partial_sequence.append(
            feedback_msg.partial_sequence[i] + feedback_msg.partial_sequence[i - 1])
        goal_handle.publish_feedback(feedback_msg)
        time.sleep(1)

    goal_handle.succeed()
    result = Fibonacci.Result()
    result.sequence = feedback_msg.partial_sequence
    return result
```

**課題**: クライアントで`order`を大きめの値（15程度）にして実行を開始し、途中で`ros2 action list`と`ros2 action info /fibonacci`を確認しつつ、別ターミナルからキャンセルを送ってみてください。`ActionClient`側でキャンセルするには、`goal_response_callback`で受け取った`goal_handle`を保持しておき、`goal_handle.cancel_goal_async()`を呼びます。サーバ側のログに`Goal canceled`が出ればキャンセルが機能しています。

<details><summary>解答</summary>

クライアント側にキャンセル用の呼び出しを追加する例です。

```python
def cancel_goal(self):
    self.get_logger().info('Canceling goal')
    future = self._goal_handle.cancel_goal_async()
    future.add_done_callback(self.cancel_done_callback)

def cancel_done_callback(self, future):
    cancel_response = future.result()
    if len(cancel_response.goals_canceling) > 0:
        self.get_logger().info('Goal successfully canceled')
    else:
        self.get_logger().info('Goal failed to cancel')
```

`goal_response_callback`の中で`self._goal_handle = goal_handle`として保持しておく必要がある点に注意してください。実行中に`cancel_goal`を呼ぶと、サーバ側の`execute_callback`は次のループ判定タイミングで`is_cancel_requested`が真になり、`goal_handle.canceled()`を経由して停止します。即座には止まらず、ループの粒度（今回は`time.sleep(1)`ごと）でしか止められない点が実機の経路追従などでは重要になります。

</details>

## 発展

第4部で使う`move_base_flex`は、経路追従を`ExePath`アクションで受け取ります。ロボットに「この経路を走ってくれ」と頼むのはgoal送信そのもので、走行中に流れる進捗（現在どのあたりを走っているか）はfeedbackそのもの、そして「走行中に止めたい」という要求はキャンセルそのものです。ここで書いたFibonacciサーバの構造が、経路追従という実際のロボット制御にそのまま対応していることを覚えておいてください。


## おわりに

アクションはトピックとサービスの組み合わせなので、コード量はサービスより増えますが、覚えることは「goal/result/feedbackの3セクション」と「succeed/abort/canceledで状態を確定させる」の2つに尽きます。キャンセル処理を実装し忘れているアクションサーバはよく見られるので、書いたら必ず途中キャンセルを試す習慣をつけてください。わからなければ先輩に聞きましょう。
