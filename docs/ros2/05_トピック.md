# ROS2講習05: トピック

## はじめに

この記事を終えると、トピックを使ってノード間でデータを流す仕組みを理解し、`turtlesim`の亀をコマンドラインから手動で走らせられるようになります。

前提は[04_ノード](04_ノード.md)を読み終えていることです。ノードが「何であるか」がわからないと、トピックの説明は宙に浮きます。

## 講習目標

- トピックのpub/subモデルを理解し、自分の言葉で説明できる
- `ros2 topic`系のコマンド（list/echo/info/hz/pub）を実際に打てる
- QoSの2つの基本設定（Reliable/Best Effort）の違いと、どちらを使うべきか判断できる

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境（[02_環境構築](02_環境構築.md)完了）
- `ros-jazzy-turtlesim`パッケージ（未インストールなら`sudo apt install ros-jazzy-turtlesim`）
- ターミナルを2〜3枚並べて開ける画面（tmuxでもウィンドウ分割でもよい）

### 時間配分の目安

- pub/subモデルの説明: 10分
- コマンド演習（list/echo/info/hz）: 15分
- 亀を手動で回す課題: 15分
- QoSの説明と口頭試問: 10分

### 口頭試問

**Q1. トピックとサービスの一番の違いは何ですか。**

模範解答: トピックは非同期の一方向配信（pub/sub）で、送り手は受け手の有無や応答を気にしない。サービスは同期的なリクエスト/レスポンスで、呼び出した側は結果を待つ。センサ値や`cmd_vel`のような「常に流れ続けるデータ」はトピック向き、「一度だけ計算結果を聞きたい」というものはサービス向き。

**Q2. `ros2 topic pub`で亀を走らせるコマンドを、リンギング（メッセージを1回だけ送る）と継続送信の両方で説明してください。**

模範解答: `ros2 topic pub /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0}, angular: {z: 1.8}}"`は1回だけメッセージを送って終了する。`--rate`オプションを付けて`ros2 topic pub --rate 1 /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0}, angular: {z: 1.8}}"`にすると1秒に1回のペースで送り続け、Ctrl+Cするまで亀が動き続ける。単発だと亀は少し進んですぐ止まるので、円を描かせたいなら継続送信が必要。

**Q3. LiDARのようなセンサのトピックにBest Effortが使われがちな理由を説明してください。**

模範解答: センサデータは高頻度で流れ続け、1つのメッセージを取り損ねても次のメッセージがすぐ来るため、再送のコストをかけるより新しい値を優先したい。Reliableだと再送のためのバッファや確認応答が発生し、遅延と負荷が増える。逆に一度きりの重要なコマンドや設定変更はReliableで確実に届けたい。

## 本文

### 学習内容：トピックとは何か

学習内容：pub/subモデルの基本を理解する。

準備：[04_ノード](04_ノード.md)まで完了していること。

内容：

ROS2のノードは互いに直接呼び合うことはほとんどありません。代わりに、トピックという名前付きのチャンネルにメッセージを流し込み（publish）、興味のあるノードがそれを受け取る（subscribe）という間接的なやり取りをします。送り手（publisher）は誰が受け取っているか知らず、受け手（subscriber）も誰が送っているか知りません。この非同期・多対多の構造がROS2の分散システムを支えています。

LiDARのスキャン値、IMUの姿勢、バッテリー残量、モータへの速度指令——ロボットの中を流れるデータのほとんどがトピックです。トピックはロボットの血流だと考えてください。血液が止まればロボットは動かず、逆に血流を見ればロボットの状態がだいたいわかります。デバッグの第一歩は「今どのトピックに何が流れているか」を確認することです。

### 学習内容：トピックを覗く

学習内容：`ros2 topic`コマンドで動いているトピックを確認する。

準備：turtlesimを起動しておきます。

```bash
ros2 run turtlesim turtlesim_node
```

内容：

別のターミナルを開いて、まずどんなトピックが存在するか一覧します。

```bash
ros2 topic list
```

`/turtle1/cmd_vel`、`/turtle1/pose`、`/turtle1/color_sensor`などが出てくるはずです。名前だけでは型がわからないので、型も一緒に見るには`-t`を付けます。

```bash
ros2 topic list -t
```

流れている中身を実際に見るには`echo`を使います。

```bash
ros2 topic echo /turtle1/pose
```

亀が動いていなければ何も表示されませんが、それも正しい挙動です。何も送られていないトピックは何も流れません。次に、別のターミナルからteleopを起動して矢印キーで亀を動かしてみましょう。

```bash
ros2 run turtlesim turtle_teleop_key
```

矢印キーを押している間、`echo`側の画面に座標や速度がリアルタイムで流れ続けるのを確認してください。

トピックの詳細情報（型、publisher数、subscriber数）は`info`で見られます。

```bash
ros2 topic info /turtle1/cmd_vel
```

```
Type: geometry_msgs/msg/Twist
Publisher count: 1
Subscriber count: 1
```

`turtle_teleop_key`がpublisherで、`turtlesim_node`がsubscriberです。実際にどんなプログラムがどう繋がっているかは、この数字を追うだけでかなり見えてきます。

流れる頻度を知りたいときは`hz`です。

```bash
ros2 topic hz /turtle1/pose
```

`turtlesim_node`は内部で一定周期（デフォルト約60Hz程度）で自分の座標をpublishし続けているため、動いていなくても値が出ます。

### 学習内容：メッセージ型を確認する

学習内容：トピックに流れるメッセージの構造を`ros2 interface show`で確認する。

準備：特になし。

内容：

`cmd_vel`にどんな値を送ればいいかは、メッセージ型を見ればわかります。

```bash
ros2 interface show geometry_msgs/msg/Twist
```

```
# This expresses velocity in free space broken into its linear and angular parts.

Vector3  linear
        float64 x
        float64 y
        float64 z
Vector3  angular
        float64 x
        float64 y
        float64 z
```

`Twist`は`linear`（並進速度）と`angular`（角速度）の2つの`Vector3`を持つだけの単純な構造です。地上を走るロボットなら`linear.x`（前後）と`angular.z`（旋回）だけ使うのが基本で、`linear.y`や`angular.x`などは無視されることが多いです（turtlesimも同様）。

ヒント：メッセージ型がわからないときは慌てず`ros2 interface show <型名>`を打つ癖をつけてください。フィールド名を覚える必要はありません、毎回調べれば十分です。

### 学習内容：亀を手動で回す

学習内容：`ros2 topic pub`でトピックに直接メッセージを送り込む。

準備：turtlesimが起動していること。teleopは終了しておいてかまいません。

内容：

コマンドラインから直接`cmd_vel`に速度を送ってみます。

```bash
ros2 topic pub --rate 1 /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0}, angular: {z: 1.8}}"
```

`--rate 1`は1秒に1回このメッセージを送り続けるという意味です。前進速度2.0と角速度1.8を同時に与えているので、亀は円を描きながら進みます。Ctrl+Cで停止してください。

**練習問題**: `--rate`を付けずに同じコマンドを打つと亀はどう動くか予想し、実行して確認してください。また、半径の大きい円を描かせるには`linear.x`と`angular.z`の比をどう変えればいいか考えてください。

<details markdown="1"><summary>解答</summary>

`--rate`を付けないと`ros2 topic pub`はメッセージを1回だけ送って終了します。亀はごく短い距離だけ弧を描いて止まります。継続的に動かすには`--rate`で送信を繰り返す必要があります。

円の半径は角速度に対する前進速度の比でおおよそ決まります。角速度`angular.z`を小さくするか、前進速度`linear.x`を大きくすると、同じ時間で進む距離が増えるのに対して向きの変化は変わらないため、円が大きくなります。逆に`angular.z`を大きくすると小さい円になります。

</details>

### 学習内容：QoSの触り

学習内容：トピックには通信品質の設定（QoS: Quality of Service）があることを知る。

準備：特になし。

内容：

トピックは「何を」流すかだけでなく、「どう」流すかも設定できます。これがQoS（Quality of Service）です。よく使う設定は次の2つです。

| 設定 | 挙動 | 使われる場面 |
|---|---|---|
| Reliable | 届くまで再送する。取りこぼしを許さない | `cmd_vel`、サービス的に使う重要なコマンド |
| Best Effort | 届かなければ届かないまま。再送しない | LiDAR/IMUなどのセンサ、映像 |

センサ系のトピックはBest Effortが標準的です。理由は口頭試問のQ3で説明した通りで、高頻度で流れ続けるデータは1つ取りこぼしても次が来ればいいので、再送のコストをかけないほうが低遅延で動きます。逆に一度しか送らない重要な指令はReliableで確実に届けたいところです。

実際に動いているトピックのQoSを確認するには`-v`（verbose）オプションを使います。

```bash
ros2 topic info -v /turtle1/cmd_vel
```

`Reliability: RELIABLE`のような行が出力に含まれます。publisherとsubscriberのQoSが噛み合っていないと通信が繋がらないことがあるので、「トピックが繋がっているはずなのに`echo`に何も出てこない」というときは、まずこの`-v`出力を疑ってください。

> コラム: QoSにはReliability以外にもHistory（直近N件だけ保持するか全件保持するかの方式）、Depth（そのN件の件数）、Durability（後から接続したsubscriberに過去のメッセージを渡すか）など複数の軸があります。HistoryとDepthは別のポリシーで、`create_publisher(..., 10)`の`10`はDepthのほうです。ここでは触りだけ扱いますが、実機でセンサ統合をする段階（[21_センサ統合](21_センサ統合.md)）で改めて向き合うことになります。

## 発展

トピックのpub/subは、実は裏側でDDS（Data Distribution Service）という通信ミドルウェアが動いています。ROS2はDDSの上に薄いAPIを被せたものだと考えると理解が早まります。

DDSにはノード同士が互いを見つけ合うdiscoveryという仕組みがあり、`ros2 node list`や`ros2 topic list`で他のノードやトピックが見えているのはこのdiscoveryのおかげです。同じネットワーク内で複数の環境のROS2が動いていると、意図せず互いのトピックが見えてしまうことがあります。これを避けるための`ROS_DOMAIN_ID`という環境変数がありますが、ここでは名前を知っておく程度で十分です。

深掘りは[05b_DDSとdiscoveryとROS_DOMAIN_ID](05b_DDSとdiscoveryとROS_DOMAIN_ID.md)で扱います。**部室で複数人が作業していて「他人のノードが見える」「自分のテストが落ちる」という状況に当たったら、先にそちらを読んでください。** 2つの環境変数を設定すれば解決します。1人で進めているうちは、この記事の続き（[06_サービス](06_サービス.md)）に進んで構いません。
