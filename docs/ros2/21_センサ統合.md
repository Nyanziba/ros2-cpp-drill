# ROS2講習21: センサ統合

## はじめに

この記事を終えると、LiDAR・IMUといった実センサのデータをROS2の標準メッセージとして受け取り、RViz2で可視化できるようになります。

前提は[18_TF2と座標系](18_TF2と座標系.md)（frame_idとtfの関係）と[20_ros2_control概要](20_ros2_control概要.md)です。センサ統合はメッセージの中身よりもむしろ座標系の扱いで詰まるので、TFの理解が浅いとこの記事の後半でつまずきます。

## 講習目標

- `sensor_msgs`の主要な型（LaserScan, PointCloud2, Imu, JointState）の構造とfield_idの役割を理解する
- LiDARドライバ（Livox系を例に）がどういうトピック・メッセージ形式でデータを出すかを説明できる
- RViz2でセンサデータが表示されないときに、Fixed Frameとframe_idの不一致を疑って直せる
- `pointcloud_to_laserscan`のような変換ノードが何のために存在するかを理解する

## 講習として使う場合

### 準備物

- Ubuntu 24.04 + ROS 2 Jazzy Jaliscoがセットアップ済みの環境
- bagファイル、またはLiDAR/IMU実機（利用可能なもの。実機が無ければbag再生で代替する）
- `ros-jazzy-rviz2`、`ros-jazzy-pointcloud-to-laserscan`（`sudo apt install ros-jazzy-pointcloud-to-laserscan`）
- Livoxドライバを使う場合は事前に`livox_ros_driver2`をビルドしておく（当日ビルドは時間がかかるので避ける）


### 時間配分の目安

- sensor_msgsの型とframe_id/stampの説明: 15分
- LiDAR/IMUドライバの実物確認: 15分
- RViz2で可視化・詰まりポイントの実演: 15分
- 課題（bagまたはドライバから点群を表示）: 15分
- 口頭試問: 10分

### 口頭試問

**Q1. `sensor_msgs/msg/PointCloud2`の`header.frame_id`を間違ったフレーム名にするとどうなりますか。**

模範解答: RViz2側では、その名前のフレームがtfツリーに存在しなければ「Fixed Frameからの変換ができない」というエラーになり点群が表示されない。存在はするが実際のセンサ位置と違うフレームだと、変換自体はできるがロボット座標系から見た点群の位置がずれる。tfが繋がっていないと詰むだけでなく、tfが繋がっていても間違ったフレームなら気づかれにくい形で自己位置推定の入力が壊れる。

**Q2. LiDARのトピックにBest EffortのQoSが使われがちな理由と、それがRViz2で反映されない場合に起きる現象を説明してください。**

模範解答: 高頻度で流れ続けるデータは1つ取りこぼしても次が来るので、再送コストをかけるより低遅延を優先する（[05_トピック](05_トピック.md)参照）。RViz2のサブスクライバがReliableのままだとpublisherのBest EffortとQoSが噛み合わず、トピック自体は`ros2 topic list`に見えているのに表示パネルには何も出てこないという現象になる。RViz2のDisplay設定でQoSをBest Effortに合わせる必要がある。

**Q3. `pointcloud_to_laserscan`のようなノードがなぜ必要ですか。3D LiDARのPointCloud2をそのまま使えばいいのではないですか。**

模範解答: 2D的な障害物回避やSLAMアルゴリズムの多くは`sensor_msgs/LaserScan`（1平面上の距離配列）を前提に作られている。3D LiDARのPointCloud2をそのまま渡すと計算量が増えるし、対応していないアルゴリズムもある。`pointcloud_to_laserscan`は点群を指定した高さ範囲でスライスしてLaserScan形式に変換し、既存の2Dベースのナビゲーションスタックに載せられるようにする役割を持つ。

## 本文

### 学習内容：sensor_msgsの標準メッセージを知る

学習内容：ROS2がセンサデータをどう型として表現しているかを理解する。

準備：特になし。

内容：

ROS2にはセンサの種類ごとに標準化されたメッセージ型があり、`sensor_msgs`パッケージにまとまっています。自作のメッセージ型でセンサデータを流すこともできますが、標準型を使うとRViz2やnav2、SLAMツールなど既存のツールがそのまま繋がるため、特別な理由がなければ標準型を使うべきです。

代表的な4つを見てみましょう。

```bash
ros2 interface show sensor_msgs/msg/LaserScan
```

```
std_msgs/Header header
float32 angle_min
float32 angle_max
float32 angle_increment
float32 time_increment
float32 scan_time
float32 range_min
float32 range_max
float32[] ranges
float32[] intensities
```

`LaserScan`は1平面をスキャンする2D LiDAR向けの型です。`angle_min`から`angle_max`まで`angle_increment`刻みで測った距離が`ranges`配列に並んでいます。配列のインデックスと角度が対応しているだけで、座標としてのx, y値は入っていない点に注意してください。

```bash
ros2 interface show sensor_msgs/msg/PointCloud2
```

`PointCloud2`は3D LiDARやDepthカメラが出す点群です。`ranges`のような単純配列ではなく、バイナリのバッファに(x, y, z, intensity, ...)を詰め込んだ可変フォーマットになっています。フィールド構成が`fields`に記述されているため、直接読むよりも`sensor_msgs_py`やpclのユーティリティを介して読むのが基本です。

```bash
ros2 interface show sensor_msgs/msg/Imu
```

```
std_msgs/Header header
geometry_msgs/Quaternion orientation
float64[9] orientation_covariance
geometry_msgs/Vector3 angular_velocity
float64[9] angular_velocity_covariance
geometry_msgs/Vector3 linear_acceleration
float64[9] linear_acceleration_covariance
```

`Imu`は姿勢（クォータニオン）、角速度、線形加速度と、それぞれの共分散行列を持ちます。共分散が全部0埋めのIMUドライバも多いですが、これはセンサ融合（EKFなど）にとっては「このセンサをどれだけ信用するか」の重みそのものです。0埋めのままだと融合側が正しく重み付けできないので、実際の値が取れないドライバでも最低限「だいたいこのくらい」という対角成分だけ入れておくべきです。

```bash
ros2 interface show sensor_msgs/msg/JointState
```

`JointState`はエンコーダやサーボの関節角度・角速度・トルクを名前付きで持つ型です。センサというよりアクチュエータ側の情報ですが、`robot_state_publisher`がTFを更新するための入力として使われるため、この記事で一緒に扱います。

### 学習内容：frame_idとstampの重要性

学習内容：`std_msgs/Header`の`frame_id`と`stamp`が何のためにあるかを理解する。

準備：[18_TF2と座標系](18_TF2と座標系.md)を読んでいること。

内容：

上に挙げた4つのメッセージは全て`std_msgs/Header header`を持っています。

```
builtin_interfaces/Time stamp
string frame_id
```

`frame_id`は「このデータがどの座標系を基準に測られたものか」を示す文字列です。LiDARの点群なら`lidar_link`、ロボット本体基準の値なら`base_link`のように、tfツリー上に実在するフレーム名を入れます。RViz2や他のノードは、この`frame_id`を見て「今表示したいFixed Frameとの間でどう変換すればいいか」をtfツリーから探します。frame_idが間違っていたり、tfツリーにそのフレームが存在しなければ変換できず、データはただ捨てられます。

`stamp`はそのデータが実際に取得された時刻です。複数センサのデータを組み合わせるとき（例: LiDARとIMUを同時刻の姿勢で統合する）、この`stamp`がずれているとどのタイミングの値を合わせるべきか分からなくなります。センサドライバの実装によっては、データを受け取った瞬間の時刻ではなく「実際にセンサが測定した瞬間の時刻」を`stamp`に入れることを意識しているものもあります。ここがずれるノードは、後段のSLAMや自己位置推定で謎の精度低下を起こすことがあるので覚えておいてください。

> コラム: `frame_id`と`stamp`は一見おまじないのように見えるフィールドですが、実際にはセンサ統合の大半のバグがこの2つに起因します。「トピックは流れているのにRViz2に出ない」「複数センサを統合すると精度が落ちる」と感じたら、まずこの2つを疑ってください。

### 学習内容：LiDARドライバの一般的な使い方

学習内容：市販LiDARのROS2ドライバがどうデータを出すかを、Livox MID360を例に理解する。

準備：特になし。

内容：

3D LiDARを使う場合、多くのメーカーが専用のROS2ドライバパッケージを提供しています。Livoxの場合は`livox_ros_driver2`というパッケージが公式に配布されており、シリアル/イーサネット経由でセンサと通信してROS2トピックにデータを流し込みます。

`livox_ros_driver2`は標準の`sensor_msgs/PointCloud2`に加えて、独自の`livox_ros_driver2/msg/CustomMsg`という型でも点群を出すことができます。`CustomMsg`は各点にタイムスタンプ・タグ・ライン番号を持たせた形式で、標準の`PointCloud2`より細かい情報を保持できますが、標準ツール（RViz2、nav2など）とはそのまま繋がりません。標準の`PointCloud2`出力に設定しておけば既存のツールチェーンにそのまま載るので、特別な理由がなければ`PointCloud2`出力を使うのが安全です。

```bash
ros2 topic list | grep -i livox
```

典型的には`/livox/lidar`（PointCloud2）や`/livox/imu`（内蔵IMUがある機種の場合）のようなトピック名で流れます。実際のトピック名やQoS設定はドライバの設定ファイル（`config`ディレクトリ以下のyaml）で変えられるため、使う前に一度`ros2 topic info -v <トピック名>`でQoSと型を確認する癖をつけてください。


### 学習内容：IMUの座標系と共分散

学習内容：IMUデータを使うときに確認すべき座標系の向きと共分散の扱いを理解する。

準備：特になし。

内容：

IMUは搭載する向きによって軸の定義がずれることが多いセンサです。ROS2の慣習ではx軸前方・y軸左・z軸上（右手系）に揃えることが期待されていますが、IMU基板をロボットにそのまま貼り付けると軸が逆や90度回転していることがよくあります。ドライバ側で軸を補正して出しているものもありますが、そうでない場合はIMUのフレームと`base_link`の間の静的な回転を表す`static_transform_publisher`をtfに追加して、座標系のズレをtf側で吸収する必要があります。

```bash
ros2 run tf2_ros static_transform_publisher --x 0 --y 0 --z 0 --roll 0 --pitch 0 --yaw 1.5708 --frame-id base_link --child-frame-id imu_link
```

このコマンドはIMUがz軸周りに90度回転して取り付けられている場合の補正例です。実際の値はセンサの取り付け方によって変わるので、まずCADや実物で取り付け角度を確認してから決めてください。

共分散については前節で触れた通り、EKFなどのセンサ融合ノードに渡す重みそのものです。`ekf_params`のようなローカライゼーションノードの設定を見ると、`process_noise_diag`のように各センサの信頼度を対角成分で指定する仕組みになっているものが多く、IMU側の共分散が正しく入っていないとこの重み付けが機能しません。

### 学習内容：RViz2で可視化する

学習内容：RViz2でセンサデータを表示し、典型的な詰まりポイントを解消する。

準備：LiDARドライバまたはbagを再生できる状態にしておきます。

内容：

RViz2を起動します。

```bash
rviz2
```

左上の「Add」から`LaserScan`または`PointCloud2`のDisplayを追加し、Topicに実際のトピック名（例: `/scan`や`/points`）を指定します。ここで最もよく起きる詰まりポイントが**Fixed Frameの設定ミス**です。

RViz2の左パネル「Global Options」の`Fixed Frame`が、センサメッセージの`frame_id`とtfで繋がっていないフレーム名になっていると、Displayパネルに赤いエラーマークが出て何も表示されません。よくある間違いは次の3つです。

- `Fixed Frame`が`map`になっているが、まだSLAM/AMCLが起動していないため`map`フレームがtfツリーに存在しない
- センサの`frame_id`が`lidar_link`なのに、`static_transform_publisher`や`robot_state_publisher`で`lidar_link`が`base_link`から見た変換として登録されていない
- QoSがBest Effortのトピックに対して、RViz2のDisplay側QoSがReliableのままで噛み合っていない（[05_トピック](05_トピック.md)のQoS参照）

確認の第一歩は`ros2 run tf2_tools view_frames`か`ros2 run rqt_tf_tree rqt_tf_tree`でtfツリーを見ることです。センサのフレームが孤立していないか、`Fixed Frame`に指定した名前まで繋がっているかをここで確認してください。

**練習問題**: `Fixed Frame`を`odom`にした状態で、点群のDisplayに赤いエラーが出たとします。考えられる原因を2つ挙げてください。

<details><summary>解答</summary>

1つは、点群の`frame_id`（例: `lidar_link`）から`odom`まで繋がるtfのチェーンが存在しない、または途中の`static_transform_publisher`やドライバのtfブロードキャストが起動していないこと。もう1つは、点群のトピックのQoSとRViz2のサブスクライバQoSが噛み合っておらず、そもそもメッセージ自体が届いていないこと（この場合はエラーメッセージの文言が「フレームが見つからない」ではなく「データが来ない」に近い形になる）。`ros2 topic hz`でデータが実際に流れているかを先に確認すると、どちらが原因か絞り込みやすくなります。

</details>

### 学習内容：pointcloud_to_laserscanで型を変換する

学習内容：3D点群を2Dのナビゲーションスタックで使える形式に変換する。

準備：`ros-jazzy-pointcloud-to-laserscan`がインストールされていること。

内容：

3D LiDARのPointCloud2をそのまま2D的な障害物検知やSLAMに使いたい場合、`pointcloud_to_laserscan`パッケージのノードを挟むのが定番です。指定した高さ範囲にある点だけを抜き出し、角度ごとの最短距離を計算して`LaserScan`として再パブリッシュします。

```bash
ros2 run pointcloud_to_laserscan pointcloud_to_laserscan_node \
  --ros-args \
  -r cloud_in:=/points \
  -r scan:=/scan \
  -p target_frame:=base_link \
  -p min_height:=-0.1 \
  -p max_height:=0.3
```

`min_height`/`max_height`は`base_link`から見た高さの範囲です。ロボットの走行面付近に絞ることで、天井や壁の上部にある無関係な点を無視できます。この高さの決め方はロボットの車高やセンサの取り付け高さに依存するので、一律の正解値はありません。実際に`rviz2`で点群を見ながら、走行の障害物として拾いたい範囲を目で確認して決めるのが安全です。

## 発展

このLiDAR/IMU/PointCloud2の値は、そのまま次の[22_自己位置推定の考え方](22_自己位置推定の考え方.md)の入力になります。自己位置推定アルゴリズム（AMCL、NDT、EKFなど）は「このセンサ値からロボットが今どこにいるか」を計算するものですが、入力となるセンサ値のframe_id・stamp・共分散が正しくなければ、アルゴリズムがいくら優秀でも精度は出ません。この記事で扱った詰まりポイントは、22で自己位置推定がうまく動かないときに最初に見直すべき箇所でもあります。

複数のLiDAR/カメラを1台のロボットに載せて点群を統合する（extrinsic calibrationやマルチセンサfusion）話は、それ自体が1記事分のテーマになるため、ここでは扱いません。


## おわりに

センサ統合は「動いているように見えて実は繋がっていない」という状態が一番厄介です。トピックが流れていること、frame_idが正しいこと、tfが繋がっていること、この3つを順番に確認する癖をつけましょう。わからなければ先輩に聞きましょう。

次は[22_自己位置推定の考え方](22_自己位置推定の考え方.md)で、ここで整えたセンサ値を使って実際に自己位置を推定します。
